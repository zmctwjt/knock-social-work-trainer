# 功能合理性评价与后续规划

评价时间：2026-11-19
评价依据：代码现状 + 实际运行观测 + 21 轮迭代中积累的验证证据

---

## 一 评价方法与标准

不按"功能多不多"评，按四条标准：

| 标准 | 追问的问题 |
| --- | --- |
| **切题** | 是否服务"个案面谈能力训练"这个核心目标，而不是可有可无的点缀 |
| **可验证** | 是否有测试或实测证据，而不是"应该能用" |
| **口径一致** | 同一个指标在不同路径下是否同一算法，否则数据不可比 |
| **有出口** | 失败时是否有降级/兜底，而不是白屏或报错 |

结论分四档：**保留** / **需改进** / **合并** / **建议下线**。

---

## 二 整体判断

**核心链路是成立的，外围有几处不一致需要收口。**

成立的证据：
- 训练闭环完整走通（浏览器 E2E：输入 → AI 台词 → 六维评分 → 结算 → 成长记录 → 危机拦截）
- 六维评分可溯源到《社会工作方法 个案工作》具体条款，不是黑箱打分
- 危机内容本地硬规则短路，零模型调用（有测试断言 provider 未被调用）
- 四角色权限矩阵有 15 项端到端审查，越权一律 403
- AI 三级降级链实测有效：换无效密钥后四条链路全部 200 并降级

不成立的短板：见第四节，主要是**数据归属**与**评分口径**两处。

## 四 发现的真实问题（按严重度）

### 问题 1：训练记录有两套数据源，且用昵称归属 —— 严重

**证据**
- 成长中心读 `store.records`（浏览器 localStorage）：
  `useMyRecords()` 里 `records.filter(r => r.nickname === account.nickname)`
- 教师端读服务端 `training_records` 表
- 提交训练时**两边都写**（`addRecord` + `saveTraining`）

**后果**
1. 学生换设备或清缓存后，自己的成长中心为空，但教师仍能看到他的记录
2. 用**昵称**匹配归属：两个同昵称的学生在同一台设备上会互相看到对方数据

**怎么改**：成长中心改为读服务端 `/api/v1/stats/me`（已有接口），
localStorage 只保留"未登录演练"用途并明确标注。

### 问题 2：评分口径在两种模式下不同源，统计却不区分 —— 严重

**证据**
- `MERGE_RATIO = {"rule": 0.4, "ai": 0.6}`，AI 可用时综合分 = 规则 40% + AI 60%
- AI 不可用时 `merge_scores()` 直接返回 `rule_safe`，即 **100% 规则分**
- 记录里存了 `score_source: 'blend' | 'rule'`，但**所有统计都没用它**

**后果**：同一学生的成长曲线、班级均分里混着两种算法算出的分数，
跨时段比较失真。答辩若被问"你的评分标准一致吗"，目前答不上来。

**怎么改**（两步）
1. 统计接口按 `score_source` 分组返回，界面标注"本段含 AI/纯规则"
2. 或更彻底：把规则分作为唯一锚点，AI 只在规则分 ±15 区间内微调，
   保证两种模式可比

### 问题 3：孤儿页面 `/editor` —— 中等

366 行代码、有路由、**界面无任何入口**。属原 Node 项目遗留。
建议下线，减少维护面与评审困惑。

### 问题 4：教师端「内容查阅」与学员端「知识库」重复 —— 轻

同一份知识卡数据两个入口。教师端只是少了案例/维度筛选。
建议教师端删掉该 tab，导航里已有的「知识库」足够。

### 问题 5：访客模式价值不明确 —— 轻

`/knowledge` 本身在未登录可访问名单里（`OPEN = ['/', '/about', '/knowledge']`）。
访客账号能做的事，未登录用户本来就能做；却要占一条账号记录、
进统计、出现在账号列表。建议下线，或改为"演示专用账号"并标注用途。

### 问题 6：无剧透模式与"即时反馈"存在张力 —— 需产品决策

设置项 `blindfold_default` 默认关闭分数显示。动机可理解（减少分数焦虑），
但本系统的核心卖点就是"说一句当场告诉你共情到位还是越界"。
开无剧透等于把卖点关掉。建议保留但**默认关闭**，并在引导里说明适用场景
（如考前模拟、纯对话练习）。

## 五 后续规划

> **执行状态（2026-11-19）**
> - 阶段一：✅ 已完成（第 17 轮）——4 项全部落地
> - 阶段二：✅ 已完成（第 18 轮）——4 项全部落地

>   K8s 静态校验未做

### 阶段一：口径与归属统一（最高优先，影响数据正确性）

| # | 任务 | 验收标准 |
| --- | --- | --- |
| 1 | 成长中心改读服务端统计 | 换浏览器登录同一账号，成长数据一致；`audit_growth_consistency.py` 通过 |
| 2 | 记录归属从昵称改为 account_id | 两个同昵称账号互不可见对方记录（加测试） |
| 3 | 统计按 score_source 分组 | `/stats/me` 返回 blend/rule 两段，界面标注来源 |
| 4 | 补迁移或兼容旧本地数据 | 已有 localStorage 记录可一次性上云或明确丢弃 |

### 阶段二：功能收口（减少困惑）

| # | 任务 | 验收标准 |

| 7 | 访客模式决策：下线 或 明确为演示账号 | 若下线：登录页去掉访客按钮，`/auth/guest` 标注 deprecated |

| # | 任务 | 验收标准 |

### 明确不做（避免范围蔓延）

- 作业分发、班级实体、多班级管理 —— 任务书未要求，属教务系统职责
- 教师给学生打分/排名 —— 与"AI 陪练 + 教师观察"的定位冲突
- 富文本/附件/图片上传 —— 无场景，且扩大攻击面
- 移动端原生 App —— 浏览器方案已满足实训室场景

## 六 一句话总结

**核心（训练-评分-复盘-危机）立得住，外围有 2 个数据口径问题必须修、
4 处功能需要收口。** 阶段一做完，系统的"可比较性"才真正成立；
阶段二做完，界面与文档才不留困惑；阶段三属于加分项。

建议按阶段一 → 二 → 三推进，不要先做阶段三（工程指标好看但不解决数据问题）。
