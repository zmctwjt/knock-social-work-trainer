# 第10章 验收标准与上线检查单

验收的作用不是"证明做完了"，而是把"能不能上线"从主观判断变成一组可复核的判定。本章给出三层验收：交付物验收（东西齐不齐）、功能与非功能验收（对不对、快不快、稳不稳）、上线 Go/No-Go 检查单（敢不敢切）。三层之间是递进关系——任一层不通过，下一层不启动；检查单中任何一项为否则整体判定 No-Go，不允许"带条件上线"。

## 10.1 验收原则

- **可判定**：每条标准必须能用命令、截图、报告或第三方工具输出佐证，不接受"已确认""基本可用"这类描述。
- **可复现**：验收在 staging 环境执行，环境构建方式与生产一致（同一镜像、同一迁移版本、同一配置模板）。
- **双人确认**：涉及成绩口径与危机拦截的验收项，须由学生与指导教师（或同行评审）共同签字。
- **一票否决**：四条业务铁律（危机永不调模型、台词白名单、AI 失败静默降级、成绩服务端权威）任一被破坏，其余项即便全绿也判定不通过。

## 10.2 交付物验收

| 编号 | 交付物 | 验收方式 | 通过标准 |
|---|---|---|---|
| D1 | 主文档 docx | 打开检查 | 封面/摘要/目录/10 章/3 附录齐全；目录可更新且条目完整；无"[待补充]"；图表编号连续 |
| D2 | 章节 Markdown 源 | 文件清点 | 14 个 md 文件齐全，与 docx 内容一致；单章字数达大纲下限 80% 以上 |

| D4 | Python 后端 | `pytest` + 启动冒烟 | 测试全绿；`uvicorn` 启动后 `/healthz` 返回 200；`/metrics` 有指标输出 |
| D5 | 部署制品 | 语法校验 + 演练 | 全部 YAML/JSON 可解析；`docker compose up` 起全栈；`kubectl apply --dry-run=server` 通过 |
| D6 | 实施计划 xlsx | 打开检查 | WBS/甘特/风险三表齐全，与第9章表 9-5、9-7 逐行对应 |

### 10.3.2 业务铁律验收

四条铁律单列，因为它们的失败不是"缺陷"而是"改坏了原作"。

| 铁律 | 验收方法 | 通过标准 |
|---|---|---|
| 危机永不调模型 | 用 20 条危机样本直连 API，检查审计日志与 mock 供应商调用计数 | 模型调用次数为 0；响应含危机引导；审计记录 `intercepted=true` |
| 台词白名单 | 构造 50 轮对话，检查所有服务对象台词的来源标记 | 100% 命中白名单（`script_line_id` 非空）；模型生成文本仅作为"润色"且被标注 |
| AI 失败静默降级 | 分别注入超时、429、非 JSON、熔断打开四类故障 | 四类均返回可用结果，`used_ai=false`，无 5xx |
| 成绩服务端权威 | 用篡改过的前端请求（自造高分）提交 | 服务端忽略客户端分数，按规则重算；最终分数与离线复算一致 |

**表 10-3 业务铁律验收**

这四项验收必须在 staging 完成并留下截图与日志片段。其中"台词白名单"一项最容易在移植中被忽略——Python 侧如果直接用模型输出替代白名单台词，功能看似正常，但业务铁律已经失效。

## 10.4 非功能验收

### 10.4.1 性能与容量

| 指标 | 目标 | 测量方法 | 判定 |
|---|---|---|---|
| 非 AI 接口 P95 | ≤ 300 ms | k6 场景一，稳定 10 分钟 | 达标 |
| AI 接口 P95 | ≤ 6 s | k6 场景二（mock 供应商固定 200 ms） | 达标 |
| 峰值吞吐 | ≥ 100 RPS，错误率 < 0.5% | k6 渐进加压至 100 RPS | 达标 |
| 并发在线 | 500 虚拟用户 30 分钟无内存泄漏 | k6 + 进程 RSS 监控 | 达标 |
| 数据库连接 | 池使用率 < 80% | PgBouncer 指标 | 达标 |
| 冷启动 | Pod 就绪 ≤ 30 s | 部署记录 | 达标 |

**表 10-4 性能验收指标**

AI 接口压测必须使用 mock 供应商，否则既会产生真实费用，也会因供应商限流导致结果不可解释；真实供应商只做小流量（10 次）连通性验证。

### 10.4.2 可用性与恢复

| 项 | 验收方式 | 通过标准 |
|---|---|---|
| SLO 计算 | 用 7 天 Prometheus 数据计算可用性 | ≥ 99.9%（不含计划内维护） |
| 备份可恢复 | 从最近全备 + WAL 恢复到新实例 | 数据完整，RTO ≤ 1 h，RPO ≤ 15 min |
| 回滚演练 | L1/L2/L3 三级各一次 | 均在时限内恢复，记录耗时 |
| 单点故障 | 停一个 API Pod、重启 Redis、主库切从 | 服务可用性下降但无 5xx 雪崩 |
| Redis 故障降级 | 停 Redis | 限流 fail-open 为内存计数，AI 缓存跳过，服务不中断 |

**表 10-5 可用性与恢复验收**

"Redis 故障降级"一项来自第7章的失败模式分析：缓存与限额不是核心链路，不能因为 Redis 挂掉就让全站 503。验收时要确认降级路径真的存在，而不是文档里写了。

## 10.5 上线检查单（Go/No-Go）

检查单按时间轴分三段，每段由不同角色执行：发布前由开发自检，发布时由值班人逐项打勾，发布后由指导教师确认。全部勾选方可判定 Go。

### 10.5.1 发布前（T-7 至 T-1）

- [ ] 主干分支 CI 全绿（lint/test/build/scan 四段）
- [ ] 镜像已推送至 SWR，tag 与 commit 对应，digest 已记录
- [ ] 数据库迁移脚本在 staging 空库与生产副本各演练一次，回滚脚本可用
- [ ] 配置项与附录B 清单逐项核对，无新增未登记变量
- [ ] 密钥已写入 KMS/Secret，镜像与仓库中无明文
- [ ] 备份已执行且验证可恢复
- [ ] 性能压测报告达标（表 10-4）
- [ ] 安全扫描无 CRITICAL，HIGH 已处置
- [ ] 回滚演练（L1/L2）通过并记录耗时
- [ ] 告警规则已加载，通知渠道测试通过
- [ ] 值班表与升级路径已公布
- [ ] 变更公告已发出（面向试点用户）

### 10.5.2 发布时（T-0）

- [ ] 发布窗口内无其他变更并行
- [ ] 数据库迁移先执行且校验通过（先兼容后切换）
- [ ] 新版本 Pod 就绪数与期望一致，`/readyz` 全绿
- [ ] 灰度 5% 已生效，观察 10 分钟
- [ ] 五项核心指标正常：错误率、P95、降级率、配额余量、DB 连接数
- [ ] 无新增 P0 告警
- [ ] 抽样 3 笔真实训练走通全流程（含危机样本一条）
- [ ] 回滚命令已就绪（一条命令可回切，且已知执行人）

### 10.5.3 发布后（T+0 至 T+7）

- [ ] 24 小时内错误率与延迟无异常抬升
- [ ] 一致率抽样 ≥ 99%（与灰度期基线比较）
- [ ] AI 降级率在预期区间（< 5%）
- [ ] 审计日志无异常（无 crisis + used_ai=true 组合）
- [ ] 用户反馈渠道无 P0 投诉
- [ ] 连续 7 天 SLO 达标，错误预算消耗 < 30%
- [ ] 发布记录、指标截图、事故单一并归档

### 10.5.4 No-Go 判定

出现以下任一情况即判定 No-Go，执行回退，不讨论"再观察一下"：

1. 四条业务铁律任一被证伪；
2. 越权或数据泄露被复现；
3. 数据库迁移不可回滚或校验失败；
4. 错误率 > 2% 持续 10 分钟，或 P95 > 8 s 持续 10 分钟；
5. 备份不可恢复；
6. 关键告警通道失效（告警发不出去等于没有监控）。

## 10.6 演进路线

一期（本次交付）完成"可上线的生产级单院系系统"。后续演进按"先深度、后广度"排序：

| 阶段 | 能力 | 前置条件 | 价值 |
|---|---|---|---|
| 二期 | 对象存储报告导出、教师端班级报表、题库版本管理 | 一期稳定运行 1 学期 | 教学闭环 |
| 二期 | AI 供应商多活与成本路由（按链路选模型） | 网关稳定、有成本数据 | 降本 20%–30% |
| 三期 | 多租户（多院系/多校）与计费 | 一期数据模型预留 tenant_id | 产品化 |
| 三期 | 语音面谈（ASR/TTS）与视频复盘 | 音频存储与合规评估 | 训练真实感 |
| 三期 | 评分模型校准（用教师评分做监督） | 积累 ≥ 5,000 条教师标注 | 评分可信度提升 |

**表 10-9 演进路线**

演进的前提是一期把"可扩展点"留对：数据模型预留 `tenant_id`、AI 网关按链路配置模型、对象存储只暴露接口不暴露实现。这三点在第5、6章已落实，因此二三期不需要重构主干。

## 10.7 本章小结

- 验收分交付物、功能与非功能、上线检查单三层递进，任一层不通过不进入下一层；四条业务铁律具备一票否决权。
- 功能验收 15 条用例中 9 条为 P0，覆盖登录、越权、危机拦截、降级与幂等；铁律验收必须用注入故障与直连 API 的方式验证，不接受"看代码没问题"。
- 非功能验收覆盖性能、可用性、安全、可观测、代码与文档五组，全部给出可执行的测量方法与判定阈值。
- 上线检查单按 T-7/T-0/T+7 三段共 27 项，全部勾选方可 Go；No-Go 的六种情形明确列出，且不支持"带条件上线"。
- 演进路线按"先深度后广度"排序，一期预留的 tenant_id、按链路模型配置、对象存储接口是二三期不重构主干的前提。
