# 第 1 章 现状分析

本章以交付包内 70 个有效源码文件、16,331 行代码为唯一证据来源，从技术栈与代码构成、运行时架构、核心业务流程、AI 调用链路、存储现状、构建运行与质量保障七个维度还原系统真实形态。文中所有数字均取自 FACTS.md，证据统一以"源码目录相对路径:行号"标注，为第 2 章的问题诊断提供可复核的事实基础。

## 1.1 项目背景与定位

"叩门·社工个案面谈 AI 陪练舱"是一个面向社会工作专业学生的个案面谈实训系统，作品版本 1.1.0，专业依据为民政部《社会工作方法 个案工作》（公告第 426 号）。系统让学生在浏览器中与 12 位虚拟服务对象进行多轮面谈，训练建立关系、问题探索、评估与介入三类能力，训练结束后按同感、提问、建议、伦理、过程、风险六个维度给出评分，并对自杀风险与无望感两类危机信号实施分级处置。

系统的设计取向可以概括为"规则主干、AI 长尾"。确定性部分由 171 条判定词表（九表 165 条 + 6 条封闭提问后缀）、118 个台词节点、19 张技巧卡、11 条伦理守则加 1 条边界声明、六维底分公式与三级风险分级构成，全部以 TypeScript 常量与纯函数形式固化在前端；不确定性部分（自由表达的意图归类、服务对象台词生成、语义评分、复盘报告）交给智谱 GLM-4.7-Flash，并约定"危机永不调模型、模型失败静默降级、台词必须过白名单"三条铁律。这一取舍使系统在没有大模型时仍可完整跑通，属于有价值的专业设计。

从使用者视角看，系统目前只覆盖学生的单人练习路径。学生打开页面即可获得 12 个角色、三档难度与三档 AI 参与度的完整体验；教师与督导角色在系统内没有任何入口——没有班级、没有作业布置、没有成绩汇总、没有审阅与批注，也没有对训练记录的抽查机制。这意味着系统还无法进入真实课程的教学流程：教师不知道谁练了、练到什么程度、是否需要干预，督导也无法复核评分是否合理。生产化的第一诉求正是补齐这一侧，第 5 章的三角色 RBAC 与第 6 章的训练记录查询接口都由此而来。

从交付形态看，系统是一个单机演示程序：`start.bat` 或 `start.sh` 检查 Node 版本、安装依赖、构建前端、启动内置 HTTP 服务，随后在 8787 端口提供服务。它没有教师端管理后台，没有真实身份体系，没有多租户隔离，没有部署脚本与运行监控，数据默认落在浏览器 localStorage 中。因此，本项目的准确定位是"课程作品级单机演示系统"——它验证了专业模型与交互设计，但工程形态尚未进入生产系统范畴。第 2 章将逐项量化这一差距。

## 1.2 技术栈与代码构成

## 1.3 运行时架构

生产运行的拓扑只有一个进程。`server/index.mjs` 通过 `node:http` 创建服务，监听 8787 端口（端口常量见 `server/glm.mjs:59`，可由 `PORT` 覆盖），在同一进程内承担三类职责：

第一，AI 代理。四条形如 `/api/ai/{intent|persona|score|debrief}` 的路径在 `server/index.mjs:112-219` 的 `ROUTES` 表中分发，统一先过 IP 限流，再读请求体，再交给对应处理函数组装提示词，最终调用 `glm.mjs` 的 `chat()` 访问智谱接口。代理层不保存会话、不鉴权、不写数据库，只做参数截断与提示词拼装。

第二，静态资源托管。`serveStatic` 在 `server/index.mjs:223-274` 中把 `dist/` 映射为站点根目录，路径先经 `normalize` 防止目录穿越（`:228-232`），命中带哈希的构建产物时返回一年期 immutable 缓存头（`:267-271`），未命中且无扩展名时回退 `index.html` 以支持前端路由（`:243`）。若 `dist/` 不存在，则返回 503 与中文构建提示（`:246-258`），避免出现空白页。

第三，健康与运维端点。`/api/health` 返回 AI 是否配置、主模型与降级模型、是否关闭思维链、超时、用量快照、端口与 uptime（`:300-314`）；`/api/usage` 返回用量快照（`:316-319`）；`/api/selftest` 触发一次极小模型请求（`:321-329`）。这三个端点都不需要认证。

请求处理顺序为：`setCors` 写 CORS 头（`:52-62`）→ OPTIONS 直接 204（`:281-284`）→ 非 `/api` 路径只允许 GET/HEAD（`:289-296`）→ 命中 AI 路由则限流、读体、分发（`:331-349`）→ 其余交给静态托管 → 最终 404（`:351`）。可用下面的路由骨架概括：

```js
// server/index.mjs:331-351
const m = pathname.match(/^\/api\/ai\/(intent|persona|score|debrief)$/);
if (m && req.method === 'POST') {
  const fn = m[1];
  if (!allowIp(clientIp(req))) {
    sendJson(res, 429, {
      ok: false, usedAI: false,
      error: { code: 'RPM', message: '请求过于频繁，请稍候再试' },
    });
    return;
  }
  try {
    const body = await readBody(req);
    const out = await ROUTES[fn](body);
    sendJson(res, 200, out);
  } catch (e) {
    fail(res, e, { usedAI: false });
  }
  return;
}
sendJson(res, 404, { ok: false, error: { code: 'NOT_FOUND', message: `未知接口 ${pathname}` } });
```

这条链路有几个值得注意的工程特征。其一，静态资源与 API 同源同端口，前端不需要配置跨域，但也意味着静态站点与模型代理共享同一个进程的事件循环，静态文件读取与模型等待会互相影响。其二，代理层对请求只做截断不做校验：`readBody` 只保证体积不超过 512 KB，字段级只截取长度（原话 600 字、对话 8,000 字、系统提示词 4,000 字），不校验类型与枚举，非法结构由下游解析函数兜底返回 null。其三，失败路径统一走 `fail()`，把异常映射为 `{ok:false, error:{code,message}}`，前端只读 `ok` 与 `error.code`，不再区分业务失败与系统故障。其四，进程没有任何优雅停机逻辑，收到终止信号时正在等待模型返回的请求会被直接切断。

模型出口集中在 `server/glm.mjs`：主模型 `glm-4.7-flash`，失败后按 `glm-4.5-flash`、`glm-4-flash` 顺序降级（`server/glm.mjs:44-49`）；每次请求固定关闭思维链（`:199`），超时 45 秒（`:51`）；单 IP 每分钟 20 次（`:103-116`），全局并发 2（`:118-131`），日调用上限 800 次（`:185-187`），相同请求体 10 分钟内命中内存缓存（`:135-155`）。这些计数全部在进程内存中，重启即清零。

单进程形态带来一个直接后果：所有运行时状态都随进程生死。限流窗口、日调用计数、结果缓存、并发信号量全部存在内存里（`server/glm.mjs:64-155`），进程重启即归零，横向扩容时副本之间互不共享。以日调用上限 800 次为例，若部署两个副本，实际可用额度会变成 1,600 次；若在额度耗尽后重启，额度立即恢复。缓存同理，10 分钟窗口内相同请求体可命中缓存，但缓存键是请求体的 SHA-1，跨进程无法共享，命中率随副本数增加而下降。并发信号量固定为 2，意味着同一时刻最多两个模型请求在飞，第 3 个请求在进程内排队等待，排队时间不计入 45 秒模型超时，前端 60 秒超时反而先触发。

存储侧有两种模式。未配置 `VITE_SUPABASE_URL` 与 `VITE_SUPABASE_ANON_KEY` 时，`dbReady` 为 false（`src/lib/db.ts:13-22`），所有数据写入 localStorage，云端函数直接返回空；配置后，`saveTraining` 会向 `training_records`、`training_details`、`proficiency` 三张表写入（`src/lib/db.ts:83-146`），但页面读取路径并不改走云端——这一点在 1.6 节展开。现状运行时架构如图 1-1 所示。

![图 1-1 现状运行时架构](figures/fig-01-current-arch.png)

需要指出的是，这个架构并不是"前端 + 后端"的常规两层结构，而是"业务全在前端 + 极薄 AI 代理"的浏览器自治结构。代理层存在的唯一理由是隐藏模型密钥并规避智谱接口的跨域限制（`server/index.mjs:1-12` 注释对此有明确说明），它不具备业务权威性，也无法对前端提交的成绩做任何校验。

## 1.4 核心业务流程

### 1.4.1 账号与入口

系统没有服务端账号体系。登录页提供"登录/注册"两个页签，注册与登录都在浏览器内完成：口令经 djb2 变体哈希后存入 `knock.accounts`，当前账号存入 `knock.currentAccount`（`src/store/store.tsx:91-101`、`:158-183`）。源码注释自认该哈希"仅本地演示，不能用于生产"。

系统没有游客态。`App.tsx:184-196` 的 `Guard` 组件把未登录用户重定向到 `/login`，仅 `/`、`/login`、`/about`、`/knowledge` 四个路径开放。也就是说，OUTLINE 中"保留游客"是目标设计，现状并不存在免登录训练入口。

### 1.4.2 选角色与难度

角色选择页列出 12 位服务对象，卡片展示姓名、年龄、原型、难度星级（1-5）与主诉（`src/pages/CaseSelectPage.tsx:35-42`、`:109-115`）。难度初值优先取 `sessionStorage` 的 `knock.diff`，取不到时改用本地设置中的默认难度（`:26`）；确认后调用 `startSession(id, diff)` 建立会话并写回默认难度（`:56-60`）。

### 1.4.3 三阶段训练与五阶段内容

内容层阶段为建立关系、问题探索、评估、介入、结束五段（`src/types.ts:76-84`），UI 层合并为三段，映射规则写在 `src/hooks/useSession.ts:62-66`：第一阶段前两轮为建立关系，其余为问题探索；第二阶段前两轮为评估，其余为介入；第三阶段固定为结束。映射结果决定当前台词节点区间与评分中的过程分。

会话状态包含情绪值、轮次、阶段、评判计数、无望感标记、分数偏移、危机阻断标记与阶段起点（`src/hooks/useSession.ts:68-89`）。其中情绪值初始 30-50，服务对象每轮回应后按意图效果加减；危机阻断标记一旦置位，本轮不计分、不调模型。

### 1.4.4 每轮面谈的六个步骤

学生每次发送一句话，`send()`（`src/hooks/useSession.ts:216-473`）依次执行六个步骤：

1. 本地规则判定。`matchLocalRules` 先跑 8 步判定（危机、评判、建议过早、离题、沉默陪伴、共情、开放式提问、封闭式提问），返回意图、风险级别、六维分值增量与是否需要 AI 补判（`src/services/rules.ts:328-472`）。危机词表单独做过语境边界，"你可以打我电话""拿刀切菜"不会被误判为危机。
2. AI 意图补判。当本地规则未覆盖、参与度为混合或全 AI、且风险级别不是自杀级时，调用 `/api/ai/intent` 做长尾分类；AI 判定成功后用 `effectsForIntent` 换取与规则层同口径的分值增量（`:261-298`）。
3. 危机闸门。若判定为自杀级，立即置 `crisisBlocked`、暂停本轮计分与模型调用，并渲染危机处置卡（`:300-331`）。
4. 状态累加。把六维增量、情绪变化、评判计数、无望感标记、轮次写入会话（`:333-342`）。
5. 台词生成。先由对话引擎按阶段、话题、情绪三要素取预置台词；全 AI 模式下再调 `/api/ai/persona` 生成，返回结果必须通过 `isScriptLine` 白名单校验，否则回落预置台词（`:346-392`）。
6. 标记与备注。计算矛盾点、边注与高亮区间，供复盘页展示（`:394-419`）。

台词生成的具体算法在 `dialogueEngine.ts` 中。情绪值按 0-100 分为三档：不高于 29 取回避型台词，30-69 取平实型，不低于 70 取打开型（`selectVariant`）。话题匹配由 `TOPIC_TABLE` 与 `matchTopic` 完成，把学生原话映射到某个节点 id；匹配不到时按阶段决定是否推进到下一节点（`matchTopic`、`shouldAdvance`）。若上一轮被判定为评判，则本轮返回防御台词并保持节点不推进，学生必须先把关系修复回来才能继续。全 AI 模式下，模型生成的台词还要经过 `isScriptLine` 白名单比对——只有与台词库中某一句完全一致，或属于允许的标点变体，才会被采用，否则静默回落预置台词。这条约束保证了"AI 永远不会说出剧本外的话"，是危机内容无法从角色扮演链路漏出的关键。

### 1.4.5 阶段评分与结算

每个阶段结束时提交。`TrainingPage.tsx:148-277` 的 `onSubmit` 先调用 `collectUtterances` 收集本阶段学生发言（`:109-112`），用 `computeRuleScore` 算规则六维（`:114-126`），再调 `/api/ai/score` 取 AI 六维，用 `mergeScores` 按 0.4/0.6 融合（`:191`），`weightedTotal` 加权成百分制（`:192`）。随后生成复盘文本、写入本地记录与复盘缓存、推进阶段，若设置开启自动结算则跳转结算页（`:196-271`）。

评分细节写死在 `scoring.ts`。六维初值取 60，伦理取 70；每一轮按意图增量累加，其中共情加同感 8、开放提问加提问 8、评判扣伦理 8、建议过早扣建议 8、危机轮直接跳过计分。三处封顶规则用于约束"看起来不错但没做到"的情况：出现过评判则伦理封顶 60；空泛共情累计两句及以上则同感封顶 50；出现无望感线索而学生未识别则风险封顶 55，识别成功则风险加 10。过程分不按轮次计算，而是已完成阶段数除以总阶段数再乘 100。所有维度最终统一收敛到 0-100，再按 25/20/15/20/10/10 的权重加权成百分制。

融合阶段的关键约定是"AI 缺一即废"：AI 六维中只要有一维缺失或非法，整条 AI 结果作废，规则分以 1.0 权重计入（`src/services/scoring.ts:333-336`）。这是"AI 失败不影响出分"的实现方式，也意味着一次 AI 评分失败会让最终成绩与另一名学生相比少了一半语义信息，而系统没有任何提示。

结算页从会话的 `lastResult` 或当前账号最近一条记录取分展示总分与六维（`src/pages/SettlePage.tsx:39-51`）。复盘页从 `knock.debriefs` 读取最近一份复盘，展示"做得好/需要改进/下一步练什么"三段，并标注来源是模型生成还是规则模板（`src/pages/ReviewPage.tsx:77-125`）。

## 1.5 AI 调用链路

四条链路共用同一套基础设施：客户端 `aiClient.ts` 负责超时、探活与降级记录；服务端 `index.mjs` 负责限流与参数截断；`prompts.mjs` 负责提示词构造与输出解析；`glm.mjs` 负责模型链、缓存与用量统计。共同约定是"解析失败不抢救、服务端不重试业务、每条链路独立降级、危机内容不进模型层"（`server/prompts.mjs:1-8`）。四条链路的输入输出见表 1-4。

**表 1-4 四条 AI 链路的输入、提示词与降级**

| 链路 | 端点 | 客户端传入 | 服务端提示词结构 | 失败时前端表现 |
|---|---|---|---|---|
| 意图分类 | `/api/ai/intent` | 学生原话（截 600 字）、阶段、服务对象、主诉、本地初判 | system 限定"观察员只输出 JSON"；user 给八类定义与上下文；`json_object`，60 token，温度 0 | 返回 `usedAI:false`、`intent:null`，沿用规则判定 |
| 角色扮演 | `/api/ai/persona` | 整段 `systemPrompt`（截 4,000 字）、难度、情绪、阶段、禁区、最近 20 条历史、已说 6 句 | system 首行即客户端上传的 `systemPrompt`，其后拼接难度/情绪/阶段/禁区与 11 条说话规则；180 token，温度 0.8 | 静默回落预置台词，并过白名单校验 |
| 六维评分 | `/api/ai/score` | 本阶段对话（截 8,000 字）、六维事实（发言数、评判数、无望感识别等） | 六维评分标准 + 纪律（空泛共情≤50、评判伦理≤60、无望感未识别风险≤60、35-95 区间、基线 60）+ 记录；`json_object`，900 token，温度 0.2 | 整条作废，仅用规则分（权重回到 1.0 规则） |
| 复盘报告 | `/api/ai/debrief` | 昵称、服务对象、六维分、命中规则（≤12 条） | 三段各 60-120 字、禁用词表、给六维与命中规则；700 token，温度 0.4 | 回落规则模板，页面标注"规则模板" |

意图链路的解析最严格：`parseIntent` 只接受八个枚举值，JSON 解析失败后还会在原文中做一次裸匹配，仍失败即返回 null（`server/prompts.mjs:99-108`）。角色扮演链路的风险面最大：服务端把客户端上传的 `systemPrompt` 直接作为 system 消息首行（`server/prompts.mjs:115`），只校验长度不小于 10（`server/index.mjs:138-139`）；输出侧虽做过十词黑名单、长度 2-200、禁用词命中即作废（`server/prompts.mjs:159-176`），但提示词内容的合法性完全由客户端决定。评分链路的输出解析要求六个维度全部齐全，缺一即整条作废（`server/prompts.mjs:232-255`），这条约束在前端融合时被再次执行（`src/services/scoring.ts:333-336`）。

意图链路只在规则未覆盖时触发。规则层对八类意图中的多数有明确词表与句式判据，唯一不设词表的是自由表达，因此 `matchLocalRules` 在未命中时返回占位意图 `共情` 与 `shouldCallAI:true`（`src/services/rules.ts:459-471`）。AI 返回合法枚举后，前端用 `effectsForIntent` 取与规则层完全相同的分值表，保证"谁判定的不影响算分口径"；若 AI 返回 null，占位意图保留，分值仍按本地规则计。

角色扮演链路的提示词由三段拼成：客户端上传的人设说明、服务端追加的难度与情绪约束、以及 11 条说话规则（记住每一件事、不主动推进剧情、不用括号描述动作、不说脏话等，`server/prompts.mjs:122-136`）。历史只保留最近 20 条，已说台词只保留最近 6 句，用于避免重复。输出侧另有一道质量下限：当情绪不低时，长度不超过 2 字的短句会被判为无效（`server/index.mjs:167-171`），防止模型用"嗯""哦"敷衍。

评分链路的提示词包含六维定义、锚点与引用标准（公告第 426 号），并要求理由不超过 30 字且引用学生原话。服务端解析时强制六维齐全、越界丢弃、理由截断 60 字（`server/prompts.mjs:232-255`）。前端再做一次收敛：把分数柔性压到 35-95 区间，避免 AI 给出 0 分或 100 分造成失真（`src/lib/aiClient.ts:364`）。复盘链路则要求三段各 60-120 字，禁止"赋能、闭环、底层逻辑、抓手"等六类空话（`server/prompts.mjs:288`），解析不合格回落模板。

失败处理可以归纳为一张隐式矩阵：无密钥返回 503 且 `usedAI:false`；日上限返回 429 `DAILY_CAP`；单 IP 超频返回 429 `RPM`；模型 45 秒未返回返回 504 `TIMEOUT`；上游 5xx 或网络异常返回 502；响应缺 `choices` 或内容为空返回 502；解析不合格则由 `parse*` 返回 null，路由层仍以 200 返回 `{ok:true, usedAI:false}`。前端对这七种情况的处理完全一致：记一条 `failReason`、继续用规则层结果、页面不报错。这种"永不失败"的体验是产品优点，但也意味着故障在用户侧不可见、在运维侧无痕迹。

模型侧的降级顺序统一为"主模型 2 次机会 → 两个降级模型各 1 次"，只有 429 与 5xx 可重试，重试间隔 700 毫秒，最终失败抛出最后一次错误（`server/glm.mjs:209-253`）。错误码映射为：无密钥 503、日上限 429、超时 504、上游网络错误 502、响应结构异常 502、内容为空 502（`server/glm.mjs:181-187`、`:296-304`）。客户端对失败只记录 `lastError` 并在 5 秒后重新探活，不做页面级降级（`src/lib/aiClient.ts:100-120`）。

耗时与成本量级见表 1-5，数据取自 FACTS G 区声明值。需要说明的是，本次核验环境中抽取目录没有 node_modules，也没有可用的模型密钥，因此这些数字无法复测，只能作为量级参考；第 8 章压测时需要重新测量。

**表 1-5 耗时与成本量级（声明值）**

| 项 | 量级 | 说明 |
|---|---|---|
| 一次完整训练模型调用 | 3-6 次 | 每次阶段提交 1 次评分 + 1 次复盘，意图与台词按需 |
| 单次调用 token | 100-600 | 输入含上下文，输出受 max_tokens 限制 |
| 免费档单次延迟 | 2-16 s | 网络与排队波动 |

## 1.6 存储现状

存储现状可以用"一个权威、一个孤岛"概括：localStorage 是事实上的权威存储，Supabase 是可选的孤岛。

前端共有 8 个活跃的 localStorage 键，另有 3 个只出现在清理列表中的死键，见表 1-6。`knock.records` 是单一键存放全部账号的训练记录，切换账号只做昵称过滤而不做物理隔离；`knock.session.<account>` 按账号分槽，写入以 800 毫秒节流（`src/store/store.tsx:146-156`）。

**表 1-6 localStorage 键清单**

| 键 | 内容 | 写入点 | 读取点 |
|---|---|---|---|
| `knock.accounts` | 全部本地账号与口令哈希 | `src/store/store.tsx:141` | `store.tsx` 登录/切换 |
| `knock.currentAccount` | 当前账号 | `src/store/store.tsx:98` | `store.tsx`、`db.ts:358-365` |

| `knock.settings` | 默认难度、AI 参与度、自定义剧本等 | `src/lib/db.ts:347-356` | `useSession.ts:34-51`、编辑页 |

| `knock.draft`、`knock.sessions`、`knock.heat` | 仅出现在清理列表，无写入点 | `src/lib/db.ts:419-420` | 无 |

云端部分由两份迁移脚本构成，最终形态为 7 张表、5 个视图、9 个索引、2 个触发器，见表 1-7。

**表 1-7 云端表与视图**

| 对象 | 名称 | 用途 |
|---|---|---|
| 表 | `case_scripts` | 角色剧本元数据与系统提示词 |
| 表 | `training_records` | 每次阶段提交一条，含六维分、总分、来源 |
| 表 | `training_details` | 逐句明细与标记 |
| 表 | `proficiency` | 按日的能力快照，受触发器维护 |
| 表 | `achievement` | 成就定义 |
| 表 | `session_record` | 未完成会话的草稿 |
| 表 | `user_settings` | 用户偏好（缺 `ai_mode` 列） |
| 视图 | `v_user_stats`、`v_training_heatmap`、`v_heatmap`、`v_script_progress`、`v_dimension_avg` | 统计、热力图、剧本进度、维度均值 |

问题在于这一层的权威性被彻底放弃。7 张表中有 6 张启用了 RLS，但策略一律是 `for all using (true) with check (true)`（`supabase/migrations/001_schema.sql:178-199`、`002_schema_supplements.sql:177-180`），`case_scripts` 甚至没有启用 RLS。匿名 key 会随前端构建产物一起分发，任何拿到站点的人都能提取该 key，进而读写全部训练记录、篡改角色剧本。迁移脚本注释本身也承认"昵称即身份，不做登录，正式上线应改 auth.uid()"。

RLS 全放行的后果可以具体化。攻击者只需在浏览器控制台从打包产物中取出匿名 key，即可用 PostgREST 直接对 7 张表发起增删改查：读取全部学生的六维分与逐句对话（其中包含家暴、自杀倾向等敏感内容）、把自己的历史成绩改成 100 分、批量删除他人记录、修改 `case_scripts` 中的系统提示词从而改变所有后续会话的服务对象人格。由于 `case_scripts` 连 RLS 都未启用，改提示词这条路径不需要任何特殊条件。这一风险不是理论推演——匿名 key 是前端构建产物的公开内容，迁移脚本的 `using (true)` 使过滤条件形同虚设。

更关键的是，云端数据在运行时只写不读。全仓检索显示，`db.ts` 的读取函数（`fetchStats`、`fetchHeatmap`、`fetchProficiency`、`fetchHistory`、`fetchDimensionAvg`、`fetchScriptProgress`、`fetchHeatmapRows`、`fetchDetails`、`loadDraft`、`loadSettings`）没有被任何页面引用；真正被引用的只有 `saveTraining`、`loadSettingsLocal`、`saveSettingsLocal`、`exportCsv`、`purgeLocal` 与 `dbReady`。也就是说，7 张表与 5 个视图在运行时是"只写不读"的孤岛，用户界面完全依赖 localStorage。

此外还存在一处结构性漂移：`user_settings` 表没有 `ai_mode` 列，而前端 `UserSettings` 类型与默认设置包含该字段，`saveSettingsLocal` 会把它一起 upsert（`src/lib/db.ts:326-334`、`:350-354`），`loadSettings` 又会读取 `data.ai_mode`（`:379`）。配置一旦启用云端同步，该写入必然失败，且错误被 `void` 丢弃，用户无感知。

localStorage 作为权威存储还有三个工程后果。其一是容量，浏览器对单一源约 5 MB 配额，一条训练记录约 1-2 KB，长期使用会先遇到 `QuotaExceededError`；复盘缓存在写入失败时选择静默丢弃，用户会看到复盘消失而没有任何提示。其二是并发，同一浏览器多标签页各自持有内存副本，800 毫秒节流落盘会让后写者覆盖先写者，训练记录可能凭空丢失。其三是迁移，数据只存在单台设备的单个浏览器配置里，清除站点数据、换浏览器、换设备都等于清零，教师也无法在另一台机器上查看学生记录。

`start.bat` 与 `start.sh` 是四步流程：检查 Node 版本不低于 18.17；若缺 node_modules 则执行安装；若缺 `.env.local` 则从 `.env.example` 复制；执行构建后以前台进程启动 `node server/index.mjs`，打印本机与局域网地址并尝试打开浏览器。两个脚本合计约 3,900 字节，没有服务守护、没有进程管理、没有失败重试。

运行形态上存在四项缺失。其一，无容器化与编排，交付物中没有 Dockerfile、Compose 文件或 Kubernetes 清单。其二，无 CI/CD，仓库没有 `.github/workflows` 等流水线定义，构建与校验全靠开发者手工执行。其三，无环境隔离，只有一套 `.env.local`，`VITE_*` 变量在构建期被固化进产物，无法在不重新构建的情况下区分开发、测试与生产。其四，无制品管理与回滚，`dist/` 由本地构建产生，没有版本号、校验和与历史版本，出问题只能重新构建。

配置面同样单薄。前端只有两个构建期变量（`VITE_SUPABASE_URL`、`VITE_SUPABASE_ANON_KEY`）和一个可在设置页改写的运行期变量（`VITE_AI_BASE`，改后存入 localStorage）；后端只有模型密钥、端口与可选的自定义接口地址。`.env.example` 是唯一的环境模板，`.env.local` 被 `.gitignore` 忽略，但没有密钥管理、没有分级配置、没有配置校验。由于 Vite 的 `VITE_*` 变量在构建时被字面替换，同一份 `dist/` 无法在不同环境间迁移，测试环境与生产环境必须分别构建；这也使"构建一次、多处部署"的标准做法无法实施。

## 1.8 质量保障

质量保障由 7 个 Python 自检脚本与 1 个 TypeScript 引擎自检组成，见表 1-9。

**表 1-9 自检脚本清单**

| 脚本 | 行数 | 检查内容 |
|---|---|---|
| `tools/validate.py` | 204 | 17 个源文件的乱码与括号配平、跨模块导入一致性、关键统计与 15 条不变量，实跑结果为 PASS（词表 165、节点 118、台词 354、卡 19、伦理 12、阻抗 6、权重 100） |
| `tools/check_paths.py` | 133 | 相对导入文件是否存在、CSS 变量是否已定义、className 是否有对应规则，仅警告不阻断 |
| `tools/check_pdf_vs_src.py` | 129 | 文档 PDF 中的数字是否与源码对象字面量一致 |
| `tools/check_consistency.py` | 125 | PDF、200 字简介、提交物清单、线上实测四方口径对齐，共 15 个检查项 |
| `tools/check_sql_columns.py` | 63 | 002 迁移引用的列是否都在 001 的表中 |
| `tools/count_intro.py` | 54 | 200 字简介的字数与要素完整性 |
| `tools/shrink_shots.py` | 45 | 截图转 JPEG 以压缩文档体积，非代码检查 |

`src/smoke_test.ts` 是唯一的业务逻辑测试：55 个 `t()` 调用点，其中 3 个位于循环体内并展开为 17 项（八类意图 9 项、话题表 5 项、情绪变体 3 项），实际执行 69 项断言，分为 13 组。另有 `dialogueEngine.ts:540-568` 的 `selfCheck()` 对 12 个剧本各 18 条探针、3 种情绪共 648 次白名单校验，聚合成 12 条结果。

13 组的划分是：数据完整性、敬称归一化、离题优先于提问、三级风险分级、八类意图判定、规则未覆盖需调 AI、话题表命中、台词必须来自台词库、情绪值决定台词变体、评判触发防御台词且节点不推进、六维评分链路、回归断言、12 个剧本台词自检。这些断言全部是进程内的纯函数调用，不启动 HTTP 服务、不访问模型、不写数据库，因此无法覆盖代理层的路由、限流、超时、降级与错误映射——后端恰是最需要测试的部分。

覆盖面之外的问题同样明确。后端 1,046 行代码没有任何测试，`server/` 下不存在测试文件；前端没有 ESLint、Prettier 配置，也没有覆盖率统计；类型检查只挂在 `npm run build` 与手工 `typecheck` 上，`tsconfig.json` 还把 `noUnusedLocals` 与 `noUnusedParameters` 关闭，死变量与死参数不会报错。`tools` 下的脚本以文档与交付物校验为主，只有 `validate.py`、`check_paths.py`、`check_sql_columns.py` 真正触及代码结构，且全部是文本级检查而非执行级测试。

值得注意的是，校验脚本自身的口径已经出现错值：`tools/check_consistency.py:27-31` 的真值表把规则条数写成 165、阻抗形态写成 10、视图写成 4，而源码实测分别为 165（九表）、6、5：规则条数一项校验脚本反而是对的，此前把"162"当作实测值是误判。这说明校验工具本身缺乏测试，口径未经交叉核对，无法作为质量门禁的可信基础。

## 1.9 本章小结

综合以上事实，可以明确判定：本项目是演示级、课程作品级工程，具备完整的专业模型与交互流程，但不具备生产系统所需的可信边界、安全边界、数据持久化与运维能力。差距可以量化为五点。

- 可信边界缺失：1,856 行规则与评分逻辑（rules 568 行、scoring 522 行等）全部运行在浏览器，成绩由前端计算后直接落盘，服务端没有任何复算与校验入口，改一个数字即可篡改成绩。
- 安全边界缺失：后端仅 1,046 行、零第三方依赖，没有身份认证、没有 RBAC、没有审计；7 张表中 6 张以 `using (true)` 全放行，`case_scripts` 未启用 RLS；Edge Function 无鉴权、无配额，CORS 为 `*`。
- 持久化缺失：8 个 localStorage 键是事实权威存储，容量 5 MB 量级、换设备即丢、多标签页互相覆盖；云端 7 表 5 视图只写不读，`user_settings` 还缺 `ai_mode` 列导致配置同步必失败；`durationSec` 恒为 0。
- AI 工程质量缺失：4 条链路在服务端没有任何结构化输出校验与版本管理，提示词内容由客户端决定（`systemPrompt` 整段上传），模型链、超时、日上限全部硬编码，无评测集、无成本预算维度。
- 运维与交付工程缺失：日志只有 `console`，无指标、无追踪、无告警、无备份；无容器、无 CI/CD、无环境隔离、无制品与回滚；后端 1,046 行零测试，类型检查未设门禁。

这五点差距对应第 2 章的六组共 26 项问题，其中 10 项为 P0。第 2 章将逐项给出代码位置、可量化后果与整改章节指向，第 3 章起给出目标架构与实施路径。
