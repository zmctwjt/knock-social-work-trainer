# 第5章 Python 后端详细设计

本章给出生产级后端的落地设计。设计以第 3 章的 ADR-01、ADR-02、ADR-05、ADR-06、ADR-07 为前提，把原先散落在浏览器与 Node 单进程中的业务规则、评分融合、危机拦截与 AI 调用收敛到 Python 服务端，并保证旧前端在不改动调用代码的情况下继续可用。全章按分层、请求链路、配置、认证授权、接口契约、AI 网关、领域下沉、兼容灰度、可观测性与性能预算的顺序展开。

## 5.1 设计目标与分层

### 5.1.1 设计目标

后端承担四项不可下放的职责：业务规则的唯一权威、危机内容的硬拦截、AI 调用的统一出入口、训练数据的持久化与统计。围绕这四项职责形成五条设计目标。

- 规则可复算：同一段对话在任何实例、任何时刻评分结果一致，评分不依赖浏览器状态。
- 拦截不可绕过：危机级内容在服务端判定，判定为危机时模型调用次数为零。
- 降级不阻断：AI 超时、限流、返回非结构化内容时，接口仍返回可用结果，页面不出现空白或异常。
- 契约可演进：新接口统一 `/api/v1`，旧接口 `/api/ai/*` 保留并标注弃用，前端迁移可分链路灰度。
- 运行可观测：每次请求有 request_id，每次 AI 调用有模型、耗时、降级原因与审计记录。

应用进程保持无状态，会话、配额、缓存等跨请求状态放在 PostgreSQL 与 Redis；单实例故障不影响训练进行，扩容通过增加实例完成。

本设计明确三项非目标：不做服务端渲染，页面仍由前端构建产物提供；不在本期引入多租户与组织层级，角色只有四类（访客、学生、教师、管理员）；不实现实时消息推送，训练过程以请求响应方式推进。非目标写入设计文档的目的是约束范围，避免在基础设施尚未稳定时引入额外复杂度。二期可在此基础上增加班级与作业能力，数据模型已为教师角色与记录归属预留字段。

### 5.1.2 分层结构与依赖方向

代码按接口层、服务层、领域层、基础设施层划分，另设核心横切层与提示词层。依赖方向严格单向，下层不反向依赖上层。

**表 5-1 后端分层职责**

| 层次 | 目录 | 职责 | 允许依赖 |
|---|---|---|---|
| 接口层 | `app/api/` | 路由、鉴权依赖、参数校验、响应封装 | 服务层、领域 schema |
| 服务层 | `app/services/` | 用例编排、事务边界、AI 网关、账号与会话逻辑 | 领域层、基础设施层、提示词层 |

| 基础设施层 | `app/infra/` | 数据库会话、Redis 键值存储、缓存实现 | 核心配置 |

## 5.2 请求生命周期与中间件链

### 5.2.1 生命周期

一次请求依次经过接入、横切、路由、业务、持久化与回写六个阶段，如图 5-1 所示。

![图 5-1 请求处理链路与 AI 网关内部流程](figures/fig-06-request-chain.png)

1. ASGI 服务器接收连接，完成 TLS 卸载后的 HTTP 解析（生产由 Nginx 承担 TLS）。
2. `CORSMiddleware` 处理跨域预检与响应头，允许来源取自配置的 `CORS_ORIGINS`。
3. `TrustedHostMiddleware` 校验 Host 头，生产环境配置具体域名，开发环境允许通配。
4. `RequestContextMiddleware` 读取或生成 `X-Request-ID`，写入上下文变量，绑定日志字段，记录起始时间。
5. `BodyLimitMiddleware` 检查 `Content-Length`，超过 512 KB 直接返回 413，不进入路由。
6. 路由匹配后执行依赖：Bearer 解析、令牌验签、撤销表查询、账号加载、角色判定。
7. AI 链路额外执行单 IP 固定窗口限流，键含身份与时间窗，超限返回 429 并带 `Retry-After`。
8. 请求体经 Pydantic 模型校验，校验失败由异常处理器转为 40001。
9. 服务层组织事务，调用领域函数或 AI 网关，必要时写审计表。
10. 响应统一封装为 `{code,message,data,request_id}`，中间件记录耗时、状态码与路由模板后返回。

应用启动时由 lifespan 初始化日志、追踪、数据库引擎、键值存储、AI 缓存、配额、用量统计、供应商、模型路由、审计记录器、AI 网关与限流器，挂载到 `app.state`；关停时依次关闭 httpx 客户端、Redis 连接与数据库引擎，避免连接泄漏。

初始化的顺序按依赖关系排列：配置与日志最先，其后是数据库与键值存储，再次是缓存、配额与用量统计，最后才构造供应商与网关。关停顺序与之相反，先停止接收流量，再释放外部连接，保证在途请求有机会完成。任何可选组件初始化失败只降级不退出，例如 Redis 不可用时退回进程内实现，模型密钥缺失时进入规则模式。

### 5.2.2 中间件职责与失败行为

**表 5-2 横切组件**

| 组件 | 触发时机 | 职责 | 失败行为 |
|---|---|---|---|
| CORS | 所有请求 | 回显允许来源、暴露 request_id 头 | 不允许的来源不返回跨域头 |
| TrustedHost | 所有请求 | 拒绝伪造 Host | 400 |
| RequestContext | 所有请求 | 生成 request_id、计时、访问日志、指标 | 内部异常不影响主流程 |
| BodyLimit | 请求进入路由前 | 限制请求体 512 KB | 413 与 40001 |
| 限流依赖 | AI 与认证路由 | 固定窗口计数，20 次每分每 IP | 429 与 42901，带重试秒数 |
| 异常处理器 | 抛出未捕获异常时 | AppError、校验错误、HTTP 异常、未知异常分流 | 统一错误体，不泄漏堆栈 |

中间件注册顺序与执行顺序相反，最后注册的跨域中间件位于最外层，保证错误响应同样带跨域头；体积限制位于上下文之后，使 413 响应也能携带 request_id 与耗时指标。异常处理器对 `AppError` 输出其携带的业务码与 HTTP 状态；对 `RequestValidationError` 输出 40001 并给出字段级提示；对 Starlette 的 HTTP 异常按状态码映射为 40401 或 40901；对未知异常输出 50001，日志保留堆栈但不进入响应。

### 5.2.3 统一响应包与错误码

成功响应固定四字段，`code` 为 0；失败响应的 `data` 为 `null`，`request_id` 可用于在日志与审计表中定位同一次请求。

```json
{"code": 0, "message": "ok", "data": {"items": [], "total": 0}, "request_id": "8f1c0a9b2d4e4a0e9b7c6a5d4e3f2a10"}
```

**表 5-3 错误码表**

| 业务码 | HTTP | 语义 | 典型触发 |
|---|---|---|---|
| 0 | 200/201 | 成功 | 正常返回 |
| 40001 | 400/413 | 参数或请求体不合法 | 字段缺失、超长、JSON 损坏 |
| 40101 | 401 | 未认证或令牌失效 | 无令牌、过期、签名错误、已撤销 |
| 40301 | 403 | 越权或角色不足 | 访客写操作、访问他人会话、非管理员删除 |
| 40401 | 404 | 资源不存在 | 会话、案例、知识卡 ID 不存在 |
| 40901 | 409 | 状态冲突 | 已结束会话继续发言、重复结束 |
| 42901 | 429 | 请求频率超限 | 单 IP 每分钟超过 20 次 |
| 42902 | 429 | AI 日配额耗尽 | 当日调用达到 800 次 |
| 50301 | 503 | AI 能力不可用 | 未配置密钥且无规则兜底的链路 |
| 50001 | 500 | 未预期内部错误 | 未捕获异常 |

## 5.3 配置管理

### 5.3.1 配置模型

配置使用 pydantic-settings 的扁平模型，环境变量为大写蛇形且不区分大小写，不设前缀，键名与 `env.example`、`docker-compose.yml`、附录 B 完全一致。模型在进程内以 `lru_cache` 单例提供；测试通过 `Settings(_env_file=None, **overrides)` 注入独立实例，避免环境变量串扰。所有密钥类字段不设可用默认值：密钥缺失时进入降级路径，而不是启动失败。

派生属性集中处理字符串到结构的分裂：模型链由主模型与降级模型拼接并去重，CORS 与 Host 白名单拆分为列表，数据库类型由 URL 前缀判断，令牌有效期由分钟与天数换算为秒。`safe_summary()` 输出可公开的配置摘要，供健康检查与排障使用，不含任何密钥明文。

### 5.3.3 密钥缺失的降级

未配置 `GLM_API_KEY` 时，`ai_configured` 为假，网关在入口处短路，四类 AI 请求全部返回结构完整的规则结果：意图由本地词表判定，角色台词回落到按情绪档位准备的固定话术，评分使用纯规则分，复盘使用弱点建议模板。此时 `used_ai` 为假、`degrade_reason` 为 `no_key`，接口状态码仍为 200。生产环境使用开发默认 JWT 密钥时启动日志输出告警，避免误上线。

配置在启动时完成类型校验，端口、池大小、超时等数值越界会直接拒绝启动，避免带病运行；字符串类密钥不做长度校验，只在使用处判断是否为空。生产环境启动日志打印 `safe_summary()`，便于核对实际生效的模型链与超时值。

## 5.4 认证、授权与 RBAC

### 5.4.1 令牌设计

认证采用 JWT 双令牌。访问令牌有效期 30 分钟，刷新令牌 7 天，访客令牌 24 小时；算法 HS256，载荷包含主体标识、角色、令牌类型、唯一编号、签发方与签发时间。密码使用 Argon2id 哈希，参数由环境变量控制，生产取时间成本 3、内存 65536 KB、并行度 4。

刷新采用轮换策略：每次刷新先校验刷新令牌类型与唯一编号未被撤销，随后把旧刷新令牌写入撤销表，再签发新的令牌对。注销时把当前访问令牌写入撤销表，使其在剩余有效期内立即失效。撤销表按过期时间建索引，过期记录由清理任务删除。令牌解码强制校验类型，刷新令牌不能当作访问令牌使用，避免权限提升。

令牌由前端保存在内存与安全存储中，不写入 URL；所有认证接口强制 HTTPS，生产在 Nginx 层重定向。刷新令牌只用于刷新端点，前端不得用它调用业务接口。服务端不维护会话表，登录态完全由签名令牌与撤销表推导，因此水平扩展无需粘性会话。

访客是本期新增能力。原系统在应用入口强制登录，训练数据直接写在浏览器本地；新增访客态用于开放体验与招生演示，仅授予只读权限，写操作统一返回 40301。

**生产环境启动校验。** 默认密钥、`DEBUG`、通配 `ALLOWED_HOSTS`/`CORS_ORIGINS`、SQLite、缺 Redis、关闭限流、自动建表这八项在开发期都方便，但只要漏到生产就是可直接利用的漏洞。因此 `Settings.production_errors` 在 `app_env=prod` 时逐项检查，任一命中即抛 `StartupConfigError` 让进程拒绝启动——不做降级、不写警告了事。配套 14 项测试覆盖每一条阻断项与合规放行路径。

**安全响应头。** 全局下发 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`、`Permissions-Policy`（关闭摄像头/麦克风/定位）、`Cross-Origin-Resource-Policy`/`Cross-Origin-Opener-Policy: same-origin`。`Strict-Transport-Security` 只在 `prod` 下发：开发期是 HTTP，加 HSTS 会让浏览器把 localhost 记住成 HTTPS，反而破坏本地调试。CORS 与凭证的关系也做了约束——来源配置为 `*` 时自动关闭 `allow_credentials`，避免"任意站点可携带 Cookie 调用"这一经典反模式。

**CSP 必须按响应类型区分。** 接口不渲染页面，`default-src 'none'` 是最严也最合适的策略；但单端口部署时后端**同时托管前端 HTML**，若把同一套策略套在页面上，页面自己的 `<script src="/assets/*.js">` 与样式表会被浏览器直接拦掉，表现为白屏加一串 CSP 报错——这是实现期真实踩到的回归。因此 `pick_csp()` 按响应类型分流：`text/html` 用 `CSP_WEB`（`default-src 'self'`，放行同源脚本样式与同源接口请求，仍禁止外域脚本与内联事件），接口用 `CSP_API`（`default-src 'none'`），`/assets/*` 静态子资源不下发 CSP。配套 4 项测试锁定该行为，其中一项用真实 dist 目录验证 HTML 与接口各自拿到正确策略。

教师端与本表同批落地，不再是二期：教师通过 `accounts.teacher_id` 与学员建立归属，只能看到名下学员的汇总与记录；跨班查询返回空集而非 40401，避免泄露资源存在性。管理员继承教师权限并额外获得账号、内容与系统管理能力，用于教务导入与内容运营。班级实体、点评与作业分发仍属二期，届时把自引用归属替换为独立班级表。

### 5.4.3 越权防护

原 Supabase 方案的权限依赖行级安全策略，但 6 张启用表全部使用 `using (true) with check (true)`，等价于不做隔离；案例表甚至未启用行级安全。新方案改为应用层强制过滤：会话与记录表都带 `owner_id`，所有按 ID 读取的入口先按主键查询，再比较归属。

判定顺序影响信息暴露：资源不存在返回 40401，资源存在但归属他人返回 40301，两者不合并，便于前端区分「链接失效」与「无权访问」。删除接口只授予管理员，同样经过归属比较。写接口额外要求非访客身份，由依赖 `require_human` 统一拒绝访客。

授权失败同时写入访问日志与指标，按账号与来源地址聚合，便于识别批量探测。同一账号在短时间内多次越权访问时，运维侧可临时禁用账号，禁用状态在登录与令牌校验两处同时生效。

### 5.5.2 幂等与状态约束

训练会话支持客户端生成标识，`(owner_id, client_session_id)` 唯一，重复创建返回同一会话。发言支持 `client_turn_id` 去重，同一标识二次提交返回首次结果，避免网络重试产生重复台词。分段评分按 `(session_id, stage_index)` 唯一，重复评分覆盖为最新一次并保持同分性。结束训练与生成复盘均为幂等操作：已结束会话再次结束返回既有记录，复盘已存在时直接返回，不重复调用模型。

状态机约束为线性推进：进行中的会话可发言、可评分；结束后的会话只读，发言返回 40901；危机轮触发暂停，暂停期间不生成角色回应，等待人工介入或结束训练。

列表接口统一支持页码与页大小，页大小上限 100，返回总数供前端计算分页器；会话详情不分页，轮次按序返回，单会话轮次上限由 `max_turns` 约束，默认 40 轮。版本演进遵循只加字段不改语义的原则：新增字段必须有默认值，删除字段先标记弃用并至少保留一个迭代周期；破坏性变更通过新增版本前缀实现，旧前缀继续服务直至调用方迁移完成。

## 5.6 AI 网关设计

### 5.6.1 网关组成

AI 网关是模型调用的唯一出入口，由九个部件组成，各部分职责单一、可替换。

- 供应商协议 `LLMProvider`：定义 `name`、`complete`、`close` 三个成员，新增供应商只需实现该协议。
- 智谱实现 `ZhipuProvider`：基于 httpx 异步客户端调用 OpenAI 兼容端点，请求体固定携带 `thinking` 关闭字段。
- 模型路由 `ModelRouter`：按模型链顺序尝试，负责重试、退避、熔断查询与失败归类。
- 缓存 `AICache`：进程内 LRU 为一级，Redis 为二级，两级共用同一键格式。
- 配额 `DailyQuota`：按东八区日期计数，跨进程以 Redis 增量保证准确。
- 并发闸门：进程级信号量，默认 2，限制同时进行的模型调用数。
- 输出解析器：四条链路各自把模型文本解析为枚举、字符串或结构化对象。
- 审计记录器：写 `ai_audit_log`，只保存输入摘要与长度，不保存对话原文。
- 用量统计：累计调用、成功、失败、降级、缓存命中与令牌数，供旧接口 `/api/usage` 使用。

调用顺序为固定流水线：密钥检查、缓存查询、配额扣减、并发等待、熔断检查、供应商调用、状态归类、内容解析、缓存写回、审计落库。任一环节失败都不会把异常抛给页面，唯一例外是配额耗尽，它需要以 42902 明确告知调用方今日额度已用完。

### 5.6.2 模型链与重试

模型链由主模型 `glm-4.7-flash` 与两个降级模型 `glm-4.5-flash`、`glm-4-flash` 组成，顺序固定，配置重复时自动去重。主模型允许两次尝试，第一次与第二次之间按指数退避加抖动等待，基准 0.7 秒；每个降级模型只允许一次尝试。该策略继承自旧实现，保留原因是主模型偶发限流与网关抖动占失败的大多数，第二次尝试成本低、收益明确。

重试只发生在可重试错误上：HTTP 429、HTTP 5xx、请求超时与网络中断。鉴权失败、参数错误、响应体结构错误不重试，直接中止整条模型链。中止的理由是成本控制：不可重试错误继续向降级模型发送，只会产生三次计费而不改变结果。平台返回体中的限流码（1305、1302）统一归类为限流，与 HTTP 429 同等处理。

重试预算按调用次数而非时间计算，主模型两次尝试加两个降级模型各一次，全链最多四次调用；按单次 45 秒超时计算，理论最坏等待接近三分钟，因此实现中把退避基准压到 0.7 秒并限制抖动上限，避免用户在页面长时间等待。若前端预算先到期，服务端仍会完成当前调用并写入缓存，下一次相同输入可直接命中，不造成额度浪费。

### 5.6.4 熔断状态机

每个模型一个熔断器，采用滑动窗口统计最近 20 次调用，失败率超过 0.5 且样本数不少于 10 时打开，打开持续 30 秒。

```text
            失败率 > 0.5 且样本 >= 10
  CLOSED ──────────────────────────────▶ OPEN
    ▲                                      │ 经过 30s
    │ 探测成功                              ▼
    └──────────────────────────────── HALF_OPEN
                          探测失败 ──▶ OPEN
```

半开状态只放行一个探测请求，其余请求继续按熔断处理，避免打开瞬间被并发打穿。探测成功清空窗口样本回到关闭状态，探测失败立刻重新打开并重新计时。状态变化同步到 `breaker_state` 仪表盘，取值 0 为关闭、1 为半开、2 为打开；打开次数累加到 `breaker_open_total`。熔断按模型独立生效，主模型熔断时请求直接落到降级模型，不必等待超时。

### 5.6.5 缓存设计

缓存键由五段组成：固定前缀、链路名、提示词版本、模型名、输入哈希。输入哈希取规范化 JSON 的 SHA-256 前 32 个十六进制字符，规范化保证键不受字段顺序影响。提示词版本进入键是硬约束：修改提示词必须提升 `PROMPT_VERSION`，否则旧缓存会与新模板混用，产生难以复现的评分差异。

缓存有效期 600 秒，两级容量均为 300 条。一级为进程内 LRU，命中耗时在微秒级；二级为 Redis，供多实例共享。二级读写异常被吞掉并记调试日志，缓存不可用只是降低命中率，不影响正确性。缓存查询位于配额扣减之前，命中不消耗当日额度，这是缓存对成本的实际贡献。

### 5.6.6 配额算法

配额按自然日统计，日期以东八区计算，保证跨时区部署时「今天」的定义一致。键为 `knock:ai:quota:{日期}`，每次真实调用前执行原子自增，返回值为当日已用次数；超过 800 时抛出配额耗尽错误并直接返回 42902。键的过期时间设为两天加一小时，自然过期，无需定时清理。

存储故障时返回负数并放行请求，属于有意的可用性取舍：配额宁可短暂失效，也不能让训练整体不可用。多实例计数依赖 Redis 的原子自增；单机开发未配置 Redis 时退化为进程内计数，进程重启后归零。`ai_quota_used` 仪表盘展示当日已用量，告警阈值设为 720，留出 10% 缓冲用于人工处置。

配额口径是供应商调用次数而不是用户请求次数：缓存命中不计入，降级后未真正发往供应商的请求也不计入。该口径与旧实现的日上限含义一致，便于迁移期对比两侧用量。按每日 800 次、单次平均 0.3 秒测算，配额对应的供应商侧压力远低于每分钟限额，实际瓶颈通常出现在网络抖动而非配额。

### 5.6.7 并发与超时

进程内使用信号量限制同时进行的模型调用，默认 2，与旧实现的全局并发上限一致。生产以 4 个 worker 运行，理论并发上限为 8；真实约束仍是供应商侧的每分钟限额与每日配额，因此信号量主要起削峰与成本保护作用，而不是吞吐上限。

单次调用超时 45 秒，由 httpx 客户端配置；超时被归类为可重试错误，但只有主模型允许重试，整体等待时间上界约为两次超时加退避。前端对意图链路设置 15 秒预算、其余链路 60 秒预算，服务端超时设置必须小于前端预算，避免页面先放弃而服务端仍在计费。网关不实现业务级重试，只在模型链内做一次降级，避免同一发言被重复结算。

### 5.6.8 结构化输出与校验

四条链路对模型输出执行不同强度的校验，校验不通过一律降级，不把半成品写入数据库。

- 意图：去除标点后与八个意图枚举做包含匹配，命中危机关键词时不依赖模型结果。
- 扮演：去引号、去括号动作、合并多行，长度限制 2 至 200 字，命中角色禁区或十类禁用短语即判废。
- 评分：六个维度必须齐全，分值必须落在 0 至 100，理由截断到 60 字；缺任一维度即判废。
- 复盘：优势、改进、下一步三段均非空，下一步不少于 10 字，每段截断到 320 字并删除六个空泛词。

评分链路另有分数带约束：模型给出的分数在融合前柔性收敛到 35 至 95，避免极端值压过规则分。融合比例为规则 0.4、模型 0.6，最终总分按六维权重加权并取整。

四类校验失败都计入 `parse_failed` 降级计数，并按链路拆分到日志字段，便于判断是模板问题还是模型漂移。提示词版本与解析器版本同源，修改解析规则必须同步提升版本号，否则缓存中的旧输出会被新解析器误判。

### 5.6.9 审计与脱敏

每次真实调用或降级都写入审计表，字段包括请求标识、账号标识、链路、供应商、模型、状态、是否使用模型、降级原因、提示词版本、输入哈希与长度、输出长度、耗时、输入输出令牌数、是否缓存命中。输入只保存哈希与长度，不保存对话原文，既可追溯调用量，也不扩大个人信息暴露面。审计写入失败只记调试日志，不影响业务返回。

映射表只列主要入口，函数级对应关系以源码为准：旧实现的每个纯函数在 Python 侧都有同名或近名函数，入参与返回结构按数据类重建，副作用（写本地存储、更新 React 状态）被移到服务层。这样迁移时可以逐函数对照测试，而无需重读整段前端代码。

### 5.7.2 评分与危机复算

评分复算的输入是数据库中的轮次序列，而不是页面传回的分数。服务层先取出该会话的全部轮次，按说话人拆分为服务对象台词与工作者台词；工作者台词逐条匹配规则表，命中危机时该轮不计分并置危机标记；随后计算六维规则底分并应用硬封顶，例如伦理维命中评判句后封顶 60。模型分可用时按 0.4 与 0.6 融合，不可用时直接用规则分，并在响应中标注 `source` 为 `rule`、`used_ai` 为假。

危机判定分两级：命中自杀风险词直接判定为危机级，命中无望表达判定为关注级。危机级在业务入口即短路，模型调用次数为零；关注级允许继续对话，但在评分时提示工作者识别与转介。风险分级结果同时决定是否生成热线卡与暂停会话，暂停后页面必须展示求助渠道才能继续。

### 5.7.3 与旧实现的有意偏离

三处偏离均以业务铁律或部署边界为依据，需在评审中明示。

- 服务对象台词也参与危机判定。旧实现只在工作者台词上判危机（`src/services/scoring.ts:238-250`），服务对象说出「不想活了」不会阻止评分链路调用模型；新实现把该情形置为危机状态并跳过模型，符合「危机级内容永不调模型」铁律。
- 旧评分接口在未配置密钥时返回 `ok=false`，由前端用本地规则兜底；新接口在同样条件下返回结构完整的规则分。兼容层保留旧形状的失败语义，新接口不保留，因为新前端已完成兜底改造。
- 静态资源托管不进入应用进程。旧 Node 进程同时托管构建产物并提供单页应用回退，新方案由 Nginx 与 CDN 承担，应用只提供 API，减少进程内存与文件句柄占用。

## 5.8 兼容层与灰度方案

### 5.8.1 旧接口契约保真

兼容层挂载在 `/api` 前缀，请求体按旧字段名解析，响应体不带统一封装，全部响应附加弃用头。

**表 5-9 旧接口响应形状**

| 接口 | 成功响应 | 失败响应 | 弃用头 |
|---|---|---|---|
| `POST /api/ai/intent` | `ok`、`usedAI`、`intent`、`model`、`ms`、`cached` | `ok=false` 与错误对象 | Deprecation、Sunset |
| `POST /api/ai/persona` | `ok`、`usedAI`、`text`、`model`、`ms` | 同上 | 同上 |
| `POST /api/ai/score` | `ok`、`usedAI`、`scores` 六维对象 | 无密钥时 `scores=null` | 同上 |
| `POST /api/ai/debrief` | `ok`、`usedAI`、`report` 三段 | 无密钥时 `report=null` | 同上 |
| `GET /api/health` | 模型配置、用量、服务端口 | 不适用 | 同上 |
| `GET /api/usage` | 调用、成功、失败、降级、令牌数 | 不适用 | 同上 |
| `POST /api/selftest` | 七条规则样例的自检结果 | 不适用 | 同上 |

旧错误码与业务码的映射为：参数错误对应 `BAD_INPUT`，限流对应 `RPM`，配额对应 `DAILY_CAP`，上游不可用对应 `UPSTREAM`。映射表集中在兼容层，新增业务码不影响旧前端。

### 5.8.2 双跑与切换

灰度遵循绞杀者模式，新旧实现并行运行，按链路逐步切换流量。

1. 新后端部署到独立域名或独立端口，前端仍指向旧 Node 服务。
2. Nginx 按路径把 `/api/ai/intent` 的 1% 流量转发到新后端，其余仍走旧实现。
3. 对比两条链路的关键指标：成功率、`usedAI` 比例、意图分布、P95 耗时、错误码分布。
4. 意图链路一致后按 10%、50%、100% 递增，再依次切换扮演、评分、复盘链路。
5. 四条链路全部切换后，前端把调用地址改为 `/api/v1/ai/*`，开始消费统一响应包与错误码。
6. 观察一个迭代周期，确认无回归后下线旧 Node 服务的 AI 代理部分。

回滚以秒计：把 Nginx 上游改回旧服务即可，数据库仍由新后端写入，旧服务不读新库，因此不存在双向同步问题。评价链路一致性的口径是「同一输入下意图标签一致率」与「评分总分差值不超过 5 分」，而非逐字比对模型输出。

观察窗口建议不少于七个自然日，覆盖工作日与周末两类使用曲线。回滚判据预先约定：错误率超过 1%、意图一致率低于 90%、评分总分平均偏差超过 5 分，任一条件触发即回退。对比数据来自两侧的审计日志与访问日志，按 request_id 无法跨系统关联时，退化为按时间窗与输入哈希配对。

### 5.8.3 兼容层实现要点

兼容层直接复用 v1 的服务与网关，不复制业务逻辑，只做字段名转换与错误形状转换。请求体使用裸字典接收，避免旧前端多传字段被 Pydantic 拒绝；缺失字段按旧默认值补齐。响应中的毫秒数取网关 meta 的延迟，缓存标记取 meta 的命中位。自检接口用七条内置样例跑规则判定，覆盖危机、评判、建议过早、空回应等典型输入，返回通过数与明细，供部署后快速验证规则表是否被正确加载。

## 5.9 可观测性设计

### 5.9.1 结构化日志

日志采用 structlog 输出单行 JSON，字段固定：时间、级别、事件名、服务名、环境、request_id、user_id_hash、HTTP 方法、路径、路由模板、状态码、耗时、客户端地址；AI 相关事件附加模型、是否降级、降级原因、耗时与缓存命中。request_id 由中间件生成并回写响应头，用户标识只输出加盐哈希前 16 位，不输出账号明文。

脱敏在日志处理器层完成，覆盖手机号、邮箱、身份证号与 Bearer 令牌四类模式。对话原文不进入日志，审计表也只保存哈希与长度，满足个人信息最小化要求。

日志按级别分流：生产环境访问日志保留 30 天，错误日志保留 90 天，审计表保留 180 天；超过保留期的日志由集中式日志系统按策略删除，不在应用进程内做文件轮转。采样只作用于成功请求的访问日志，错误与降级事件不采样，保证问题可追溯。

### 5.9.2 指标

**表 5-10 指标清单**

| 指标 | 类型 | 标签 | 用途 |
|---|---|---|---|
| `http_request_duration_seconds` | 直方图 | method、path、status | 非 AI 接口 P95 观测 |
| `http_requests_total` | 计数器 | method、path、status | 流量与错误率 |
| `ai_calls_total` | 计数器 | provider、model、status | 模型健康度 |
| `ai_degraded_total` | 计数器 | reason | 降级原因分布 |
| `ai_quota_used` | 仪表盘 | 无 | 当日配额水位，告警 720 |
| `ai_call_duration_seconds` | 直方图 | model | 模型耗时分布 |
| `breaker_state` | 仪表盘 | model | 0 关闭、1 半开、2 打开 |
| `breaker_open_total` | 计数器 | model | 熔断频次 |
| `training_started_total` | 计数器 | scenario、difficulty | 训练开始量 |
| `training_completed_total` | 计数器 | scenario、difficulty、result | 训练完成量与完成率 |
| `crisis_blocked_total` | 计数器 | risk_level、source | 危机拦截次数 |
| `score_overall` | 直方图 | 无 | 综合分分布，桶 40 至 100 |

`path` 标签使用路由模板而非真实路径，防止带会话 ID 的路径造成标签基数爆炸。指标抓取为纯内存读取，不触发数据库查询。

### 5.9.3 追踪与探针

OpenTelemetry 由开关控制，未安装 SDK 或初始化失败时只输出告警并继续运行，不阻断启动；初始化成功后对 FastAPI 与 httpx 自动埋点，追踪上下文通过响应头透传。存活探针 `/healthz` 恒定返回 200，只反映进程存活；就绪探针 `/readyz` 依次检查数据库连通、键值存储连通与模型配置，任一不满足返回 503，不接收流量。指标端点 `/metrics` 与两个探针均在根路径，不经过版本前缀，便于编排系统与抓取器配置。

## 5.10 性能与并发设计

### 5.10.1 容量预算

**表 5-11 容量与预算**

| 项目 | 目标值 | 实现方式 |
|---|---|---|
| 目标并发 | 500 在线、100 RPS 峰值 | 无状态实例水平扩展 |
| 单实例 worker | 4 | gunicorn 加 uvicorn worker |
| 数据库连接池 | 10 加 20 溢出 | 每实例上限 30 |
| AI 并发 | 每实例 2 | 信号量削峰 |
| 非 AI 接口 P95 | 不超过 300 毫秒 | 索引查询与内存缓存 |
| AI 接口 P95 | 不超过 6 秒 | 超时 45 秒，降级即返回 |
| 缓存有效期 | 600 秒、300 条 | 一级内存加二级 Redis |

非 AI 请求的耗时主要来自数据库往返与序列化，单次查询均走索引，典型查询在两跳以内完成。AI 请求的耗时由供应商决定，网关通过缓存、熔断与快速降级把尾部延迟限制在可接受范围：熔断打开时直接返回规则结果，不等待超时。

性能验收分两步：先在单实例上用固定并发回放真实请求，测非 AI 接口的 P95 与数据库连接占用；再在目标环境用 100 RPS 持续 30 分钟验证水平扩展与配额行为。压测脚本与数据集在二期交付，本期以冒烟脚本验证功能链路，以指标端点验证观测口径。

### 5.10.2 保护与退化

四层保护依次生效：请求体超过 512 KB 直接拒绝，单 IP 每分钟超过 20 次返回 42901，当日配额超过 800 次返回 42902，模型链全失败返回规则结果。四层保护的顺序保证廉价拒绝在前、昂贵调用在后，避免无效流量消耗模型额度。

数据库连接池耗尽时请求在获取连接处排队，由服务器超时兜底；Redis 不可用时缓存与配额退化为进程内实现，功能降级但服务不中断。日志与审计写失败均不影响主流程，防止可观测组件反过来拖垮业务。

## 5.11 本章小结

- 分层以领域层为稳定内核，接口层只做编排，AI 调用集中在网关一处，替换供应商不影响业务代码。
- 请求链路把身份、限流、体积与异常处理放在路由之前，业务代码不重复处理横切关注点。
- 认证采用双令牌加撤销表，授权以应用层归属过滤替代失效的行级安全策略。
- AI 网关以「缓存、配额、熔断、降级」四道闸门控制成本与可用性，降级原因限定为有限标签。
- 旧接口以兼容层保真并带弃用头，灰度按链路递增，回滚只需切换上游。
