# 第6章 数据库设计与迁移

本章给出训练数据的持久化模型与迁移方案。设计目标是让评分、统计、复盘与审计在服务端可复算、可追溯，同时把原先依赖浏览器本地存储与 Supabase 表结构的数据纳入统一关系模型。全章从建模原则与实体关系入手，逐表说明字段与索引，再给出旧存储到新模型的映射、权限模型迁移、Alembic 演进策略与数据治理规则。

## 6.1 设计原则与总体模型

### 6.1.1 建模原则

数据库选用 PostgreSQL 16，开发与测试环境可用 SQLite 兼容驱动运行，两者共用同一套 SQLAlchemy 模型与迁移脚本。

- 主键分两类：账号、会话、轮次、评分、复盘、记录、审计使用 UUID 主键，避免可枚举；案例与知识卡使用业务编号（W-01、T-01）作主键，便于种子数据幂等写入与日志直接引用。
- 时间统一存 UTC，列类型为带时区时间戳；东八区只出现在统计口径与展示层，例如配额日期与热力图按业务时区聚合。
- 稳定查询的字段单独成列，形态多变的字段用 JSON 列保存，例如轮次的附加信息、评分的六维对象、审计的提示词版本与降级原因。
- 关系完整性由外键与级联删除保证，业务状态由状态列表达；会话结束不删除数据，管理员删除账号时级联清理其训练数据，满足个人信息删除要求。
- 枚举值以字符串落库而不是数据库枚举类型，新增取值不需要变更表结构，迁移成本更低。

命名保持两类约定：表名用复数小写蛇形，列名用单数小写蛇形；外键统一以 `_id` 结尾，时间列统一以 `_at` 结尾，布尔列以 `is_`、`has_` 或动词开头。索引命名为 `ix_表名_列名`，唯一约束命名为 `uq_表名_列名`，便于按名称定位对象与排查迁移冲突。案例与知识卡的业务编号保留大写与连字符，与前端路由和日志引用保持一致。

## 6.2 表结构设计

字段类型按 PostgreSQL 表述：`uuid` 对应 SQLAlchemy 的通用 UUID，在 SQLite 下映射为 32 位字符；`timestamptz` 为带时区时间戳；`json` 为通用 JSON，后续可平滑迁移为 JSONB；`text` 为不定长文本，`varchar(n)` 为限长文本。

### 6.2.5 写入顺序与事务边界

一次发言涉及会话、轮次与指标三处写入，事务边界设为「单次请求一个事务」：先更新会话的轮数与情绪，再插入工作者轮次与角色轮次，最后提交。评分写会覆盖同阶段旧结果，结束训练在提交前检查会话状态，避免并发双击产生两条记录。复盘以会话唯一约束作为幂等保证，重复请求命中唯一冲突后读取既有结果返回。

归档训练的写入顺序为：读取会话与全部轮次、计算或读取分段评分、写入训练记录、更新会话状态与结束时间。顺序不可颠倒，因为训练记录依赖评分结果；若中途失败，事务整体回滚，会话仍为进行中，用户可以重试。

审计写入与业务事务分离，采用独立短事务并吞掉异常，原因是审计不应影响业务结果，且模型调用发生在业务事务之外。该取舍需要在监控中补偿：审计写入失败计数进入日志，超过阈值时告警。

## 6.3 索引设计与查询路径

索引按真实查询路径设计，不为「可能有用」的字段建索引。写入侧的成本同样计入：轮次表每次发言写一行，索引过多会拖慢高频写路径。

高频查询共七类：按账号列出会话并按时间倒序、按会话读取全部轮次、按会话读取三阶段评分、按账号读取训练记录时间线、按账号与日期聚合热力图、按维度求平均、按时间清理审计。前四类由复合索引覆盖，最左列均为过滤条件；后三类分别依赖记录表的创建时间索引与审计表的时间索引。

复合索引遵循最左前缀：`(owner_id, status)` 可服务「某账号的进行中会话」，也能服务「某账号的全部会话」，因此不再单建 `owner_id` 索引。唯一约束同时承担索引职责，例如 `(session_id, turn_index)` 既防重复又支撑顺序读取，无需再建同列普通索引。

索引在初始迁移中一次性创建。对大表后续新增索引时，应使用并发创建并在事务外执行，避免长时间锁表；索引是否生效以执行计划为准，上线后通过统计视图观察扫描行数与命中率，再决定增删。

索引总量保持克制，当前 11 张表共 18 个普通索引与 9 个唯一约束，其中约半数为复合索引，单表索引不超过 3 个，写入放大有限。统计类查询优先走训练记录表的复合索引与列式分数，不在会话表上做全表聚合。热门查询若出现回表成本过高，可考虑把案例名等展示字段冗余进记录表，本设计已经在训练记录中冗余案例名与难度标签，避免统计时二次关联。

## 6.4 从旧存储到新模型的映射

### 6.4.1 浏览器本地存储的迁移

旧系统把训练记录、当前会话、设置与草稿写在浏览器本地，键名以 `knock.` 为前缀，数据只存在于当前设备，换机即丢失。新模型把服务端作为唯一事实源，本地只保留未提交的草稿。

- 训练记录：首次登录时按会话标识批量导入，重复标识跳过，导入成功后清理本地记录。
- 当前会话：未结束的会话迁移为服务端会话与轮次；已结束的会话只迁记录，不回放对话。
- 设置与草稿：设置迁入偏好表的 JSON 字段；草稿保留在本地七天，超期清理，避免与服务端会话冲突。
- 成就：旧数据无稳定主键，本期不迁移，成就体系列入二期。

### 6.4.2 Supabase 表的映射

原库共 7 张表、5 个视图，运行时只写不读，因此迁移以结构对齐为主，历史数据可选导入。

**表 6-13 旧表与视图映射**

| 旧对象 | 新对象 | 映射方式 |
|---|---|---|
| case_scripts | scenarios | 字段一一对应，主键沿用业务编号 |
| training_records | training_records | 增加 owner_id，难度文本拆为数值与标签 |
| training_details | turns | 每行明细转为一条轮次，轮次号按序重建 |
| proficiency | 无独立表 | 由训练记录按日聚合，不再冗余存储 |
| achievement | 二期 | 本期不建模 |
| session_record | training_sessions 与 turns | 会话状态入会话表，消息数组拆为轮次 |
| user_settings | user_settings | 补 ai_mode 列，其余偏好入 JSON |
| v_user_stats | `GET /api/v1/stats/me` | 实时聚合训练记录 |
| v_training_heatmap | `GET /api/v1/stats/heatmap` | 按日聚合，时区取东八区 |
| v_heatmap | 同上 | 两个视图合并为一个接口 |
| v_script_progress | 二期 | 按案例进度看板 |
| v_dimension_avg | `GET /api/v1/stats/me` | 六维平均随统计接口返回 |

视图合并的依据是查询成本：原库为每个视图单独维护一份聚合，写入放大且口径容易漂移；新模型只在读时聚合，训练记录表上的索引足以支撑单账号查询，无需物化。

口径对齐需要逐项确认。活跃天数按自然日计数，同一天多次训练只记一天；连续天数在当天尚未训练时不清零，避免上午查看统计误判断签；热力图以天为单位返回计数与等级，等级划分沿用四档，与旧视图的配色阈值一致。六维平均只统计有记录的训练，未评分会话不参与平均，否则会把零分拉低均值。脚本进度与成就看板列入二期，接口契约预留查询参数而不预留表。

### 6.4.3 字段语义变化

- 归属键从昵称改为账号标识。昵称可重复且可修改，不能作为归属依据；旧数据导入时按昵称匹配账号，无法匹配的归入迁移账号并在报告中标注。
- 难度从中文文本改为数值加标签双列。数值用于排序与筛选，标签用于展示，避免排序时按字符串比较。
- 对话从 JSON 数组改为轮次行。行式存储支持按序号分页、按轮次引用与单轮标记，也让评分复算可以只取必要列。
- 时间统一为 UTC。旧表使用本地时间，导入时按东八区换算，避免跨时区部署后统计错位。
- AI 使用标记保留。旧表的 ai_used 与新表的 used_ai 语义一致，用于区分纯规则结果与融合结果。

### 6.4.4 历史数据导入流程与校验

导入分四步，每步可重跑，失败不污染新库。

1. 导出旧表为 UTF-8 的 CSV，保留原始主键与创建时间，导出后记录行数与校验和。
2. 账号匹配：按昵称匹配新库账号；匹配不到的行写入迁移账号，并在报告中标明数量与昵称清单。
3. 结构转换：记录表补 owner_id 与难度双列，明细表按会话分组并重建轮次序号，分数逐列校验取值范围 0 至 100。
4. 入库校验：比对导入行数、六维分数之和、总分与来源会话的一致性；抽样核对对话条数与首末轮内容。

校验失败的条目进入隔离表而不是直接丢弃，便于人工复核。导入脚本以会话标识幂等，重复执行只补充缺失行。导入完成后关闭旧库写入，保留只读快照一个迭代周期作为回退依据。

## 6.5 权限模型迁移：从行级安全到应用层过滤

### 6.5.1 原权限状况

原方案在 6 张表上启用行级安全，但策略全部是 `using (true) with check (true)`，等价于对任何持有匿名密钥的客户端完全放行；案例表甚至没有启用行级安全。前端直接持有数据库密钥，意味着任何打开开发者工具的访问者都可以读写全部训练数据与案例内容。

这一状况的实际后果有三类。其一，越权读取无法拦截，任何客户端都能拉取全部账号的训练记录，涉及学生心理与家庭信息。其二，越权写入无法追溯，记录表的归属字段由客户端填写，篡改后没有服务端签名可以校验。其三，密钥一旦进入构建产物就难以回收，轮换需要重新发布前端，而历史版本仍可能被缓存。因此迁移的第一目标是切断浏览器与数据库之间的直连，而不是在原方案上叠加更复杂的策略。

### 6.5.2 新权限模型

新方案取消浏览器直连数据库，前端只与 API 通信，数据库凭据只存在于服务端。权限分三层：身份层校验令牌，角色层校验操作资格，数据层按归属过滤。

**表 6-14 数据访问控制**

| 数据对象 | 访客 | 学生 | 教师 | 管理员 |
|---|---|---|---|---|
| 案例与知识卡 | 只读 | 只读 | 只读 | 只读 |
| 本人账号 | 只读 | 只读 | 只读 | 读写 |
| 偏好设置 | 禁止 | 本人读写 | 本人读写 | 本人读写 |
| 训练会话 | 禁止 | 本人 | 二期 | 全部 |
| 轮次与评分 | 禁止 | 经会话归属 | 二期 | 全部 |
| 训练记录 | 禁止 | 本人 | 二期 | 全部 |
| 审计日志 | 禁止 | 禁止 | 禁止 | 只读 |
| 撤销令牌 | 服务端 | 服务端 | 服务端 | 服务端 |

数据层过滤统一写成 `where(owner_id == 当前账号)`，会话内的轮次、评分、复盘先校验会话归属再读取，不直接按子表主键查询。该写法集中在服务层的归属加载函数中，新增接口复用它即可，避免各处手写条件导致遗漏。

行级安全不作为主防线，但可在数据库层保留一层兜底策略：服务端专用账号可全量访问，匿名角色无任何权限。历史数据导入完成后，匿名密钥从构建产物中移除并轮换。

归属过滤需要可验证。测试用例覆盖三类场景：访问他人会话返回越权码、访问不存在会话返回不存在码、访客调用写接口返回角色不足码。三类用例在每次提交时运行，防止后续重构把条件写回子查询而绕过归属校验。管理员的跨账号访问单独授权并写审计，避免以「运维方便」为由长期保留超级权限。

## 6.6 Alembic 迁移策略

### 6.6.1 版本与目录

迁移使用 Alembic 单头管理，脚本目录为 `alembic/`，版本表为 `alembic_version`。初始迁移 `0001_initial_schema` 一次性创建 11 张表、全部索引与唯一约束，并实现完整回滚。环境脚本从应用配置读取数据库地址，不把连接串写入 ini 文件，避免凭据入库。

### 6.6.2 演进规则

- 只允许单头。多人并行开发时先拉取最新版本再生成迁移，出现多头立即合并并补一个合并迁移。
- 先加列后切读。新增非空列先以可空形式加入，回填数据后再加非空约束；切换读取代码放在下一个发布，保证任意时刻新旧代码都能运行。
- 重命名与删除走两阶段。先新增列并双写，观察一个发布周期后再停写旧列，最后删除，禁止一条迁移内完成重命名。
- 迁移脚本不做业务计算。数据修复用独立脚本或一次性任务，迁移只改结构，失败时可安全回滚。
- 大表操作避免锁表。新增可空列在 PostgreSQL 中不重写表；索引使用并发创建；回填分批提交。
- 每个迁移必须有降级路径。无法降级的操作需在评审中说明并准备数据备份。

### 6.6.3 实测结果

初始迁移在空库上执行 `alembic upgrade head` 成功创建全部对象；随后执行 `alembic check` 输出无新操作，确认模型与迁移无漂移。开发环境使用 SQLite 时，批量修改通过批处理模式渲染，避免 SQLite 不支持的部分 DDL 语法。

发布顺序固定为：流水线先执行迁移，再滚动更新应用实例；应用启动不自动建表，建表只由迁移负责。回滚时先回滚应用再执行迁移降级，避免旧代码读到不存在的列。生产发布前由预发环境执行一次完整升级与降级演练，记录耗时与锁等待时间。

## 6.7 数据校验与治理

### 6.7.1 校验分层

校验分三层：接口层用 Pydantic 校验必填、长度与范围；服务层校验状态机与归属；数据库层用非空、唯一与外键约束兜底。三层职责不重叠：接口层拒绝非法输入，服务层拒绝非法状态迁移，数据库层防止绕过服务写入脏数据。

案例难度、情绪值、六维分数都有明确区间；轮次序号由服务端生成，不接受客户端指定；会话标识与轮次标识由客户端提供时只作为幂等键，不参与业务判断。

以评分为例：六维分必须是 0 至 100 的整数，缺任一维不允许入库；总分由服务端按权重重算，客户端提交的总分被忽略。以会话为例：状态只能是三个取值，结束后不允许再追加轮次，服务层先查状态再写库，数据库唯一约束作为最后一道防线。

### 6.7.2 脱敏与保留

审计表只保存输入哈希与长度，不保存对话原文；日志对手机号、邮箱、身份证与令牌做掩码。访问日志保留 30 天，错误日志保留 90 天，审计记录保留 180 天，训练记录长期保留供学生回看，账号删除时级联删除其会话、轮次、评分、复盘与记录。备份与恢复策略由第 4 章定义，本章只约束删除范围与保留期。

### 6.7.3 清理与归档

撤销表的过期记录由清理任务删除，删除条件是过期时间早于当前时间；审计表按月归档，超过保留期的数据先导出再删除。会话与记录不做自动归档，避免学生回看历史时数据缺失。二期可对审计表做按月分区，把清理从删除行变为删除分区，降低大表维护成本。

清理任务必须幂等并可观察：每次执行记录删除行数、耗时与失败原因，删除量异常增大时告警，防止条件写错误删有效数据。删除操作先按主键批量查询再删除，单批不超过一万行，避免长事务阻塞写入。

### 6.7.4 数据质量巡检

除写入时的即时校验，还需要周期性巡检兜住历史数据与边界情况。巡检包含四项：会话轮数与实际轮次行数是否一致；训练记录的六维分与总分是否满足加权关系；结束会话是否都有一条训练记录；审计日志中是否存在无请求标识的记录。任一项发现偏差时输出差异清单，不自动修复，由人工确认后再执行订正脚本。

巡检频率为每日一次，结果写入日志并进入看板。偏差比例超过百分之一时告警，因为这说明写入路径存在系统性缺陷，而不是个别脏数据。巡检脚本与迁移脚本放在同一目录，复用同一套数据库连接配置，避免运维时需要两套凭据。

## 6.8 本章小结

- 数据模型以账号为聚合根，训练域四表围绕会话展开，统计与审计各自独立成表。
- 主键分 UUID 与业务编号两类，时间统一 UTC，枚举以字符串落库，迁移成本最低。
- 索引按七类高频查询设计，复合索引承担过滤与排序，唯一约束兼任索引职责。
- 权限模型从失效的行级安全迁移到应用层归属过滤，浏览器不再持有数据库凭据。
- 迁移遵循先加列后切读与两阶段重命名，初始迁移已实测可升级且无漂移。
