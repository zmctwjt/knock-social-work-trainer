# 第9章 重构实施计划

本章把第3章至第8章的设计落成可执行、可检查、可回退的 13 周计划。计划的核心不是"排期表"，而是三条纪律：任何一周结束时系统都处于"可演示、可回退"的状态；新旧两条链路始终有一方可承接全部流量；每个阶段的准出条件都用可自动判定的指标表达，而不是"感觉差不多了"。在此基础上给出 WBS、测试策略、风险登记册与回滚预案。

## 9.1 迁移策略：绞杀者模式

### 9.1.1 四态演进

![图 9-2 绞杀者迁移路径](figures/fig-07-migration.png)

如图 9-2 所示，迁移分四态推进，任何时刻都不同时存在"两个真相"。

| 状态 | 流量分布 | 数据写入 | 判定条件 | 退出条件 |
|---|---|---|---|---|
| 状态一：Node 单跑 | 100% → Node 8787 | localStorage + 可选 Supabase | 基线版本冻结、评测集就绪 | 第2周末 |
| 状态二：双跑灰度 | 5% → Python，95% → Node | 双写（PG 为准，localStorage 镜像） | 四链路一致率 ≥ 99%、错误率差 ≤ 0.5% | 第7周末 |
| 状态三：Python 主跑 | 100% → Python /api/v1，Node 旁路 | PG 为唯一权威 | 连续 7 天 SLO 达标、零 P0 事故 | 第11周末 |
| 状态四：收尾 | 100% → Python，Node 下线 | PG + 对象存储 | 旧服务无流量 14 天 | 第13周末 |

**表 9-1 绞杀者四态与切换条件**

四态设计的价值在于"随时可停"：任一状态出问题，只需把 Nginx 的 upstream 权重调回上一态，数据层因双写而不会撕裂。这也解释了为什么第5章要求 legacy 兼容层必须保留到状态四——它不是技术债，而是安全绳。

### 9.1.2 双跑与一致率判定

双跑期间，同一笔请求在两侧各算一次，比对以下五项：

1. **判定结果**：intent 分类的四类枚举是否一致；
2. **六维分数**：delta ≤ ±3 分视为一致（评分含语义判断，允许小幅波动）；
3. **风险等级**：三级 must be exactly equal，任何不一致立即阻断切换；
4. **是否调用模型**：`used_ai` 标记必须一致，否则说明降级逻辑偏移；
5. **响应时延**：P95 差值 ≤ 500 ms。

一致率按 `1 - 不一致样本数 / 总样本数` 计算，样本来自第2周冻结的 150 条 golden set 加上灰度期真实流量的 10% 抽样。判定阈值为 99%，未达标则回到对应链路单独修复，不整体回退——这正是"按链路灰度"的含义：intent、persona、score、debrief 四条链路可以分别切换。

### 9.1.3 流量切换规则

| 阶段 | 切量 | 观察期 | 观察指标 | 继续条件 |
|---|---|---|---|---|
| 切量一 | 5% | 48 小时 | 错误率、P95、降级率、一致率 | 全部达标 |
| 切量二 | 50% | 72 小时 | 同上 + 用户投诉数 | 全部达标 |
| 切量三 | 100% | 7 天 | 同上 + SLO 消耗 | 全部达标 |

**表 9-2 灰度切量规则**

切量操作统一由 Nginx 权重变更完成，不重启服务；每次切量前自动打 tag 与快照，切量后 10 分钟内值班人必须确认核心四项指标。任何一项突破阈值（错误率 > 1%、P95 > 8 s、降级率 > 20%、一致率 < 98%）立即回切并记录事故单。

### 9.3.2 估算方法与关键路径

估算采用三点法（乐观/最可能/悲观加权），并对无历史数据的任务（T3.1 领域移植）用类比法校正：Node 侧对应代码 1,090 行（rules 568 + scoring 522），按"1 行移植 + 0.6 行测试 + 0.4 行比对脚本"的经验系数折算 6 人天。

关键路径为 T1.1 → T1.2 → T3.1 → T3.4 → T5.1 → T5.4，链条上任何环节延期直接压缩缓冲。非关键路径的任务（T4.3 可观测、T4.4 安全加固）有 2–3 天浮动时间，可在周五对齐会上动态调整。计划只排 63 人天有效工作 + 2 人天缓冲，余量故意留薄，目的是把"范围可裁剪"变成显式决策：一旦某周落后超过 2 天，立即按"砍一期范围（对象存储导出、教师端报表）→ 保核心链路"的优先级削减，而不是靠加班。

### 9.4.2 新旧口径一致性回归

这是本项目最重要的一类测试，因为"成绩可信"是改造的第一目标。做法如下：

1. golden set 中每条样本包含：服务对象角色、阶段、历史对话、学生本轮发言、期望的意图类别、期望六维分数区间、期望风险等级。
2. Node 侧写一个离线导出脚本（复用 `src/services/rules.ts` 等模块，用 tsx 直接跑，不起服务），输出 JSON。
3. Python 侧用 pytest 参数化跑同一批样本，输出同结构 JSON。
4. 比对脚本输出差异报告：按维度统计 delta 分布，标注超阈值样本。
5. 差异必须"归因"后才能修：是移植错误（改代码）、是阈值设计差异（改阈值并记录 ADR）、还是模型波动（扩大容差并说明）。

一致性测试的通过标准是三层：风险等级 100% 一致、意图 100% 一致、六维分数 99% 在 ±3 内。任一层不达标即阻断 M3 里程碑。

### 9.4.3 性能与安全测试

性能测试用 k6 三组场景：混合读写（80/20）、AI 链路（仅打 intent/score，避免真实计费，用 mock 供应商）、峰值突刺（30 秒内 0→100 RPS）。验收阈值见第8章 SLO 表；不达标时的优化顺序为：先查 N+1 查询与缺失索引，再调连接池，再考虑加 worker，最后才考虑加机器。

安全测试按第7章 7.8 节清单执行，其中三条为强制项：越权访问他人 session 必须返回 403 而非 404（避免存在性泄露）；危机内容直连 API 必须被服务端拦截（不依赖前端）；限流在 Redis 故障时必须 fail-open 降级为内存计数而不是全站 503。

## 9.6 回滚与应急预案

### 9.6.1 回滚触发条件

| 级别 | 触发条件 | 动作 | 时限 |
|---|---|---|---|
| L1 单链路 | 某条 AI 链路错误率 > 10% 持续 5 分钟 | 该链路回切 Node，其余保持 | 5 分钟 |
| L2 应用 | 5xx > 2% 或 P95 > 8 s 持续 10 分钟 | Nginx 权重整体回切上一态 | 10 分钟 |
| L3 数据 | 迁移后数据校验不一致或写入异常 | 停止双写，回滚到快照，读走旧库 | 30 分钟 |
| L4 安全 | 发现越权或数据泄露 | 关闭对应接口、吊销令牌、启动事故流程 | 立即 |

**表 9-8 回滚触发条件与时限**

回滚不是"恢复备份"这么简单，必须与数据迁移顺序配合。第4章 4.8 节规定的三条向前兼容原则在此落地：只加列不删列、只加表不改语义、新旧代码都能读旧数据。因此 L2 回切不需要回滚数据库，L3 才需要，且 L3 的回滚点是"迁移前快照"，不是"最后一次备份"。

### 9.6.2 演练要求

每个里程碑前做一次回滚演练，记录"从发现到恢复"的实际耗时。M4 前的演练必须覆盖 L1、L2 两级；M5 前覆盖 L3。演练不通过不得切量，这是硬门禁。演练脚本与记录纳入第10章上线检查单的附件。

## 9.8 本章小结

- 采用绞杀者模式四态迁移，任何时刻只有一方承接流量、数据双写保证可回切；四条 AI 链路可独立灰度，切换由 Nginx 权重完成，不重启服务。
- 13 周分五阶段，63 人天有效工作 + 2 人天缓冲，关键路径为基线→评测集→领域移植→会话服务→切量→答辩材料；落后超过 2 天即按预设优先级裁剪范围，不靠加班。
