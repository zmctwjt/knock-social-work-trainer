# 第3章 技术选型与总体架构

本章回答"换成什么技术、为什么这样换、换完长什么样"三个问题。选型不以"流行"为依据，而以第2章诊断出的问题清单为输入：凡是不能消除 P0 问题的技术选择一律不采用；凡是会破坏原作品业务铁律（危机永不调模型、台词白名单、AI 失败静默降级）的重构方案一律否决。在此基础上给出目标总体架构与 8 条架构决策记录（ADR），作为第4章至第8章的共同基准。

## 3.1 选型原则与约束

### 3.1.1 五条硬约束

选型必须同时满足以下五条约束，缺一不可。

| 编号 | 约束 | 来源 | 对选型的直接影响 |
|---|---|---|---|
| C1 | 业务铁律不可丢失 | 原作品设计（第1章 1.5 节） | 评分、判定、危机拦截必须可复算、可审计，且危机分支不得被任何异步链路绕过 |
| C2 | 成绩必须可信 | 第2章 P0-01、P0-02 | 评分与判定逻辑必须离开浏览器，服务端为唯一权威 |
| C3 | 13 周内可交付 | FACTS H 区 | 技术栈学习成本必须低，避免引入需要长期调优的基础设施 |
| C4 | 成本可控 | 毕业设计场景，预算有限 | 优先选用免费额度充足、单机可跑、云上可平滑放大的组件 |
| C5 | 可演进 | 500 在线 / 100 RPS 目标 | 架构需支持从单机 Compose 平滑迁移到 K8s，不推翻重来 |

### 3.1.2 评价维度与权重

对每个候选技术，按六个维度打分（1–5 分），加权求总分。权重体现本项目"宁可保守、不可返工"的取向。

## 3.2 后端语言与框架选型

### 3.2.1 语言层：Node.js 与 Python 的取舍

原作品后端使用 Node.js 内置 `node:http`，零第三方依赖，1,046 行代码承担了静态托管与四条 AI 代理链路（`server/index.mjs:112-352`）。这一形态在单机演示中表现良好，但它的问题不在语言本身，而在**工程形态**：无框架、无类型、无分层、无测试、无进程管理。因此语言选型要回答的不是"Node 好不好"，而是"在 13 周内，哪种语言能以最低风险补齐工程形态"。

| 评价项 | Node.js（Express/Fastify + TypeScript） | Python（FastAPI） | 结论 |
|---|---|---|---|
| 异步 IO 模型 | 事件循环，天然异步 | asyncio，异步生态成熟 | 持平 |
| 与原代码的连续性 | 高，可直接改写现有 handler | 中，需重写 1,046 行 | Node 占优 |
| AI/LLM 生态 | 中，SDK 可用 | 高，官方与社区 SDK 最全，评测与结构化输出工具多 | Python 占优 |
| 数据与统计能力 | 中，需额外库 | 高，pandas/numpy 可直接做成绩分析与报告 | Python 占优 |
| 类型与契约 | TypeScript 强类型 | Pydantic v2 运行期校验 + mypy 静态检查 | 持平 |
| 与毕业设计方向的匹配 | 弱（任务书方向为大数据应用开发） | 强（数据采集、分析、可视化链路完整） | Python 占优 |
| 单人交付风险 | 低（路径熟悉） | 中（需重学框架） | Node 略占优 |

**表 3-3 后端语言对比**

决策采用 Python，理由有三点。第一，C2 要求的"服务端权威评分"需要把 568 行判定规则与 522 行评分逻辑从 TypeScript 移植过来，移植的同时必须建立可回归的测试集，Python 的 pytest 与数据断言表达力更强。第二，成绩分析与热力图统计（原 `v_user_stats`、`v_training_heatmap` 两个视图）在 Python 中可直接复用 pandas 做离线校验，便于第10章验收时做"新旧口径一致性"比对。第三，任务书方向为大数据应用开发，Python 技术栈更贴合答辩叙事。

同时必须承认代价：1,046 行 Node 代码需要重写，团队需要重新熟悉异步框架。这一代价通过第9章的"绞杀者迁移 + 双跑比对"控制——旧服务不下线，新服务逐链路接管，任何一条链路指标不达标即回退。

### 3.2.2 框架层：FastAPI / Django / Flask 对比

| 评价项 | FastAPI | Django + DRF | Flask |
|---|---|---|---|
| 异步原生支持 | 原生 async/await | 3.1 起部分支持，ORM 仍同步为主 | 需扩展 |
| 请求/响应校验 | Pydantic v2 内建，OpenAPI 自动生成 | Serializer，需手工维护 schema | 无内建 |
| 依赖注入 | `Depends` 原生 | 无统一机制 | 无 |
| 后台管理 | 无（另建） | 自带 Admin，开箱可用 | 无 |
| 学习曲线 | 低 | 中高 | 低 |
| 适合场景 | API 服务、异步代理 | 内容管理、表单型系统 | 小型服务 |
| 本项目匹配度 | 高 | 中（Admin 有价值，但异步 AI 代理是短板） | 低（需自建校验与文档） |

**表 3-4 后端框架对比**

结论为 FastAPI。核心判断是：本项目 80% 的后端负载是"等待外部 LLM 返回"的 IO 等待，异步能力是硬指标；而 Django 的优势（Admin、ORM 全家桶、模板）在本项目中价值有限，教师端报表完全可以用独立的前端页面 + 只读 API 实现。FastAPI 的 `Depends` 恰好可以承载"认证 → 角色校验 → 配额检查"这条横切链，避免在每个 handler 里重复写样板代码。

### 3.2.3 ADR-01：采用 Python 3.12 + FastAPI

- **决策**：后端语言 Python 3.12，框架 FastAPI，ASGI 服务器 Uvicorn，生产用 Gunicorn 管理多 worker。
- **理由**：异步 IO 与 LLM 调用天然匹配；Pydantic v2 同时承担"请求校验 + LLM 结构化输出校验"两种职责，减少一套校验代码；OpenAPI 自动生成可直接产出附录A 的接口清单，保证文档与代码不脱节。
- **替代方案与否决原因**：Django 因异步 ORM 与 Admin 之外的收益不足被否决；Flask 因缺少内建校验与依赖注入，会重演原作品"手写路由 + 手写校验"的工程债被否决。
- **代价与缓解**：需重写 Node 层；通过第9章双跑灰度与第2章问题清单驱动重写范围（只重写必要能力，不追求 1:1 复刻）。

## 3.3 数据层选型

### 3.3.1 关系数据库：PostgreSQL 16

原作品的数据层有两个并存实现：浏览器 localStorage（默认权威）与 Supabase（可选，7 表 5 视图）。二者的共同问题是**没有真正的服务端数据权威**：localStorage 随浏览器清除而丢失，Supabase 的 RLS 策略写成 `using (true)`，等于对匿名 key 全放行（`001_schema.sql:184-198`、`002_schema_supplements.sql:177-179`）。

| 评价项 | PostgreSQL 16 | MySQL 8.0 | 结论 |
|---|---|---|---|
| JSONB 与索引能力 | 强，GIN 索引可查 JSON 内部字段 | 8.0 支持 JSON，函数索引弱 | PG 占优 |
| 窗口函数与统计 | 完整，适合热力图/排名 | 完整 | 持平 |
| 部分索引 / 表达式索引 | 支持 | 部分支持 | PG 占优 |
| 行级安全（RLS） | 原生 | 无 | PG 占优（可作为纵深防御备用） |
| 云上托管可得性 | 华为云 RDS for PostgreSQL | 华为云 RDS for MySQL | 持平 |
| 团队熟悉度 | 中 | 中高 | MySQL 略占优 |

**表 3-5 关系数据库对比**

选择 PostgreSQL 16。决定性因素是 JSONB：内容层资产（12 位角色、118 个台词节点、19 张技巧卡）结构会随教学迭代变化，用 JSONB 存储可在不频繁改表的前提下扩展，同时用 GIN 索引支持"按标签检索技巧卡"这类查询。9 个既有索引（FACTS E 区）可平移为 PG 索引，迁移成本可控。MySQL 的优势（团队熟悉度）不足以抵消 JSONB 与部分索引带来的设计余量。

### 3.3.2 缓存与配额：Redis 7

原作品的限流、并发、配额、缓存全部是进程内内存（`server/glm.mjs:103-155`、`:185-187`），带来三个生产级缺陷：重启即清零（配额可被重启绕过）、多副本不共享（扩容后配额翻倍）、无法观测（没有可导出的计数）。Redis 7 同时解决这三个问题，并额外承担三类职责：

| 用途 | 键设计 | TTL / 结构 | 对应原实现 |
|---|---|---|---|
| 单 IP 限流 | `rl:ip:{ip}:{window}` | INCR + EXPIRE 60s | `glm.mjs:103-116` |
| 全局并发 | `sem:ai` | 计数 + 超时释放（Lua 原子操作） | `glm.mjs:118-131` |
| 每日配额 | `quota:day:{yyyymmdd}` | INCR，次日 00:00 过期 | `glm.mjs:185-187` |
| AI 结果缓存 | `ai:resp:{promptVersion}:{model}:{hash}` | SETEX 600s，容量上限 300 条（LRU 淘汰） | `glm.mjs:135-155` |
| 会话与刷新令牌撤销 | `jwt:revoked:{jti}` | SETEX，等于令牌剩余有效期 | 新增 |
| 熔断器状态 | `cb:{provider}:{model}` | HASH，滑动窗口计数 | 新增 |

**表 3-6 Redis 职责矩阵**

选择 Redis 7 而非 Memcached 的理由是数据结构：并发信号量需要原子计数与超时释放，熔断器需要滑动窗口，缓存需要 LRU——这些用 Redis 的 Lua + ZSET + HASH 可直接实现，Memcached 只能靠应用层拼装。

### 3.3.3 ORM 与迁移：SQLAlchemy 2.0 async + Alembic

- **SQLAlchemy 2.0**：原生 async 会话，`select()` 构造器风格，与 FastAPI 的 `Depends` 组合良好；同时保留同步接口用于 Alembic 迁移与离线脚本。
- **asyncpg**：Python 生态最快的 PG 驱动，配合 PgBouncer 的 transaction 模式可支撑 100 RPS 峰值。
- **Alembic**：迁移脚本纳入版本控制，与 CI 绑定；要求"迁移可前滚、可回滚、向前兼容"三条规则，防止发布期间新旧代码同时读同一张表时崩溃（详见第6章与第4章 4.8 节）。
- **SQLite（aiosqlite）**：仅用于单元测试，保证 `pytest` 不需要真实 PG 即可运行；生产环境通过 `DATABASE_URL` 切换为 asyncpg。

### 3.3.4 对象存储：OBS / MinIO

复盘报告导出（PDF/DOCX）、可选的训练音频、备份归档三类数据不适合放在数据库或本地磁盘。开发与单机部署用 MinIO（S3 兼容），生产用华为云 OBS；代码层统一走 S3 兼容 SDK，仅通过 endpoint 与密钥切换。此能力在 13 周内定为"一期骨架 + 二期启用"，一期只落"导出报告"一条链路，避免范围膨胀。

## 3.4 AI 工程层选型

### 3.4.1 模型与供应商

原作品主模型为 glm-4.7-flash，降级链 glm-4.5-flash → glm-4-flash，请求固定 `thinking:{type:"disabled"}`（`server/glm.mjs:44-49`、`:199`）。生产化不更换主模型，原因有二：其一是成本（flash 档位免费/低价，适合教学场景）；其二是行为一致性——评分 prompt 与解析逻辑已针对该模型输出格式调优，换模型等于重做一遍提示词工程。

但供应商必须被抽象。设计 `LLMProvider` 协议：

```python
class LLMProvider(Protocol):
    name: str
    async def complete(self, *, model: str, messages: list[Message],
                       temperature: float, max_tokens: int,
                       timeout_s: float) -> LLMResult: ...
```

**代码 3-1 LLMProvider 协议（节选，完整实现见 `deliverables/backend/app/services/llm/base.py`）**

当前实现为 `ZhipuProvider`（OpenAI 兼容端点），另预留 `OpenAICompatProvider` 以便答辩现场演示"替换供应商不改业务代码"。协议之上是 AI 网关（见 3.4.2），业务代码只依赖网关，不直接依赖任何 SDK。

### 3.4.2 AI 网关的职责边界

原作品把配额、缓存、并发、降级、提示词全部塞在 `server/glm.mjs` 一个 327 行文件里，四条链路各自复制一份降级分支。生产化把它们收敛为一个网关，职责如下：

| 职责 | 实现要点 | 失败时的行为 |
|---|---|---|
| 配额 | Redis 日计数，按用户与全局双维度 | 返回 42902，不调模型 |
| 缓存 | 键含提示词版本、模型名、输入 hash；仅对确定性链路（intent/score）启用 | 命中直接返回，标记 `cached=true` |
| 熔断 | 滑动窗口失败率 > 50% 且样本 ≥ 10 → 打开 30s → 半开探测 | 直接走规则兜底，标记 `used_ai=false` |
| 供应商路由 | 主模型失败且为 429/5xx/超时 → 按链降级；业务错误不降级 | 全部失败则降级分支 |
| 结构化校验 | Pydantic 校验 + 字段级修正（截断、枚举归一） | 校验失败按"解析失败"降级 |
| 审计 | `ai_audit_log` 落库：链路、模型、耗时、token、降级原因、输入摘要 hash | 审计失败不影响主流程（异步写） |
| 追踪 | 每次调用生成 `ai.call` 子 span，带 provider/model/status 属性 | — |

**表 3-7 AI 网关职责矩阵**

这里有一条必须坚持的边界：**网关不做业务重试**。原作品的设计是"AI 失败即降级，不重试"，因为重试会放大延迟并可能重复计费，而教学场景对"这一次是否用了 AI"并不敏感，对"页面是否卡住"极其敏感。网关只在同一请求内按模型链切换一次，切换失败即降级。

### 3.4.3 结构化输出与校验

四条链路中，intent 与 score 需要结构化结果（意图枚举、六维分数），persona 与 debrief 是自然语言。对前两者采用"JSON 模式 + Pydantic 校验 + 容错解析"三层：

1. 提示词中给出 JSON Schema 与两个正例、一个反例；
2. 响应先用 `json.loads`，失败则尝试提取代码块/首尾大括号；
3. 用 Pydantic 模型校验，字段缺失填默认值，超出范围裁剪到 [0,100]，枚举不匹配映射为 `unknown`；
4. 任一层失败即记录 `degraded_reason`，返回规则兜底结果，`used_ai=false`。

这一设计与原作品"解析失败就返回 null、页面自行兜底"相比，把"页面兜底"上移为"服务端兜底"，页面只负责展示，避免第2章 P0-02 的绕过路径。

## 3.5 前端与交付形态

### 3.5.1 ADR-03：保留 React，不做服务端渲染

- **决策**：保留 React 18.3 + TypeScript 5.6 + Vite 5.4 + Tailwind 3.4，前端只改造 API 调用层、鉴权与错误处理；构建产物为纯静态文件，由 CDN/Nginx 托管。
- **理由**：前端 12,893 行中包含大量教学内容资产（2,463 行 data、1,856 行 services），重写等于重做内容；静态化让前端可独立灰度、独立缓存，且不占用 API 服务器资源。
- **否决方案**：Next.js SSR —— 本项目无 SEO 需求，SSR 会引入 Node 运行时，与"后端统一 Python"的目标冲突。
- **代价**：首屏需加载 JS 包；通过路由级代码分割与 CDN 缓存缓解（第4章 4.5 节）。

### 3.5.2 前端改造点清单

| 改造点 | 原实现 | 目标实现 | 影响范围 |
|---|---|---|---|
| API 基地址 | 相对路径 `/api/ai/*` | `/api/v1/*` + 环境变量 `VITE_API_BASE` | `src/lib/aiClient.ts` |
| 鉴权 | 无 | 登录后 Bearer token，401 自动刷新一次 | `aiClient` 请求拦截 |
| 评分调用 | 浏览器内 `scoring.ts` 计算 | 调 `/api/v1/sessions/{id}/stages/{n}/score` | `useSession.ts`、`TrainingPage` |
| 危机拦截 | 前端 `crisis.ts` 判断后不调模型 | 保留前端即时提示，服务端二次硬拦截（双保险） | `crisis.ts` 保留 |
| 数据持久化 | localStorage 为主 | 服务端会话 + 本地草稿缓存（离线容错） | `db.ts` |
| 身份态 | localStorage 记录昵称/账号 | JWT + `/auth/me` | 新增 auth store |
| 错误处理 | 逐处 try/catch 兜底 | 统一错误码 → 提示文案映射 | 新增 `errors.ts` |

## 3.6 部署与运维技术栈

### 3.6.1 ADR-08：单机 Compose 起步，K8s 收口

| 阶段 | 编排方式 | 适用场景 | 交付判定 |
|---|---|---|---|
| 阶段一 | Docker Compose 单机全栈 | 毕设演示、答辩现场、小规模试用（≤50 并发） | 一条 `docker compose up` 起全栈，含 PG/Redis/Nginx/监控 |
| 阶段二 | 华为云 CCE（兼容 K8s） | 院系正式上线（500 在线） | HPA 自动扩缩、滚动发布、PDB 保障 |

**表 3-9 两阶段部署形态**

### 3.6.2 可观测技术栈

| 能力 | 选型 | 理由 |
|---|---|---|
| 指标 | Prometheus + Grafana | 与 `/metrics` 端点天然对接，告警规则用 PromQL 表达 |
| 日志 | structlog JSON → Loki | 结构化字段可直接在 Grafana 联查，避免全文检索成本 |
| 追踪 | OpenTelemetry → Tempo | 与 FastAPI/httpx 自动埋点集成，可追到"哪一次 LLM 调用慢" |
| 异常 | Sentry | 前端与后端统一异常聚合，含 sourcemap |
| 告警 | Alertmanager → 企业微信/邮件 | 学校场景无需 PagerDuty |

**表 3-10 可观测技术栈**

四件套全部选择开源方案，唯一商业组件是 Sentry（有免费额度）。选择理由不是"先进"，而是"单人可以维护"：Prometheus 拉模式无需 agent、Loki 与 Grafana 共用数据源、Tempo 通过 traceID 与日志互跳，三者在 Grafana 内形成闭环，减少排障时的上下文切换。

### 3.6.3 CI/CD 与质量门禁

GitHub Actions 流水线分五段：`lint`（ruff + mypy）→ `test`（pytest + PG/Redis service 容器）→ `build`（Buildx 多阶段镜像 + 层缓存）→ `scan`（Trivy，HIGH/CRITICAL 阻断）→ `deploy`（仅 main、需人工审批）。前端单独一条流水线：`tsc --noEmit` → `vite build` → 产物上传 OBS + 刷新 CDN。

门禁标准：单测覆盖率 ≥ 70%（核心服务 ≥ 85%）；mypy strict 对 `app/` 通过；任何 P0 级 lint 告警阻断合并。这一标准写进第10章上线检查单。

## 3.7 目标总体架构

### 3.7.1 分层视图

![图 3-1 目标总体架构](figures/fig-02-target-arch.png)

目标架构分五层，自上而下为接入层、应用层、领域层、基础设施层与外部依赖，可观测作为横切能力贯穿全层。如图 3-1 所示，请求从 Nginx Ingress 进入后，先经过中间件链（请求 ID → 认证 → 限流 → 配额 → 校验），再进入路由；路由只做参数装配，业务判断在领域层，IO 在基础设施层。

### 3.7.2 层间依赖规则

| 层 | 可依赖 | 禁止依赖 | 说明 |
|---|---|---|---|
| 接入层（api/） | 应用服务、领域 schema | 直接访问 ORM 会话 | 路由不得写 SQL |
| 应用服务（services/） | 领域对象、基础设施接口 | 直接依赖 httpx/asyncpg 具体实现 | 通过端口（Protocol）注入 |
| 领域层（domain/） | 仅标准库与 Pydantic | 任何 IO、任何框架 | 纯函数，可 100% 单测 |
| 基础设施（infra/） | 领域接口的实现 | 业务规则 | 只做"翻译"，不做判断 |
| 横切（core/） | 全部 | 被业务反向依赖 | 配置/日志/安全/错误 |

**表 3-11 层间依赖矩阵**

这条规则的价值在于可测性：领域层（评分、判定、危机分级）完全不依赖数据库与网络，因此第9章的"新旧口径一致性回归"可以对同一批样本在 Node 与 Python 两侧各算一次，逐条比对，不需要起服务。

## 3.8 非功能目标

### 3.8.1 性能与容量

目标并发 500 在线、峰值 100 RPS（FACTS H 区），折算到单体 API 约 3–4 个 worker 即可满足，前提是 AI 调用不阻塞 worker——这正是选择 async 框架的原因。非 AI 接口 P95 ≤ 300 ms，AI 接口 P95 ≤ 6 s、超时 30 s。容量按 5 万账号、100 万训练记录/年设计，单表年增约 100 万行、按 30 字节/行估算年增 < 1 GB，三年内单库可承载；超过后再引入按学期分区。

### 3.8.2 可用性与恢复

月度可用性 99.9%（允许停机约 43 分钟）。RPO 15 分钟、RTO 1 小时，通过 WAL 归档 + 每日全备 + 异地对象存储达成，季度演练一次（第4章 4.9 节）。AI 供应商不可用不属于可用性违约范围，因为设计上具备"全链路降级为规则模式"的能力，降级期间可用性仍为 99.9%，仅体验下降——这一约定必须写进 SLO 文档（第8章 8.1 节）。

## 3.9 本章小结

- 选型输入是第2章的 P0 问题清单与四条业务铁律，不以技术流行度为依据；五条硬约束中"业务铁律不可丢失"具有一票否决权。
- 后端选定 Python 3.12 + FastAPI，核心依据是异步 IO、Pydantic 双向校验（请求与 LLM 输出）与领域层可纯函数化；Node 的连续性优势通过绞杀者迁移与双跑比对来对冲。
- 数据层选定 PostgreSQL 16 + Redis 7 + SQLAlchemy 2.0 async + Alembic；Redis 的关键价值是把限流、配额、缓存、熔断从"进程内存"外置为"可共享、可观测、不随重启丢失"。
- 前端保留 React 只改 API 与鉴权层，危机拦截采用"前端即时提示 + 服务端硬拦截"双保险，而非删除前端逻辑。
- 部署采取 Compose 起步、CCE/K8s 收口的双阶段形态，保证答辩现场可离线演示，同时具备生产扩展路径；可观测四件套以"单人可维护"为首要标准。
- 目标架构的五层依赖规则（接入 → 应用 → 领域 → 基础设施，横切贯穿）是后续第5章代码结构与第9章测试策略的共同基础。
