# 第8章 可观测性与运维保障

本章把"系统上线后能不能被看见、被定位、被恢复"作为目标，给出指标、日志、追踪三位一体的可观测方案，以及告警分级、仪表盘、故障预案与常态化巡检机制。所有指标名与告警规则以 `deliverables/deploy/prometheus/` 与 `grafana/dashboard.json` 为准，正文只说明设计意图与使用方式，不重复粘贴配置。

## 8.1 SLI 与 SLO

### 8.1.1 服务水平指标定义

服务水平指标（SLI）必须是用户可感知的信号，且能从监控数据直接算出，不能依赖主观判断。四类 SLI 覆盖可用性、延迟、正确性、AI 质量四个维度。

**表 8-1 SLI 与 SLO 定义**

| SLI | 定义（计算式） | SLO 目标 | 统计窗口 |
| --- | --- | --- | --- |
| 可用性 | 非 5xx 请求数 / 总请求数 | ≥ 99.9% | 滚动 30 天 |
| 非 AI 延迟 | `ai="false"` 请求的 P95 | ≤ 300 ms | 滚动 1 小时 |
| AI 延迟 | AI 请求 P95（含降级为 ok 的调用） | ≤ 6 s | 滚动 1 小时 |
| 错误率 | 5xx 请求数 / 总请求数 | < 0.5% | 滚动 1 小时 |
| AI 成功率 | `ai_calls_total{status="ok"}` / AI 调用总数 | ≥ 95% | 滚动 1 天 |

可用性口径需要注意两点：健康检查与指标抓取不计入 SLI，否则探针失败会稀释真实错误率；客户端主动取消的请求（499）不计入分母，这是用户行为而非服务故障。AI 延迟只统计最终返回成功的调用，超时与降级单独统计，避免"降级很快所以 P95 变好"的假象。

### 8.1.2 错误预算与燃尽

99.9% 的 30 天 SLO 对应错误预算 43 分 12 秒。预算按"分钟级不可用"折算，用于判断能否继续发布：

**表 8-2 错误预算燃尽策略**

| 燃尽比例（30 天窗口） | 燃尽时长 | 处置 |
| --- | --- | --- |
| < 10% | 1 小时消耗 < 4.3 分钟 | 正常发布 |
| 10%–50% | 1 小时消耗 4.3–21.6 分钟 | 发布需负责人确认，暂停非紧急变更 |
| 50%–100% | 1 小时消耗 21.6–43.2 分钟 | 冻结发布，只允许修复类变更 |
| 100% | 预算耗尽 | 停止功能迭代，进入可靠性专项 |

燃尽率用多窗口计算（5 分钟短窗口判断突发，1 小时长窗口判断趋势），短窗口燃尽过快但长窗口正常时，通常是一次瞬时尖峰；两个窗口同时越界才是持续性劣化。告警规则 `KnockErrorBudgetBurning` 负责长窗口，短窗口由 5xx 率告警覆盖。

### 8.1.3 SLO 的评审与调整

SLO 不是一次性写死的数字，需要按季度评审。评审依据三项输入：过去一个季度的实际达成率、用户投诉与反馈、成本变化。若连续三个季度达成率高于 99.95%，说明目标偏松，可以提高目标或降低冗余投入；若连续两个季度未达标，先判断是目标过严还是系统确有缺陷，前者调整目标、后者列入可靠性专项，不允许"只改数字不改系统"。

调整 SLO 必须走变更流程并记录理由，因为 SLO 直接决定告警阈值与发布节奏。SLO 收紧后，错误预算变小、告警更容易触发、发布更保守；SLO 放宽后相反。两类调整都会影响值班负担，需要在团队内同步。

另外要区分"内部 SLO"与"对外承诺"。对外可以只承诺可用性 99.9%，内部对延迟、AI 成功率设置更严的目标，留出缓冲。对外承诺一旦写进服务协议，调整成本远高于内部指标，因此对外口径应保守，内部指标应进取。

## 8.2 指标体系

### 8.2.1 技术指标：RED 与 USE

**表 8-3 技术指标清单**

| 方法 | 指标 | 类型 | 关键标签 |
| --- | --- | --- | --- |
| Rate | `http_requests_total` | Counter | `method`、`path`、`status` |
| Errors | `http_requests_total{status=~"5.."}` | Counter 派生 | 同上 |
| Duration | `http_request_duration_seconds_bucket` | Histogram | `method`、`path`、`status` |
| AI 调用 | `ai_calls_total` | Counter | `provider`、`model`、`status` |
| AI 降级 | `ai_degraded_total` | Counter | `reason` |
| AI 延迟 | `ai_call_duration_seconds_bucket` | Histogram | `model` |
| 熔断状态 | `breaker_state` | Gauge | `model`（0 关闭 / 1 半开 / 2 打开） |
| 熔断次数 | `breaker_open_total` | Counter | `model` |
| 配额 | `ai_quota_used` | Counter | 全局 |
| 连接 | `pg_stat_activity_count` | Gauge | `datname`、`state` |
| Utilisation | `node_cpu_seconds_total`、`node_memory_MemAvailable_bytes` | Counter/Gauge | `instance` |
| Saturation | `node_filesystem_avail_bytes`、PG 连接数占比 | Gauge | `instance`、`mountpoint` |

AI 与非 AI 的区分不靠额外标签，而靠路径前缀：AI 请求的 `path` 形如 `/api/v1/ai/intent`，因此非 AI 延迟用 `path!~".*/ai/.*"` 过滤，四条业务链路（intent/persona/score/debrief）也能直接按 `path` 拆分。`model` 标签记录实际使用的模型（含降级后的模型），用于分析"换模型后延迟与质量如何变化"；`status` 标签记录调用结果（ok/failed），与降级次数 `ai_degraded_total` 区分开——降级是"仍成功但回落规则模式"，失败是"没有拿到可用结果"，两者告警阈值不同。

### 8.2.2 业务指标

技术指标正常不代表业务正常。业务指标回答"训练是否真的在被使用、AI 是否真的在给分、危机是否被拦住"。

**表 8-4 业务指标清单**

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| 训练完成率 | `training_completed_total` / `training_started_total` | 判断流程是否卡顿、用户是否中途放弃 |
| AI 降级率 | `ai_degraded_total` / `ai_calls_total` | 供应商可用性与配额水位 |
| 评分分布 | `score_overall` 直方图 | 监测评分是否整体漂移 |
| 六维均分 | 各维度评分均值 | 发现某一维度异常（如共情分骤降） |
| 危机拦截次数 | `crisis_blocked_total` 按级别 | 评估拦截规则是否灵敏、是否误伤 |
| 训练时长分布 | 会话时长直方图 | 判断场景难度与用户投入度 |
| 场景使用分布 | 各场景训练次数 | 内容运营与冷门场景判断 |

技术指标由后端 `app/core/metrics.py` 注册，命名不带服务前缀（服务维度由 `job` 与 `service` 标签区分）；业务指标已按同一风格注册的四个为 `training_started_total{scenario,difficulty}`、`training_completed_total{scenario,difficulty,result}`、`crisis_blocked_total{risk_level,source}`、`score_overall`（0–100 直方图）；训练时长与场景分布的直方图属待补项，未注册前面板显示 N/A，但指标契约先定下来，避免实现时各自起名。

评分漂移采用"周同比 + 阈值"双重判定：本周均分与上周相比偏移超过 0.3 分（5 分制）且样本量超过 100，触发提示；偏移超过 0.5 分触发告警。漂移既可能是模型升级导致，也可能是场景难度调整导致，告警文案要求先看变更记录再判断。

### 8.2.3 指标命名与基数控制

指标命名遵循"对象 + 单位"两段式并统一使用基础单位：`http_request_duration_seconds`、`ai_call_duration_seconds`、`node_filesystem_avail_bytes`。一律用秒、字节、个，不用毫秒与百分比，避免同一系统内单位混用导致聚合错误；百分比在查询侧用除法算出。

基数控制是 Prometheus 使用中最容易踩的坑。禁止把用户 ID、会话 ID、请求 ID 作为标签；`path` 标签必须使用路由模板（`/api/v1/training/{id}`）而非真实路径，否则每个 ID 都会生成一条时间序列；`status` 只保留具体码值（200/401/404/429/500 等），不聚合为笼统的 `4xx`。标签组合的估算上限定为 5 000 条时间序列，超过即需要拆分或降维。直方图桶数量控制在十个左右，桶过密会让 `_bucket` 序列翻倍。

### 8.2.4 指标采集与暴露安全

指标由 prometheus-client 在应用内注册，通过 `/metrics` 暴露为文本格式。该端点是信息资产，不能对公网开放：Nginx 层只允许内网网段访问，K8s 层通过 NetworkPolicy 限制只有 observability 命名空间的 Prometheus 能连 8000 端口，ServiceMonitor 的抓取走集群内地址。

采集链路有三段职责划分。应用负责注册与自增，不做聚合计算；Prometheus 负责抓取、存储与规则评估，抓取间隔 15 秒、超时 10 秒；Grafana 只做查询与展示，不在面板里写复杂正则。职责不清会导致"指标口径在三个地方各写一遍"，最终三方数字对不上。

抓取失败本身也要可观测：`up == 0` 是最基础的信号，另外记录抓取耗时与样本数，抓取耗时接近超时说明应用侧指标量过大或 `collect()` 中有慢操作。多副本部署时，每个 Pod 独立暴露指标并带 `pod` 标签，聚合查询时用 `sum by (route)` 而不是直接对已聚合值求平均，避免副本数变化导致数值漂移。

指标暴露的性能成本需要评估：一次 `/metrics` 请求会序列化全部时间序列，序列数超过一万时单次耗时可达百毫秒级。因此自定义指标控制在一百条以内，直方图桶数量控制在十个左右，避免用高基数标签换"更细的观测"。

## 8.3 日志规范

### 8.3.1 结构化日志字段

日志统一输出 JSON（`LOG_JSON=true`），由 structlog 生成，字段名固定，便于 Loki 查询与告警。

**表 8-5 日志字段规范**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `timestamp` | ISO8601 | 是 | UTC 时间，带毫秒 |
| `level` | string | 是 | debug/info/warning/error/critical |
| `service` | string | 是 | `knock-backend` |
| `env` | string | 是 | dev/staging/prod |
| `version` | string | 是 | 镜像 sha 短标签 |
| `trace_id` | string | 是 | 32 位十六进制，与追踪一致 |
| `span_id` | string | 否 | 当前 span |
| `request_id` | string | 是 | Nginx 生成的请求 ID |
| `user_id` | string | 否 | 已登录时记录，未登录为 null |
| `route` | string | 是 | 路由模板，不含真实 ID |
| `method` | string | 是 | HTTP 方法 |
| `status_code` | int | 是 | 响应码 |
| `duration_ms` | int | 是 | 处理耗时 |
| `event` | string | 是 | 事件名，如 `ai.call.failed` |
| `error_code` | string | 否 | 业务错误码 |
| `error_message` | string | 否 | 脱敏后的错误描述 |

日志中禁止出现：口令与 token、完整手机号与邮箱、对话原文、模型完整 prompt、数据库连接串、内部 IP。需要定位对话问题时，日志只记录 `message_length`、`round_index`、`content_digest` 三项摘要信息。

### 8.3.2 脱敏与采样

脱敏在日志框架层统一完成，而不是依赖每个调用点自觉。实现上给 structlog 挂一个处理器，对已知敏感键名（`password`、`token`、`phone`、`email`、`authorization`）做掩码，对字符串值做正则替换（手机号、邮箱、身份证号），处理器在开发与生产都启用，避免"本地看不到、线上才生效"的差异。

采样按级别区分：`error` 与 `critical` 全量保留；`warning` 全量保留但同一事件 60 秒内去重；`info` 按 10% 采样，但登录、发布、审计相关事件强制全量。采样只作用于日志，不作用于指标与审计表，三者职责不同：指标看趋势、日志看细节、审计看责任。

### 8.3.3 保留期与成本

**表 8-6 日志分层留存**

| 层级 | 内容 | 保留期 | 存储 | 月成本量级 |
| --- | --- | --- | --- | --- |
| 热存 | 全部应用日志，可即时查询 | 7 天 | Loki 本地盘 | 约 60 元 |
| 温存 | error 及以上 + 审计事件 | 30 天 | 对象存储 | 约 30 元 |
| 冷存 | 审计日志归档（WORM） | 3 年 | 对象存储归档型 | 约 15 元 |
| 指标 | Prometheus 时序数据 | 30 天 | 本地盘 | 约 50 元 |
| 追踪 | 采样后的 span | 7 天 | Tempo/对象存储 | 约 40 元 |

成本控制的关键不是压缩保留期，而是减少无价值的日志量。三条措施：访问日志只记录采样后的慢请求与错误请求（Nginx 对 2xx 快速路径采样 1%）；健康检查与指标抓取不打访问日志；重复的堆栈只记录一次并计数。按 100 RPS 估算，全量访问日志每天约 8 GB，采样后可降到 200 MB 量级。

### 8.3.4 日志查询与排障范式

排障时的查询顺序固定为"入口 → 应用 → 依赖"，三步定位问题归属：

第一步在 Nginx 日志中按 `request_id` 或时间窗口查，看请求是否到达、状态码由哪一跳产生、上游耗时多少。若请求根本没到 Nginx，问题在 DNS、WAF 或客户端；若上游耗时占比超过 80%，问题在应用或数据库。第二步用同一个 `trace_id` 查应用日志，确认错误发生在鉴权、业务逻辑还是 AI 调用。第三步按 `event` 字段查依赖相关事件，如 `db.pool.timeout`、`ai.call.failed`，确认是连接池、慢查询还是供应商。

Loki 查询以标签选择器缩小范围，再用 `|=` 做文本过滤，例如先按 `service`、`level`、`route` 三个标签定位，再匹配错误码。避免用大范围时间窗口加宽泛文本过滤，那会在数百万行中扫描，查询必然超时。高频查询可以固化为"已保存查询"，值班人直接点选，减少临场拼写错误。

日志与指标的分工要清晰：指标回答"有多少、是否越界"，日志回答"是哪一条、发生了什么"。当告警指出 5xx 率升高时，不要试图在指标里找具体请求，直接带着时间窗口去日志中捞错误，再用 `trace_id` 还原完整调用链。这一条路径是值班人最常用的，应写进值班手册并定期演练。

## 8.4 分布式追踪

### 8.4.1 Span 设计

追踪采用 OpenTelemetry SDK，通过 OTLP 上报到 Collector，采样策略为"错误全采 + 正常 10% 采样 + 慢请求全采"。一次 AI 对话请求的 span 树如下。

```text
http.server  POST /api/v1/ai/chat                [根 span]
├── auth.verify                                  鉴权
├── rate_limit.check                             限流与配额
├── db.query  select training_session            读会话
├── ai.call   glm-4.7-flash                      AI 调用
│   ├── ai.cache.lookup                          缓存查询
│   ├── http.client  POST open.bigmodel.cn      供应商请求
│   └── ai.validate                               输出结构校验
├── db.query  insert message
└── audit.write  ai_audit_log
```

span 命名采用"对象.动作"格式，不用自然语言描述；`http.server` 与 `http.client` 使用语义约定命名，便于自动生成依赖拓扑。每个 span 必须带 `service.name`、`deployment.environment`、`service.version` 三个资源属性。

### 8.4.2 `ai.call` 子 span 属性

**表 8-7 ai.call span 属性**

| 属性 | 类型 | 说明 |
| --- | --- | --- |
| `ai.fn` | string | intent/persona/score/debrief |
| `ai.model` | string | 实际调用的模型名 |
| `ai.fallback_used` | bool | 是否发生模型降级 |
| `ai.cache_hit` | bool | 是否命中缓存 |
| `ai.prompt_tokens` | int | 输入 token 数（供应商返回） |
| `ai.completion_tokens` | int | 输出 token 数 |
| `ai.latency_ms` | int | 供应商侧耗时 |
| `ai.outcome` | string | ok/degraded/failed/blocked |
| `ai.retry_count` | int | 重试次数 |
| `ai.breaker_state` | string | 调用时熔断器状态 |
| `ai.quota_remaining` | int | 调用后剩余配额 |

属性中不含 prompt 与响应正文，避免追踪系统成为新的数据泄露面。需要还原具体内容时，用 `trace_id` 关联审计表与业务表，按权限取原文。

### 8.4.3 上下文传播

上下文传播采用 W3C Trace Context 标准（`traceparent` + `tracestate`），三跳的传递方式各不相同：

Nginx 作为入口生成 `X-Request-ID`（用于日志关联），并透传上游传入的 `traceparent`；若客户端未带，则由应用侧生成根 span。应用侧从请求头提取上下文，创建 `http.server` span，HTTP 客户端调用智谱时自动注入 `traceparent` 到出站请求。供应商不返回追踪头，因此 `http.client` span 的结束时间即 AI 调用耗时，无法细分供应商内部阶段，这是外部依赖的固有盲区。

跨进程传播要防止头污染：入站请求中的 `traceparent` 只信任来自 Ingress 的请求，公网直连场景（预发直连 Pod）由应用强制重新生成，避免攻击者伪造 trace ID 污染链路数据。采样决策在入口一次确定，通过 `tracestate` 透传，避免各层重复采样导致链路断裂。

### 8.4.4 采样策略与存储成本

追踪的数据量远大于指标，必须采样。三档策略组合使用：错误请求全量采集（`status_code >= 500` 或 `ai.outcome != ok`），慢请求全量采集（超过对应 SLO 阈值），正常请求按 10% 概率采样。采样决策在根 span 生成时完成一次，通过 `traceparent` 的 sampled 标志向上下游传播，保证同一条链路要么全采要么全不采。

成本估算：按 100 RPS、每请求 8 个 span 计算，全量约 6.9 亿 span/天，不可接受；10% 采样后约 6 900 万 span/天，压缩后每天约 3–5 GB，保留 7 天需要 25–35 GB 存储，符合表 8-6 的成本量级。若某段时间错误率突增，采样率可临时调到 100% 以便定位，处置完成后调回，这类临时调整必须记录在故障单中。

追踪数据不做长期留存，因为它的价值集中在"最近一次故障的还原"。需要长期保留的是审计记录与关键业务指标，追踪在复盘结束后即可过期。三个数据源的保留期不同，设计上要允许独立配置，避免用一个全局参数把三者绑死。

## 8.5 告警

### 8.5.1 分级与阈值

告警分级依据"用户影响 × 紧急程度"，P0 必须 5 分钟内响应，P3 可次日处理。阈值与生产规则文件一一对应。

**表 8-8 告警分级与阈值**

| 级别 | 告警 | 触发条件 | 持续 | 响应时限 |
| --- | --- | --- | --- | --- |
| P0 | API 不可用 | `up == 0` | 2 分钟 | 5 分钟 |
| P0 | 证书即将过期 | 剩余 < 3 天 | 30 分钟 | 30 分钟 |
| P1 | 5xx 率过高 | > 0.5% | 5 分钟 | 15 分钟 |
| P1 | 熔断器打开 | `max(breaker_state) == 2` | 2 分钟 | 15 分钟 |
| P1 | 磁盘不足 | 可用 < 15% | 10 分钟 | 30 分钟 |
| P2 | 非 AI P95 超标 | > 300 ms | 10 分钟 | 1 小时 |
| P2 | AI P95 超标 | > 6 s | 10 分钟 | 1 小时 |
| P2 | AI 降级率过高 | > 5% | 10 分钟 | 1 小时 |
| P2 | 配额接近上限 | 已用 > 720 次（90%） | 5 分钟 | 1 小时 |
| P2 | 连接接近上限 | PG 连接占 `max_connections` > 85% | 5 分钟 | 1 小时 |
| P2 | 证书 14 天内到期 | 剩余 < 14 天 | 1 小时 | 当日 |
| P3 | 错误预算燃烧 | 1 小时 5xx > 0.05% | 1 小时 | 次日 |

### 8.5.2 抑制与静默

告警抑制（inhibition）解决"一个故障触发一片告警"的问题：`KnockApiDown` 触发时抑制同一实例的 5xx 率、延迟、连接池告警；数据库主库故障时抑制依赖它的 API 告警；发布窗口内抑制 `KnockApiDown` 与 5xx 告警，但保留 AI 质量类告警。

静默（silence）用于计划内维护：发布、迁移、压测、演练前创建带到期时间的静默规则，必须写明原因与工单号，最长 4 小时，到期自动失效。禁止无限期静默，禁止对 P0 告警创建静默——P0 是"用户已经在受影响"，不允许被掩盖。

### 8.5.3 值班与升级

单人或小团队场景下不设 7×24 轮班，采用"分级响应 + 自动升级"：P0/P1 触发后先短信与电话通知值班人，5 分钟未确认自动升级到第二联系人，15 分钟未确认升级到项目负责人。P2 走即时通讯群提醒，工作时间响应。P3 汇总到日报。

值班表按周排班，交接时同步三件事：未闭环的告警、进行中的变更、近期的容量与配额水位。告警处理后必须在系统中标记处置结论（真故障/误报/已抑制），误报率超过 20% 的规则需要调整阈值或增加 `for` 时长，否则值班人会逐渐忽略告警，这是告警系统失效的最常见原因。

### 8.5.4 通知渠道与告警文案

通知渠道按级别路由：P0 走电话与短信，同时推送到即时通讯群的"紧急"频道；P1 走短信与群消息；P2 只走群消息；P3 汇总到每日晨报。渠道不在告警规则里写死，而由 Alertmanager 的路由树按 `severity` 标签分派，规则只负责判断"是否异常"，路由负责"通知谁"。

告警文案必须包含四要素：是什么（`summary`）、影响谁（`description` 中的用户视角描述）、现在该做什么（`runbook` 链接指向本章对应小节）、怎么算正常（恢复条件）。禁止只写"错误率过高"这类没有行动指向的文案——值班人看到后仍要重新排查一遍，告警就失去了节省时间的意义。

同一次故障可能触发多条告警，文案中应带 `instance`、`route` 等定位标签，并在描述中说明"这是同一故障的第二条"，避免值班人重复处置。故障结束后，告警应自动恢复（`resolved` 通知），恢复通知同样需要文案，说明恢复正常的时间点，便于事后统计 MTTR。

## 8.6 仪表盘

仪表盘按"先看结论、再看细节、最后看依赖"的顺序组织，共四张面板组，对应 `grafana/dashboard.json` 的十个 panel。

### 8.6.1 面板一：服务总览

面向值班人，一眼判断"现在是否正常"。包含四个 panel：可用性 SLI 单值（30 天滚动）、请求速率曲线（按 status 分组）、错误预算剩余、当前版本与副本数。

布局上把可用性放在左上角最大区块，因为它是最直观的结论；错误预算放在右上角，用颜色区分绿/黄/红三档（< 10% 绿、10%–50% 黄、> 50% 红）。该面板不放下钻链接，保持信息密度低，避免值班时被细节干扰。

### 8.6.2 面板二：延迟分析

包含三个 panel：非 AI 请求 P50/P95/P99 曲线、AI 请求 P95（按 `model` 分组）、延迟热力图（按分钟桶）。

延迟面板的价值在于区分"整体变慢"与"长尾变慢"。P50 稳定而 P99 抬升，通常是下游抖动或连接池排队；三条线同时抬升，通常是资源不足或流量突增。AI 按 `model` 分组能看出降级模型是否在拖慢整体，按 `path` 拆分能定位是评分链路还是对话链路变慢，两者的优化手段完全不同。

### 8.6.3 面板三：依赖与容量

包含两个 panel：PG 连接数占 `max_connections` 比例与 `pg_stat_activity_count` 明细、磁盘与证书状态表。

依赖面板回答"是不是外部组件导致的"。连接数占比持续高于 85% 说明应用侧连接需求已接近数据库上限，需要先查慢查询与长事务，再考虑调池或接入 PgBouncer；`pg_stat_activity_count` 按 `state` 分组，`idle in transaction` 数量异常升高通常意味着应用有未提交事务。SQLAlchemy 连接池的 `pool_in_use` 属于进程内状态，当前版本未导出为指标，排障时以 PG 侧连接数为主、进程日志为辅；若要观测池等待，需在二期补 `db_pool_*` 指标。证书状态用表格展示剩余天数，低于 14 天标黄、低于 3 天标红。

### 8.6.4 面板四：AI 与业务

包含四个 panel：AI 结果分布（按 `status` 堆叠 + 降级率曲线）、熔断器状态（0 关闭 / 1 半开 / 2 打开）、AI 日配额已用与剩余、业务指标（训练完成率、危机拦截次数、六维均分）。

熔断器状态用离散值展示而非折线，因为它是状态机而不是连续量；配额用"已用次数 / 上限 800"换算成百分比，剩余低于 10% 变色。业务指标放最后，是因为它们变化慢，但一旦异常往往意味着产品层面出了问题，需要在值班交接时主动查看。

### 8.6.5 从面板到排障的路径

四组面板不是孤立的图表集合，而是四条排障路径的入口：

第一条"是否影响用户"：从总览页的可用性与错误预算出发，判断是否需要立刻处置。若可用性正常但错误预算在快速消耗，说明影响面小但持续，按 P2 处理。

第二条"慢在哪一跳"：从延迟面板切到追踪，用 `duration` 排序找最慢的 20 条链路，看时间消耗在 `db.query` 还是 `ai.call`。若消耗在 `db.query`，切到依赖面板看连接池与活跃连接；若消耗在 `ai.call`，切到 AI 面板看模型与降级比例。

第三条"依赖是否健康"：依赖面板上的连接池、磁盘、证书三个信号，对应三类完全不同的处置。连接池高看慢查询，磁盘低看日志与镜像，证书临近看签发流程。

第四条"业务是否正常"：AI 与业务面板的变化通常先于技术指标的异常。例如六维均分整体下降但延迟正常，可能是模型侧输出质量变化；训练完成率下降但请求量正常，可能是前端流程或场景内容问题。这类问题不会触发技术告警，需要业务面板主动观察。

面板需要定期维护：新增指标后要同步进面板，废弃指标要从查询里删掉（否则面板出现空图），每次发布后核对发布注解是否随 Pod 重启出现（注解基于 `process_start_time_seconds` 变化）。面板长期不维护会逐渐失去可信度，值班人会转回手工查日志。

## 8.7 故障预案 Runbook

每个场景固定四段：识别信号 → 5 步内处置 → 验证 → 复盘。处置步骤要求"5 步内"是为了防止预案写成无法执行的长文，真正的应急需要肌肉记忆。

### 8.7.1 智谱 API 不可用

识别信号：`ai_calls_total{status="failed"}` 突增、`max(breaker_state) == 2`（熔断打开）、AI P95 超 6 s、日志出现供应商超时。

处置步骤：

1. 确认范围：查看 AI 结果分布，若 `degraded` 上升且请求仍有返回，说明降级已生效，服务未中断。
2. 检查配额：`ai_quota_used` 是否已达 800，若已达则是配额耗尽而非供应商故障，立即联系管理员加额。
3. 切换模型：将 `GLM_MODEL` 指向备用模型（`glm-4.5-flash`），滚动重启，观察 5 分钟。配置在 ConfigMap 中修改后需 `rollout restart` 才生效。
4. 若供应商整体不可用：保持降级模式，前端显示"当前为规则评分"，同时关闭 AI 相关非关键功能入口。
5. 通知：在状态页与用户群公告"AI 评分暂时降级，训练记录不受影响"。

验证：`ai_calls_total{status="ok"}` 占比恢复至 95% 以上、`breaker_state` 回到 0、AI P95 回到 6 s 以内。复盘：确认是配额、网络还是供应商侧故障，评估是否需要提高备用模型权重或增加配额预警阈值。

### 8.7.2 数据库主库故障

识别信号：`/readyz` 返回 503、5xx 率骤升、连接池使用率打满、`pg_stat_activity_count` 异常、日志出现连接超时。

处置步骤：

1. 确认主备状态：登录云控制台查看 RDS 主备实例状态与切换记录，判断是否已自动切换。
2. 若未自动切换：手动触发主备切换（华为云 RDS 支持控制台操作），记录切换开始时间。
3. 应用侧等待重连：连接池配置了重试，通常 30–60 秒内恢复；若 2 分钟未恢复，滚动重启 API 以重建连接。
4. 校验数据：切换后检查最近 5 分钟的写入是否完整，重点看训练记录与审计日志是否有缺口。
5. 恢复写入前先确认只读副本的复制延迟已归零，避免旧主恢复后产生双写。

验证：`/readyz` 返回 200、5xx 率回到基线、写入新记录成功、复制延迟小于 1 秒。复盘：切换耗时是否在 RTO 内、是否需要调整连接池重试参数、主库故障根因（磁盘、内存、连接数）。

### 8.7.3 Redis 故障

识别信号：限流计数异常（大量 429 或完全不限流）、缓存命中率骤降、日志出现 Redis 连接错误。

处置步骤：

1. 判断影响面：Redis 承载限流、配额、缓存、撤销黑名单，故障时后端会退回进程内实现，功能可用但限流不再全局生效。
2. 若仅主节点故障且哨兵/集群可自动切换：等待 30 秒观察是否恢复，不急于重启应用。
3. 若彻底不可用：确认后端已进入进程内降级模式，检查 `RATE_LIMIT_ENABLED` 行为是否符合预期。
4. 临时收口：在 Nginx 层把限流阈值调严（如 20 r/s），弥补应用层限流失效。
5. 恢复后重建：清除进程内计数，避免与 Redis 计数叠加造成误限流。

验证：限流返回 429 的行为恢复正常、缓存命中率回升、撤销黑名单生效（用已撤销 token 测试返回 401）。复盘：评估关键限流是否应改为"Redis 不可用则拒绝"而不是"退回本地"，这涉及可用性与安全性的取舍，需要书面确认。

### 8.7.4 磁盘空间不足

识别信号：`node_filesystem_avail_bytes` 低于 15%、日志写入报错、数据库写入失败。

处置步骤：

1. 定位占用：`du -sh` 逐层排查，优先查日志目录、容器临时目录、Prometheus 数据目录。
2. 清理日志：删除 7 天前的归档日志，压缩大文件；若 Loki 配置的保留期未生效，先手动清理。
3. 清理镜像：`docker image prune -a` 或 K8s 侧清理未使用的镜像层。
4. 清理临时文件：检查 `/tmp` 与上传暂存目录，确认无长期未清理的导出包。
5. 扩容：若清理后仍低于 20%，扩容磁盘或迁移数据目录，扩容优先于继续清理。

验证：可用空间回到 30% 以上、日志与指标写入正常、数据库可写入。复盘：确认磁盘告警是否提前触发（10 分钟 `for` 是否足够）、日志轮转策略是否失效、是否需要把访问日志采样率进一步降低。

### 8.7.5 证书过期

识别信号：`probe_ssl_earliest_cert_expiry` 剩余天数低于 14 天、浏览器出现证书告警、外部探针失败。

处置步骤：

1. 确认证书对象：`kubectl describe certificate knock-prod-tls` 查看签发状态与事件。
2. 检查挑战：若卡在 ACME 挑战，确认 `/.well-known/acme-challenge/` 未被 WAF 拦截、DNS 解析正确。
3. 手动续签：删除 Certificate 资源让 cert-manager 重新签发，或使用 `cmctl renew` 触发。
4. 核对 Secret：确认 `knock-prod-tls` 已更新，Ingress 已加载新证书（`kubectl describe ingress` 看 events）。
5. 若自动签发持续失败：临时上传备用证书，保证服务可用，再排查根因。

验证：`curl -vI https://api.knock.example.com` 显示新证书有效期、`probe_ssl_earliest_cert_expiry` 回到 60 天以上。复盘：ACME 失败原因、是否需要改为 DNS-01 挑战、监控阈值是否应提前到 21 天。

### 8.7.6 发布回滚

识别信号：灰度阶段出现 P1 告警、5xx 率超 1%、AI 降级率异常、核心链路冒烟失败。

处置步骤：

1. 立即停止灰度推进，不再扩大新版本流量。
2. 执行 `kubectl rollout undo deployment/knock-api`，观察滚动完成。
3. 若涉及数据库迁移：评估是否可向下迁移，先停写再降级，禁止直接回滚应用。
4. 验证核心链路：`/healthz`、`/readyz`、登录、训练、评分、导出五条。
5. 通报：在变更单记录回滚原因、时间、影响范围，通知相关干系人。

验证：所有 Pod 回到上一版本镜像、指标回到发布前基线、错误预算停止消耗。复盘：回滚触发条件是否被提前发现、灰度窗口是否足够、是否有可自动化的回滚判定。

### 8.7.7 演练机制与故障注入

预案写出来不等于能执行。每个季度至少做一次桌面演练（不操作真实环境，按预案口述处置步骤并计时）和一次实操演练（在预发环境注入真实故障）。实操演练选低风险场景，如停止 Redis 容器、让证书过期、制造磁盘不足，观察监控是否按预期告警、预案步骤是否可执行、恢复是否在 RTO 内。

演练要记录四项数据：从故障注入到告警触发的时间（检测时长）、从告警触发到开始处置的时间（响应时长）、处置总时长、是否触发未预料的连带故障。四项数据与 RTO 对比，差距即改进点。若检测时长超过 2 分钟，说明监控粒度不够；若响应时长超过 10 分钟，说明告警通知渠道或值班安排有问题。

故障注入必须可控：提前创建静默窗口、限定影响范围、准备好回退开关、通知相关人员。禁止在生产环境做未通报的故障注入，也禁止在演练中放过"临时绕过监控"这类动作——演练的目标是验证真实路径，而不是证明"如果有人一直盯着就不会出事"。

## 8.8 容量与性能巡检

### 8.8.1 巡检清单

**表 8-9 每周巡检清单**

| 项 | 检查内容 | 判定标准 |
| --- | --- | --- |
| 容量水位 | CPU、内存、磁盘的 P95 使用率 | 均低于 70% |
| 连接数 | PG 连接数占比、活跃与空闲连接 | 低于 80% |
| 慢查询 | Top 10 慢查询 | 无新增超过 500 ms 的查询 |

### 8.8.3 容量模型与扩容决策

容量按"目标规模 → 单实例能力 → 冗余系数"三段推算。目标峰值 100 RPS、500 并发在线；单 Pod（2 vCPU、1 GB）在非 AI 路径上可稳定承载约 40 RPS，AI 路径因外部依赖耗时不按 QPS 折算而按并发占用折算，单 Pod 的 AI 并发上限受 `GLM_CONCURRENCY=2` 约束。换算到 3 副本，非 AI 能力约 120 RPS，已覆盖 100 RPS 峰值并留有 20% 余量；AI 侧全局并发 6，与既有设计一致。

扩容判定看三个信号，缺一不可：CPU 使用率持续 10 分钟高于 70%、非 AI P95 超过 300 ms、每副本请求速率接近单实例能力上限的 80%。只看 CPU 会误判（AI 场景下 CPU 不高但连接被占满），只看延迟会误判（下游抖动也会抬高延迟），三者同时越界才说明是自身容量不足。

缩容比扩容更保守：缩容延迟 5 分钟、每次最多减少 25%、且保证至少留 2 个副本。缩容过快会导致连接被中断、缓存冷启动，用户侧表现为短暂的错误率尖峰。压测数据表明，从 4 副本缩到 3 副本时 P95 变化在 20 ms 以内，属于可接受范围；一次缩到 1 个副本则会出现明显的排队。

存储容量的增长按每年 100 万条训练记录推算：单条记录（含会话消息、六维评分、审计摘要）平均约 6 KB，年增量约 6 GB，加上索引与 WAL 约 9 GB。按三年规划预留 30 GB 业务库空间，加上备份副本与临时空间，单实例 100 GB 起步即可，扩容以 50 GB 为步长。

## 8.9 本章小结

- 四类 SLI 对应可用性、非 AI 延迟、AI 延迟与错误率，错误预算按 30 天滚动计算并驱动发布节奏。
- 指标分技术与业务两层，AI 指标必须按 `provider`、`model`、`status` 打标签，同时严格控制系统序列基数。
- 日志以 JSON 固定字段、框架层脱敏、分级采样与分层留存控制成本，禁止记录对话原文与凭据。
- 追踪采用 W3C 标准传播，`ai.call` span 记录模型、降级、缓存、token 与熔断状态，不记录正文。
- 告警分 P0–P3 四级，配合抑制、静默与自动升级，误报率超过 20% 必须调参。
- 六类故障预案统一为"识别信号 → 5 步处置 → 验证 → 复盘"，季度演练验证可执行性。
- 巡检按周与月两层执行，压测以 100 RPS 稳态与 200 RPS 突增为验收场景。
