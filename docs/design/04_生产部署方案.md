# 第4章 生产部署方案

本章给出「叩门·社工个案面谈 AI 陪练舱」从课程作品走向生产环境的完整部署方案。方案以「答辩现场可离线运行、院系上线可弹性扩展」为双目标，采用单机 Docker Compose 起步、华为云 CCE 收口的两阶段形态，并把安全、可观测、备份等生产必需项在阶段一即固化，避免后期返工。所有配置以可解析的制品形式存放在 `deliverables/deploy/`，正文只摘录关键片段。

## 4.1 环境规划

### 4.1.1 三套环境的定位与隔离

环境划分的目的不是"多建几套机器"，而是把变更风险挡在生产之外。三套环境在账号、网络、数据、密钥四个维度完全隔离：不共享数据库、不共享对象存储桶、不共享密钥，也不允许从开发环境直连生产数据库。

**表 4-1 三套环境对照**

| 维度 | 开发（dev） | 预发（staging） | 生产（prod） |
| --- | --- | --- | --- |
| 用途 | 本地编码、联调、单测 | 发布前验收、压测、演练 | 院系试用与正式服务 |
| 部署形态 | 单机 Compose 或直接 uvicorn | 单机 Compose 全栈 | 华为云 CCE 集群 |
| 网络隔离 | 本机回环，仅放行 8000/5173 | 独立 VPC 子网，白名单入口 | 独立 VPC，公网仅经 WAF/ELB |
| 数据库 | 本地 PG16 容器，可随时重建 | 独立 RDS 实例，结构与生产同版 | RDS 主备 + 只读副本 |
| 数据来源 | 造数脚本 + 脱敏样本 | 脱敏后的生产快照 | 真实数据 |
| 密钥 | `.env` 本地文件，假密钥占位 | KMS 测试密钥，与生产不同 | KMS 生产密钥，季度轮换 |
| 域名 | localhost | staging.knock.example.com | api./www./admin.knock.example.com |
| 规模 | 单副本 | 2 副本，1/10 流量 | 3–12 副本，500 在线 / 100 RPS |
| 可观测 | 控制台日志 | 全量指标 + 告警静默 | 全量指标、日志、追踪、告警 |

环境中立性的关键在配置：同一份镜像通过环境变量区分行为，禁止为环境打不同镜像。`APP_ENV` 是唯一的环境开关，其取值直接影响 `DEBUG`、`AUTO_CREATE_SCHEMA`、`SEED_SCENARIOS_ON_STARTUP` 三个高危项的默认值。生产环境必须同时满足 `APP_ENV=prod`、`DEBUG=false`、`AUTO_CREATE_SCHEMA=false`，且在启动时由应用自检打印告警，任一违反即拒绝启动。

### 4.1.2 数据脱敏规则

预发环境使用生产快照可以暴露真实的数据分布问题，但必须先脱敏。脱敏在导出侧完成，而不是在预发侧清洗，避免原始数据落地到低安全等级环境。

**表 4-2 预发数据脱敏规则**

| 数据类别 | 字段示例 | 脱敏方式 | 保留特征 |
| --- | --- | --- | --- |
| 账号标识 | 用户名、邮箱 | 保留首字符 + 固定占位，如 `zh***@example.com` | 长度与域名结构 |
| 手机号 | `phone` | 中间四位掩码 `138****5678` | 号段与前三位 |
| 口令哈希 | `password_hash` | 统一替换为固定 Argon2id 哈希 | 校验流程可跑通 |
| 对话正文 | `message.content` | 按句子随机替换词表，保留标点与长度分布 | 文本长度与轮次 |
| 训练评分 | `score_*` 六维分 | 保留数值，打乱与用户/场景的对应关系 | 分布形态 |
| 危机标记 | `crisis_flag`、`crisis_level` | 保留标记，内容替换为合成文本 | 拦截链路可验证 |
| 审计日志 | `ai_audit_log` | 仅保留最近 7 天，其余按规则裁剪 | 字段结构 |

脱敏脚本纳入版本管理并随迁移一起评审；每次刷新预发数据需记录快照时间、脱敏版本、执行人。开发环境的造数脚本生成 5 万账号量级的合成数据，用于验证分页、索引与统计口径，不使用任何真实记录。

脱敏不是一次性动作，而是数据生命周期的常态。数据按敏感度分为四级：公开级（场景描述、评分维度说明）、内部级（用户名、班级、训练轮次）、敏感级（手机号、对话正文、危机标记）、高敏级（审计日志中的个人信息片段）。预发环境只允许出现前三级，且敏感级必须脱敏；生产环境的敏感级数据在应用层做字段级加密，导出时按最小必要原则裁剪。数据留存按用途区分：训练记录与评分在账号存续期内保留，审计日志固定留存 180 天，临时上传文件 7 天自动清理，日志中的对话正文只保留摘要。

脱敏效果需要抽样校验，而非抽样检查脚本。每批快照导入后随机抽取 200 条记录，用正则扫描手机号、身份证号、邮箱三类模式，命中即判定脱敏失败并回退该批数据；同时比对脱敏前后的字段分布（长度、取值区间），防止脱敏把数据"洗平"导致统计测试失真。

## 4.2 部署拓扑

生产拓扑自上而下分为接入、应用、数据、外部依赖与可观测五个平面，如图 4-1 所示。

![图 4-1 生产部署拓扑](figures/fig-03-deploy-topology.png)

### 4.2.1 流量路径

一次面谈请求的完整链路为：浏览器 → CDN → WAF → Nginx Ingress → API Pod → PgBouncer → PG 主库 / Redis → 智谱 API。每一跳都承担明确职责，任一跳都可独立限流与观测。

**表 4-3 请求逐跳职责**

| 跳次 | 组件 | 职责 | 协议/端口 | 超时 |
| --- | --- | --- | --- | --- |
| 1 | DNS/CDN | 静态资源分发、边缘缓存 | HTTPS/443 | — |
| 2 | WAF | OWASP 规则、CC 防护、IP 封禁 | HTTPS/443 | 10 s |
| 3 | Nginx Ingress | TLS 终止、限流、路由、真实 IP 透传 | HTTPS/443 → HTTP/8000 | 60 s |
| 4 | API Pod | 鉴权、校验、业务编排、AI 网关 | HTTP/8000 | — |
| 5 | PgBouncer | 连接复用，事务级池 | TCP/6432 | 5 s |
| 6 | PG16 主备 | 事务写入、只读副本分流 | TCP/5432 | 30 s |
| 7 | Redis7 | 限流计数、并发信号量、配额、缓存 | TCP/6379 | 1 s |
| 8 | 智谱 API | 大模型推理 | HTTPS/443 | 45 s |

AI 链路的超时预算按"外到内递减"设计：前端 `60 s` 为总预算，网关 `45 s` 为单次模型调用上限，Nginx `60 s` 为读超时上限，PG `30 s` 为语句超时。任一层先超时都不会拖垮上层，降级路径（规则引擎兜底评分）在网关超时后立即接管。

### 4.2.2 信任边界与故障域

系统划为四个信任边界：公网边界（WAF/Ingress）、应用边界（Pod 网络策略）、数据边界（数据库子网，仅 PgBouncer 与运维跳板可达）、外部依赖边界（出站仅 443，白名单域名）。故障域按"单 Pod → 单节点 → 单可用区 → 单 Region"四级设计：Pod 故障由副本与 PDB 吸收；节点故障由反亲和与拓扑分布吸收；可用区故障由跨 AZ 的 3 副本与 RDS 主备吸收；Region 故障由异地 OBS 备份与冷备手册覆盖，对应第 4.9 节的 RTO 1 小时目标。

可用性目标需要换算成可执行的冗余量。99.9% 的年可用性对应全年不可用 8 小时 45 分钟，按月约 43 分钟，按周约 10 分钟。这个预算意味着：不允许每月出现两次各 20 分钟以上的全站故障，也不允许把"单副本故障重建"当作可接受的日常事件。据此设定三条硬约束——任一时刻至少有 2 个 API 副本处于 Ready；任一可用区故障后剩余副本仍能承接 100 RPS；数据库主备切换必须在一分钟内完成。前两条由副本数与拓扑分布保证，第三条由 RDS 高可用与连接重试保证。

单点故障的排查标准是"能否在不发版、不人工介入的情况下自动恢复"。按此标准，Nginx Ingress 多副本、API 多副本、数据库主备、Redis 主备均满足；PgBouncer 与 Prometheus 是已知单点，前者通过多实例 + 客户端重试缓解，后者属于可观测设施，允许在故障期间丢失监控但必须有独立的告警通道兜底。任何新增组件都必须先回答这个问题再进入架构。

## 4.3 容器化

### 4.3.1 多阶段构建与体积预算

镜像采用两阶段构建：builder 阶段安装编译工具链与 Python 依赖，runtime 阶段只拷贝虚拟环境与源码。首行使用固定 digest 的基础镜像，避免 `latest` 漂移。

```dockerfile
FROM python:3.12-slim AS builder
WORKDIR /build
RUN apt-get update && apt-get install -y --no-install-recommends build-essential \
    && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.12-slim AS runtime
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
RUN groupadd -g 10001 app && useradd -u 10001 -g app -m -s /usr/sbin/nologin app
COPY --from=builder /install /usr/local
WORKDIR /app
COPY --chown=10001:10001 app ./app
COPY --chown=10001:10001 alembic ./alembic
USER 10001:10001
EXPOSE 8000
HEALTHCHECK --interval=15s --timeout=3s --retries=3 \
  CMD python -c "import urllib.request;urllib.request.urlopen('http://127.0.0.1:8000/healthz')"
CMD ["gunicorn","-k","uvicorn.workers.UvicornWorker","-w","4","-b","0.0.0.0:8000","app.main:app"]
```

**表 4-4 镜像分层体积预算**

| 层 | 内容 | 预算 |
| --- | --- | --- |
| 基础层 | python:3.12-slim | 约 130 MB |
| 依赖层 | FastAPI、SQLAlchemy、asyncpg、uvicorn、gunicorn 等 | 约 55 MB |
| 应用层 | `app/`、`alembic/`、启动脚本 | 约 6 MB |
| 合计 | 压缩后推送体积 | 目标 < 250 MB，实测约 200 MB |

体积控制的三条约束：不在 runtime 阶段保留 `build-essential`；不安装 pytest、ruff 等开发依赖；构建产物只保留 `app/` 与迁移目录，`tests/`、`.git/`、缓存目录通过 `.dockerignore` 排除。体积直接影响冷启动与拉取时间，Pod 冷启动需控制在 30 s 以内，镜像拉取占其中约 10 s。

### 4.3.2 运行期加固

容器运行期按最小权限原则收敛，配置逐项落到 Compose 与 K8s 两套制品中。

**表 4-5 容器安全基线**

| 项 | 配置 | 目的 |
| --- | --- | --- |
| 运行用户 | `runAsUser: 10001`、`runAsNonRoot: true` | 逃逸后无 root 能力 |
| 根文件系统 | `readOnlyRootFilesystem: true` | 阻断落地 webshell |
| 可写目录 | `/tmp` 挂 tmpfs/emptyDir（64 MB，内存介质） | 满足 Python 临时文件需求 |
| 能力集 | `capabilities.drop: ["ALL"]` | 移除全部 Linux 能力 |
| 提权 | `allowPrivilegeEscalation: false` | 禁止 setuid 提权 |
| 主机命名空间 | 不开启 hostNetwork/hostPID/hostIPC | 隔离网络与进程视图 |
| 服务账号 | `automountServiceAccountToken: false` | 应用不需要访问 API Server |
| seccomp | `RuntimeDefault` | 削减危险系统调用 |

只读根文件系统的常见阻碍是 Python 的字节码缓存与临时目录。前者用 `PYTHONDONTWRITEBYTECODE=1` 关闭，后者把 `TMPDIR` 指向内存盘，`/tmp` 容量上限 64 MB 足以覆盖依赖拉取与报告导出临时文件；若导出链路需要更大空间，改为流式写对象存储而非落地本地。

### 4.3.3 构建缓存与依赖锁定

构建使用 Buildx 与 GitHub Actions 缓存后端（`type=gha`），首次构建约 3 分钟，命中缓存后约 40 s。依赖锁定采用 `requirements.txt` 全量钉版本 + 哈希校验（`--require-hashes`），或在 CI 中生成 `uv.lock` 并校验未漂移。基础镜像每月重新评估一次，安全补丁版本随时更新并重跑流水线；基础镜像 digest 变更属于变更事件，需走预发验证。

供应链环节补三道检查：依赖完整性在构建时用哈希校验，防止仓库被投毒；镜像签名用 cosign 做 keyless 签名，集群侧配置准入策略只允许拉取已签名镜像；SBOM 由 Buildx 在构建时生成并随镜像归档，出现新的高危漏洞时能反查受影响的镜像版本。三道检查的成本很低，但能在"依赖被篡改"这类低频高危事件上提供确定性证据。

镜像标签策略为"sha 短哈希 + 语义版本"双标签：部署清单只引用 sha 标签，语义版本标签供人阅读。禁止在部署清单里使用 `latest`，也禁止同一 tag 被重复推送覆盖，否则回滚时无法定位到底回滚到了哪份代码。

## 4.4 编排

### 4.4.1 阶段一：单机 Docker Compose 全栈

答辩与试运行阶段以单机 Compose 承载全栈，一条命令拉起九个服务，不依赖公网资源。Compose 的定位是"可离线演示的生产降级形态"，因此同样要求健康检查、资源上限、只读挂载与日志滚动。

**表 4-6 Compose 服务与资源**

| 服务 | 镜像 | 端口（仅本地暴露） | 资源上限 | 健康检查 |
| --- | --- | --- | --- | --- |
| api | 本地构建 `knock-api:1.0.0` | 内部 8000 | 2 CPU / 1 GB | `/readyz` |
| postgres | postgres:16.4-alpine | 内部 5432 | 2 CPU / 2 GB | `pg_isready` |
| redis | redis:7.2.5-alpine | 内部 6379 | 1 CPU / 512 MB | `redis-cli ping` |
| nginx | nginx:1.27-alpine | 80/443 → 8080/8443 | 1 CPU / 256 MB | `/nginx-health` |
| prometheus | prometheus:v2.53.2 | 127.0.0.1:9090 | 1 CPU / 1 GB | `/-/healthy` |
| grafana | grafana:11.1.5 | 127.0.0.1:3000 | 0.5 CPU / 512 MB | `/api/health` |
| loki | grafana/loki:3.1.0 | 内部 3100 | 0.5 CPU / 512 MB | `/ready` |
| 三个 exporter | postgres/redis/node-exporter | 内部 9187/9121/9100 | 各 0.1 CPU / 64 MB | 端口探测 |

Compose 的两条网络：`edge` 承载外部可达路径，`data` 为 `internal: true` 的内部网络，数据库与 Redis 只挂在 `data` 上，从网络层阻断外网直连。日志统一用 json-file 驱动并限制 `max-size=10m`、`max-file=3`，防止磁盘被日志写满。

### 4.4.2 阶段二：华为云 CCE 对象清单

集群阶段用 12 个清单对象覆盖运行所需最小集合，全部位于 `deliverables/deploy/k8s/`。

**表 4-7 K8s 对象与职责**

| 对象 | 名称 | 关键配置 |
| --- | --- | --- |
| Namespace | `knock-prod` | 启用 restricted 安全基线 |
| ResourceQuota | `knock-quota` | CPU 8/24、内存 16Gi/32Gi、Pod 40 |
| LimitRange | `knock-defaults` | 默认 500m/512Mi，上限 4C/4Gi |
| ConfigMap | `knock-api-config` | 40 余个非敏感环境变量 |
| Secret | `knock-api-secret` | 连接串、GLM 密钥、JWT 密钥 |
| Deployment | `knock-api` | 3 副本、探针、只读根文件系统 |
| Deployment | `knock-web` | 2 副本、非 root nginx |
| Service | `knock-api` / `knock-web` | ClusterIP，8000 / 8080 |
| Ingress | `knock-ingress` | TLS、限流、安全响应头 |
| HPA | `knock-api` | 3–12 副本，CPU 70% |
| PDB | `knock-api` | `minAvailable: 2` |
| ServiceMonitor | `knock-api` | 15 s 抓取 `/metrics` |
| Job | `knock-db-migrate` | Alembic 迁移，先于滚动 |
| NetworkPolicy | 5 条 | 默认拒绝 + 按需放行 |

### 4.4.3 资源 requests 与 limits

资源申请遵循"requests 按稳态、limits 按峰值、比值不超过 4"的原则。AI 网关属于 IO 密集型，CPU 需求不高但内存随并发线性增长，因此内存 limits 相对宽松。

**表 4-8 工作负载资源与副本**

| 工作负载 | 副本 | requests | limits | 说明 |
| --- | --- | --- | --- | --- |
| knock-api | 3（HPA 3–12） | 500m / 512Mi | 2000m / 1Gi | 4 worker，单 Pod 约 40 RPS |
| knock-web | 2 | 50m / 64Mi | 300m / 192Mi | 纯静态，CPU 极低 |
| knock-db-migrate | Job | 100m / 256Mi | 500m / 512Mi | 一次性执行 |
| export 侧组件 | 由监控栈托管 | — | — | 不占业务命名空间配额 |

按 100 RPS 峰值与单 Pod 约 40 RPS 的处理能力（2 核 1 GB、4 个 worker，非 AI 路径按 P95 300 ms 折算），3 个副本合计约 120 RPS，相对 100 RPS 峰值留 20% 余量，与第 8 章容量模型一致；取 3 副本同时满足单可用区故障时仍剩 2 个副本承接全量，与 PDB 的 `minAvailable: 2` 对齐。HPA 上限 12 副本对应约 480 RPS 的极端容量，足以吸收突发与重试放大。

### 4.4.4 调度、探针与滚动参数

调度上同时使用拓扑分布与反亲和：`topologySpreadConstraints` 约束可用区与节点两级 `maxSkew: 1`，`podAntiAffinity` 以 `preferred` 权重 100 倾向分散到不同节点。使用 `preferred` 而非 `required` 是为了避免节点不足时 Pod 无法调度，宁可暂时同节点也不可用。

**表 4-9 探针与滚动参数**

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| startupProbe | `/healthz`，2 s 间隔，失败阈值 20 | 最多容忍 40 s 启动 |
| livenessProbe | `/healthz`，10 s 间隔，失败 3 次重启 | 只判断进程假死，不判断依赖 |
| readinessProbe | `/readyz`，5 s 间隔，失败 3 次摘流 | 检查 DB 连通与 AI 密钥 |
| `minReadySeconds` | 10 s | 避免瞬时可用被计为就绪 |
| `progressDeadlineSeconds` | 600 s | 超时判定发布失败 |
| `maxSurge` / `maxUnavailable` | 1 / 0 | 滚动期间容量不下降 |
| `terminationGracePeriodSeconds` | 30 s | 覆盖最长非 AI 请求与连接排空 |
| `preStop` | `sleep 8` | 等 Endpoint 摘除传播完成 |

存活与就绪探针必须分离：`liveness` 打 `/healthz` 且恒为 200，只在进程卡死时触发重启；`readiness` 打 `/readyz`，数据库不可达或 AI 密钥缺失时返回 503 摘流。若把依赖检查同时放进存活探针，数据库抖动会引发全部 Pod 连环重启，把小故障放大成全局故障。

集群自身的运维同样要纳入计划。节点池按用途拆分：业务节点池承载 API 与前端，监控节点池承载 Prometheus/Grafana/Loki，两者通过污点与容忍隔离，避免监控写盘影响业务。节点镜像采用"不可变 + 定期轮换"，不打补丁而是替换节点，替换时先驱逐再下线，PDB 保证驱逐过程中可用副本数不低于 2。集群版本每年升级两次，先在 staging 集群验证一周，再升级生产；控制面升级与节点升级分开执行，两次操作之间至少间隔一周。

节点容量按"预留 30% 余量"规划：3 个 4C8G 节点可承载 12 个 API Pod 的极限扩缩，但常态只跑 3 个副本，余量用于 HPA 扩容与滚动时的 surge 副本。若节点 CPU 请求水位长期高于 70%，优先扩容节点而不是调低 limits，因为 limits 决定的是峰值能力，压缩 limits 会在流量尖峰时触发 CPU 节流，表现为延迟劣化而非错误率上升，更难被发现。

### 4.5.1 域名规划

**表 4-10 域名与职责**

| 域名 | 用途 | 后端 | 证书 | 缓存策略 |
| --- | --- | --- | --- | --- |
| api.knock.example.com | 业务 API、健康检查 | knock-api:8000 | cert-manager 自动签发 | API 响应不缓存 |

### 4.5.2 TLS 与证书

入口只启用 TLS 1.2 与 TLS 1.3，禁用 1.0/1.1 与全部弱套件，优先 ECDHE + AES-GCM 与 ChaCha20-Poly1305。TLS 1.3 的 0-RTT 关闭，避免重放风险。HSTS 策略为 `max-age=31536000; includeSubDomains; preload`，仅在确认全站 HTTPS 可用后开启 preload。

证书由 cert-manager 依据 `letsencrypt-prod` 集群签发器自动申请与续期，90 天有效期提前 30 天续签。自签证书仅用于本地与离线演示，命令写在 `nginx/certs/README.md`。证书到期由 Prometheus 的 `blackbox_exporter` 探针监控，剩余 14 天告警、3 天升级为 P0。

真实 IP 透传是限流与审计的前提。请求经过 CDN 与 WAF 后，源 IP 被层层代理覆盖，Nginx 必须信任来自负载均衡网段的 `X-Forwarded-For` 并取最右侧可信地址：配置 `set_real_ip_from` 仅包含 ELB 与 WAF 的回源网段，开启 `real_ip_recursive`，再通过 `$remote_addr` 作为限流键。信任范围必须精确，若写成 `0.0.0.0/0`，攻击者伪造 `X-Forwarded-For` 即可绕过按 IP 限流，等于关闭了限流。

代理链的另一个坑是请求体缓冲。AI 流式响应要求 `proxy_buffering off` 与 `proxy_request_buffering off`，否则 Nginx 会把分块响应攒满缓冲区再下发，前端表现为"卡住很久然后一次性出现"，用户以为系统无响应。相应地，Nginx 的读超时按 60 s 配置，略大于网关的 45 s 上限，保证超时由应用侧的降级逻辑先触发，而不是由 Nginx 直接断连。

HTTPS 之外，内部组件间通信走集群内网并叠加 NetworkPolicy；Pod 到 RDS 的连接启用 `sslmode=require`，Redis 启用 `requirepass` 并限制来源网段。

### 4.5.3 静态资源与缓存

前端构建产物按内容哈希命名，入口 `index.html` 不缓存，从而实现"发布即生效、静态资源长期缓存"。

**表 4-11 Cache-Control 策略**

| 资源 | 路径特征 | Cache-Control | 说明 |
| --- | --- | --- | --- |
| 入口 HTML | `/index.html`、`/` | `no-cache, must-revalidate` | 每次校验，保证发版生效 |
| 哈希静态资源 | `/assets/*.[hash].js/css` | `public, max-age=31536000, immutable` | 内容变则文件名变 |
| 图片与字体 | `/assets/*.png/woff2` | `public, max-age=31536000, immutable` | 同上 |
| API 响应 | `/api/**` | `no-store` | 含个人信息，禁止缓存 |
| 健康检查 | `/healthz`、`/readyz` | `no-store` | 避免中间层缓存假健康 |

压缩同时启用 gzip 与 brotli：brotli 对文本资源压缩率优于 gzip 约 15%，但需 Nginx 编译 brotli 模块；官方镜像不含该模块，因此在配置中保留注释，集群阶段由 Nginx Ingress 的 `enable-brotli` 注解启用。

### 4.5.4 WAF 规则集

**表 4-12 WAF 规则集**

| 规则组 | 动作 | 说明 |
| --- | --- | --- |
| OWASP 核心规则（SQLi/XSS/RCE/LFI） | 拦截 | 基线防护，误报项加入白名单 |

## 4.6 配置与密钥

### 4.6.1 12-Factor 配置分层

配置按敏感度分为四层，越往下越严格：代码内常量 → ConfigMap（非敏感环境变量）→ Secret（敏感环境变量）→ KMS（密钥母体，运行时注入）。应用只读环境变量，不读配置文件、不读挂载的密钥文件，保证同一镜像可跨环境运行。

**表 4-13 配置分层**

| 层级 | 存放位置 | 内容示例 | 变更方式 |
| --- | --- | --- | --- |
| 代码常量 | 源码 | 评分维度权重、危机关键词库 | 走代码评审与发版 |
| ConfigMap | `knock-api-config` | 端口、日志级别、模型名、池大小 | `kubectl apply` 后滚动 |
| Secret | `knock-api-secret` | 数据库连接串、GLM 密钥、JWT 密钥 | ESO 从 KMS 同步 |
| KMS 母体 | 华为云 KMS/CSMS | 密钥明文、轮换版本 | 密钥管理员操作 |

密钥禁止进入镜像、禁止进入 Git、禁止写入日志。CI 中增加两道闸：Trivy 的 secret 扫描与 `gitleaks` 全历史扫描；任一命中即阻断合并。本地开发使用 `.env`（已在 `.gitignore` 中），提交模板为 `env.example`，其中所有机密值均为占位符。

### 4.6.2 密钥轮换周期

**表 4-14 密钥轮换周期**

| 密钥 | 轮换周期 | 轮换方式 | 影响面 |
| --- | --- | --- | --- |
| JWT_SECRET | 90 天 | 双密钥并行，旧密钥保留 7 天验签 | 已签发 token 不受影响 |
| 数据库口令 | 90 天 | 先建新用户再切连接串，最后删旧用户 | 需滚动重启 |
| GLM_API_KEY | 180 天或泄露即换 | 平台侧新建后更新 Secret | 下次请求生效 |
| Redis 口令 | 90 天 | 与数据库口令同流程 | 需滚动重启 |
| OBS AK/SK | 180 天 | 新建子账号密钥后切换 | 导出与备份链路 |
| TLS 证书 | 90 天（自动） | cert-manager 自动续签 | 无感 |
| 管理员初始口令 | 首次登录即改 | 强制改密 + 二次验证 | 无 |

JWT 采用双密钥轮换：`JWT_SECRET` 为主密钥签发，旧密钥保留在验证集合中 7 天，覆盖 refresh token 的最长存活期。轮换窗口安排在业务低峰，且必须先在预发演练。

配置变更本身也要有流程，否则"改一个环境变量"会成为最不可控的变更来源。变更分级为三档：只读参数（日志级别、采样率）可自助修改，改完即生效，事后报备；行为参数（限流阈值、缓存 TTL、模型名）需填写变更单，经值班负责人确认后执行，执行后观察 10 分钟；结构性参数（连接串、密钥、池大小）走完整发布流程，包含预发验证与灰度观察。所有变更记录写入变更日志，与发布记录共用同一份时间线，便于事后定位"哪次改动引入了问题"。

ConfigMap 变更不会自动触发 Pod 重启，这一点必须写进操作手册。修改 ConfigMap 后需显式执行 `kubectl rollout restart deployment/knock-api`，否则新配置不会生效，而运维人员往往误以为已经改完。生产不建议把关键配置做成挂载文件热加载，热加载省下的重启时间远不及"配置已改但未生效"带来的排查成本。

## 4.7 数据库运维

### 4.7.1 PostgreSQL 16 参数建议

参数按 8 核 32 GB 主备实例估算，实际上线后按慢查询与缓存命中率微调。

**表 4-15 PG16 关键参数**

| 参数 | 建议值 | 依据 |
| --- | --- | --- |
| `shared_buffers` | 8 GB | 内存的 25% |
| `effective_cache_size` | 24 GB | 内存的 75%，供优化器估算 |
| `work_mem` | 16 MB | 单连接排序/哈希内存，需乘以并发数 |
| `maintenance_work_mem` | 1 GB | 索引创建与 VACUUM |
| `max_connections` | 200 | 与 PgBouncer 服务端连接数匹配 |
| `wal_level` | `replica` | 支持归档与只读副本 |
| `archive_mode` | `on` | 配合 pgBackRest 做 WAL 归档 |
| `max_wal_size` | 4 GB | 减少 checkpoint 频率 |
| `log_min_duration_statement` | 200 ms | 慢查询阈值 |
| `statement_timeout` | 30 s | 防止长事务拖垮连接池 |
| `idle_in_transaction_session_timeout` | 60 s | 回收悬挂事务 |
| `random_page_cost` | 1.1 | SSD 介质 |

`work_mem` 需要按最坏并发估算：100 个活跃连接各用 16 MB 可达 1.6 GB，仍远低于 32 GB 内存，故 16 MB 是安全值；若出现大量排序落盘再上调，但应优先优化 SQL 与索引。

### 4.7.2 连接池与 PgBouncer

连接数是这类系统最先撞墙的资源。应用侧每 Pod 最多 `DB_POOL_SIZE + DB_MAX_OVERFLOW = 30` 个连接，3 副本即 90 个，HPA 扩到 12 副本时理论峰值达 360 个，超过 `max_connections 200`。因此集群阶段必须在应用与数据库之间加 PgBouncer，并采用事务级池（`pool_mode=transaction`）。

池大小按公式 `服务端连接数 ≈ CPU 核数 × 2 + 有效磁盘数` 估算：8 核实例取 20 个服务端连接即可打满，因此 PgBouncer 的 `default_pool_size` 设为 20，`max_client_conn` 设为 1 000（覆盖 12 副本 × 30 + 运维连接），`reserve_pool_size` 为 5。这样 360 个客户端连接被收敛到 20 个数据库连接，数据库侧的上下文切换与内存开销下降一个数量级。

PgBouncer 不由应用镜像承载，而是作为数据库子网的独立实例或使用华为云 DAS 的连接池代理；Compose 单机阶段副本数固定为 1，应用直连 PG 即可，不做额外一跳。注意事务级池不支持会话级特性（`SET`、`LISTEN`、临时表跨语句），应用代码必须避免依赖会话状态，`SET` 一律走连接初始化参数。

### 4.7.3 只读副本与读写分流

v1 不启用读写分离（`DATABASE_READ_URL` 保留但可留空），原因是一期读多写少的比例尚未实测，盲目分流会引入复制延迟导致的"写完读不到"。上线后按实测数据再开启：当只读查询占总查询 60% 以上、且主库 CPU 持续超过 60% 时，建立 1 个只读副本，把训练记录列表、统计看板、历史对话查询切到只读连接。分流只针对最终一致性可接受的接口，任何"写后立即读"的路径必须留在主库。

### 4.7.4 慢查询与迁移执行顺序

慢查询以 200 ms 为阈值记录到日志并汇总到 `pg_stat_statements` 视图，每周巡检一次 Top 10。索引策略以覆盖高频查询条件为主，现有 9 个索引在上线前逐一用 `EXPLAIN (ANALYZE, BUFFERS)` 验证；新增索引必须走并发创建（`CREATE INDEX CONCURRENTLY`），避免锁表。

统计类查询是慢查询的主要来源。看板上的平均分、训练完成率、危机拦截次数都涉及跨时间范围的聚合，若直接对明细表做 `GROUP BY`，在百万级记录上会稳定超过 200 ms。处理方式是"明细 + 汇总"双层：明细表服务单条查询，汇总表按天预聚合，由定时任务在凌晨写入，看板只查汇总表。汇总任务必须幂等，按天重跑覆盖，出现补数时可安全重算。

大表按时间做范围分区是可选的第三条路径，但对本项目并非必需——百万级年增量远未到分区的收益点，分区的运维复杂度（自动建分区、跨分区查询计划、备份粒度）反而会引入新问题。因此在容量达到单表 5 000 万行之前，优先用索引与汇总表解决，不引入分区。

迁移遵循"先兼容后切换"三步：第一步只做加法（加表、加列、加索引，列必须有默认值或允许 NULL），此时旧版本代码仍可运行；第二步发布新版本代码，双写或兼容读，确认无异常；第三步在新的稳定版本上做减法（删列、删表、收紧约束），且必须在上一步发布后至少一个发布周期之后。任何破坏性变更都拆成两次发布，禁止在一次发布中同时改结构与改语义。

## 4.8 发布策略

### 4.8.1 滚动发布与蓝绿发布

**表 4-16 滚动与蓝绿对比**

| 维度 | 滚动发布（RollingUpdate） | 蓝绿发布（Blue-Green） |
| --- | --- | --- |
| 资源开销 | 额外 1 个副本 | 额外一整套环境 |
| 切换速度 | 逐个替换，分钟级 | 秒级切流量 |
| 回滚速度 | 重新滚动，分钟级 | 秒级切回 |
| 数据库兼容要求 | 必须向前兼容 | 必须向前兼容 |
| 适用场景 | 常规迭代（本项目默认） | 大版本、风险高的结构变更 |
| 实施复杂度 | 低，K8s 原生 | 中，需双 Deployment + Service 切换 |

本项目默认采用滚动发布，配合 `maxSurge: 1`、`maxUnavailable: 0`，保证发布期间容量不下降。蓝绿发布保留给两类场景：涉及认证与权限模型的大版本，以及需要一次性回滚的数据库结构大改。

### 4.8.2 数据库向前兼容三原则

原则一：新代码必须能读旧数据，旧代码必须能读新数据。新增列一律可空或带默认值，禁止 `NOT NULL` 且无默认值的新列。

原则二：删除类操作延后一个发布周期。列与表先标记废弃（注释 + 代码不再写入），观察一个周期确认无读取后再删除。

原则三：结构变更与应用变更解耦。迁移 Job 先于滚动执行，且迁移脚本本身必须幂等、可重入，失败可重试。

### 4.8.3 回滚决策树

回滚判定按"影响面 × 持续时间"两维决策：出现 P0 告警（服务不可用或数据错误）立即回滚，不做观察；P1 告警持续 5 分钟未缓解回滚；P2 告警持续 15 分钟且指标继续恶化回滚。回滚优先用 `kubectl rollout undo` 回到上一个 ReplicaSet，镜像标签不变，秒级生效。

若故障由数据库迁移引起，不能直接回滚应用，必须先停写、执行向下迁移、再回滚应用，顺序不可颠倒。若向下迁移不可行（已删列），则走备份恢复流程，对应第 4.9 节。

### 4.8.4 灰度推进与判定指标

**表 4-17 灰度判定指标**

| 阶段 | 流量比例 | 观察窗口 | 推进条件 | 回退条件 |
| --- | --- | --- | --- | --- |
| 金丝雀 | 5% | 15 分钟 | 5xx < 0.5%，P95 达标，无 P1 | 任一 P1 或 5xx > 1% |
| 半量 | 50% | 30 分钟 | 错误预算消耗 < 10%，AI 降级率 < 5% | 错误预算消耗 > 25% |
| 全量 | 100% | 2 小时 | 无异常，容量水位正常 | 任一 P0/P1 |

AI 链路额外看三个指标：`ai_degraded_total` 的增速、`breaker_state` 是否取值为 2（打开）、`ai_quota_used` 的消耗斜率。任一异常说明新版本在 AI 网关上引入了行为变化，即使 HTTP 层指标正常也应暂停推进。

发布演练在预发每两周做一次，重点是"回滚"而不是"发布"。多数团队对发布路径很熟，对回滚路径却只有文档没有肌肉记忆，真出事时才发现镜像已被覆盖、迁移不可逆、或者没人有生产集群权限。演练要求：随机挑一个历史版本，从当前版本回滚过去，全程计时并要求在 10 分钟内恢复服务；同时验证回滚后新写入的数据仍能被旧版本正确读取。演练结论写入运维记录，暴露的问题进入下一轮改进项。

变更冻结窗口同样要提前定义：重大活动或答辩演示前 48 小时冻结非紧急发布；期末高峰期只允许修复类发布且需双人复核；数据库破坏性变更一律安排在假期窗口。冻结不等于停止一切操作，紧急安全补丁仍可走快速通道，但必须记录绕过理由并经负责人签字。

## 4.9 备份与灾备

### 4.9.1 RPO 15 分钟与 RTO 1 小时的达成路径

RPO 15 分钟意味着最坏情况丢失 15 分钟数据，靠 WAL 连续归档实现：`archive_command` 把 WAL 段实时推送到 OBS，归档延迟监控阈值 5 分钟；每日一次全量基础备份由 pgBackRest 完成，保留 14 天；每周一次全量备份转异地 OBS，保留 90 天。

RTO 1 小时意味着从故障确认到服务恢复不超过 1 小时，其中数据库恢复占大头。按实测恢复速率 100 GB/小时估算，20 GB 的库恢复到任意时间点约 15 分钟，加上镜像拉取、Pod 启动、DNS 切换，总时长约 35–45 分钟，留有余量。

备份链路必须自监控。三项指标进入告警：最近一次基础备份的完成时间距今不超过 26 小时；WAL 归档延迟不超过 5 分钟（对比 `pg_stat_archiver` 的 `last_archived_time` 与当前时间）；备份存储的可用容量不低于 20%。任一项越界都按 P1 处理，因为"备份悄悄失败"是最危险的故障模式——它不影响线上服务，却在真正需要恢复时才发现无备份可用。

恢复后的数据校验分三层：行数校验（关键表行数与备份前快照对比）、抽样校验（随机 100 条记录逐字段比对）、业务校验（跑一遍只读的统计查询，核对汇总值落在合理区间）。三层都通过才允许把流量切到恢复实例，任何一层不通过都退回重做，不允许"先切过去再查"。

**表 4-18 备份矩阵**

| 备份对象 | 方式 | 频率 | 保留 | 存放位置 |
| --- | --- | --- | --- | --- |
| PostgreSQL | 基础备份（pgBackRest） | 每日 02:00 | 14 天 | OBS 同城桶 |
| PostgreSQL | WAL 归档 | 连续（约 16 MB/段） | 14 天 | OBS 同城桶 |
| PostgreSQL | 异地全备 | 每周日 | 90 天 | OBS 异地桶 |
| 对象存储 | 跨区域复制 | 实时 | 跟随源 | OBS 异地桶 |
| K8s 清单 | Git 版本库 | 每次变更 | 永久 | 代码仓库 |
| 配置与 Secret | KMS 版本快照 | 每次轮换 | 永久 | KMS |
| Grafana 仪表盘 | provisioning 文件 | 每次变更 | 永久 | 代码仓库 |

### 4.9.2 恢复演练

备份没有验证过就等于没有备份。恢复演练按季度执行，每次演练必须记录实际 RTO 与数据完整性校验结果。

**表 4-19 季度恢复演练表**

| 季度 | 演练场景 | 验证内容 | 通过标准 |
| --- | --- | --- | --- |
| Q1 | 单表误删恢复到指定时间点 | PITR 到误删前 1 分钟 | 数据完整，RTO ≤ 60 min |
| Q2 | 主库实例故障切换 | 主备切换 + 应用重连 | 切换 ≤ 5 min，无数据丢失 |
| Q3 | 整库恢复到新实例 | 全量恢复 + 应用指向新库 | RTO ≤ 60 min，行数一致 |
| Q4 | 可用区级故障演练 | 跨 AZ 副本接管 + 只读降级 | 可用性不低于 99%，无 P0 |

每次演练后更新 Runbook，把实际耗时、踩到的坑、需要调整的参数写回去。演练在预发环境执行，禁止直接在生产演练；涉及切换的步骤需两人复核。

## 4.10 容量与成本

### 4.10.1 容量推算

**表 4-20 目标规模下的容量推算**

| 维度 | 推算过程 | 结论 |
| --- | --- | --- |

| 请求速率 | 目标 100 RPS | 单 Pod 约 40 RPS，3 副本合计约 120 RPS |
| 数据库连接 | 3 副本 × 30 = 90，HPA 上限 12 × 30 = 360 | PgBouncer 收敛至 20 个服务端连接 |
| Redis 内存 | 限流键 + 缓存，单键小于 1 KB | 512 MB 上限，allkeys-lru 淘汰 |
| 存储增长 | 100 万记录/年，单条约 6 KB（含会话消息、六维评分、审计摘要） | 年增量约 6 GB，含索引与 WAL 约 9 GB，三年预留 30 GB |
| 对象存储 | 报告导出与音频，按 20% 记录带附件 | 首年约 50 GB |
| 带宽 | 100 RPS × 平均 8 KB 响应 | 约 6.4 Mbps，取 50 Mbps 峰值余量 |

按三年周期估算，数据库 30 GB 以内、对象存储 150 GB 以内，均处于 RDS 与 OBS 的基础规格区间，不需要分库分表。分库分表的触发条件定为：单表超过 5 000 万行或单库超过 500 GB，本项目三年内不会触及。

托管方案比自建每月多约 1 400 元，但省去数据库高可用、备份、补丁、监控的运维工作，按 0.2 人力的保守估算已远超差价。因此推荐托管方案；自建方案仅作为预算极紧或数据不得出校园时的备选，且必须自建主备与备份链路，不能省略。

成本还有三条优化路径，按收益排序。第一是规格对齐实际水位：上线首月按峰值规格采购容易过量，运行一个月后依据 CPU 与内存的 P95 水位下调一档，通常可省 15%–25%。第二是包年与预留：数据库与固定节点属于长期负载，包年相比按需通常有较大折扣，但需确认合同期内无重大架构变更。第三是把非关键负载移出计费高峰，例如预发环境在夜间与周末自动停机，监控与日志按 7 天热存 + 90 天冷存分层，可显著压缩存储成本。

成本监控本身也要有阈值。月度账单超过预算 120% 触发告警，按服务维度拆分费用，重点盯带宽与对象存储请求数这两项容易被忽略的支出——带宽超量往往来自大文件下载未走 CDN，请求数异常往往来自客户端重试放大。成本异常与性能异常一样，都应进入每周运维例会。

### 4.10.3 AI 调用成本口径

上两表只覆盖基础设施，AI 推理费用需要单列，因为它是唯一随业务量线性增长、且波动幅度最大的支出项。口径上必须按全 AI 模式估算：现状前端默认进入全 AI 模式（`App.tsx` 的默认值为 `ai`），README 所称"混合模式"与代码实测不符，因此现状即为最高成本档，容量与成本都应按这一档测算，而不是按混合档打折。

**表 4-23 AI 调用量与费用估算（按 2026 年公开价估算）**

| 项目 | 估算过程 | 结论 |
| --- | --- | --- |
| 日活用户 | 5 万账号按 10% 日活 | 5 000 人/日 |
| 日训练次数 | 日活中 30% 完成一次训练 | 1 500 次/日 |
| 日 AI 调用次数 | 每次训练约 14 次（12 轮对话 + 评分 + 复盘） | 约 2.1 万次/日 |
| 现状上限对比 | 全局日上限 800 次（`GLM_DAILY_CAP`） | 仅覆盖需求的 4%，必须扩容 |
| token 用量 | 单次输入约 1.2k、输出约 0.4k token | 月约 7.5 亿输入 + 2.5 亿输出 |
| 月费用量级 | `glm-4.7-flash` 档公开价 | 数百元/月 |

三个结论。第一，现状的 800 次/日上限是课程作品的成本护栏，直接上线会在 1 小时内触顶并全站降级，生产必须按目标规模重设配额，同时保留"单用户每日上限"作为二级护栏。第二，AI 费用在目标规模下与基础设施费用不在同一量级（数百元对比六千余元），真正的风险不是账单而是滥用：刷量、循环调用、重试放大都会让调用量在几小时内翻十倍，因此限流、配额、熔断三件套比成本本身更重要。第三，成本优化应优先做缓存与轮次上限（同一输入命中缓存可直接省下 30% 以上调用），其次才是换更便宜的模型档位，因为换档会同时改变评分风格与用户预期，属于产品决策而非纯成本决策。

## 4.11 上线操作手册

以下 20 步为一次完整发布的标准动作，按发布前、发布中、发布后、回滚四段组织，执行时逐项打勾，任一项不通过即中止。

- [ ] 1. 确认变更单已审批，发布窗口在低峰期（22:00–06:00），通知相关干系人
- [ ] 2. 确认目标版本镜像已推送，CI 全绿，Trivy 无 HIGH/CRITICAL
- [ ] 3. 确认预发环境已用同一镜像验证通过，冒烟用例全通过
- [ ] 4. 确认数据库迁移脚本已评审，属"只加不减"的向前兼容变更
- [ ] 5. 执行全量备份并确认备份完成时间戳，记录当前 RPO 基线
- [ ] 6. 记录当前副本数、镜像版本、错误预算余额，作为回滚对照
- [ ] 7. 在 Prometheus 中静默已知的维护类告警，避免噪音
- [ ] 8. 执行迁移 Job，等待状态为 complete，检查日志无 error
- [ ] 9. 验证迁移后旧版本仍可正常读写（抽查 3 个接口）
- [ ] 10. 更新 Deployment 镜像，观察滚动状态至 3 个新副本全部 Ready
- [ ] 11. 核对 Pod 分布：至少跨 2 个可用区，无单节点集中
- [ ] 12. 校验 `/healthz` 返回 200、`/readyz` 返回 200、`/metrics` 可抓取
- [ ] 13. 执行冒烟脚本：登录、开始训练、单轮对话、评分、导出共 5 条链路
- [ ] 14. 观察 5% 灰度 15 分钟：5xx、P95、AI 降级率、熔断状态四项达标
- [ ] 15. 推进至 50% 并观察 30 分钟，核对错误预算消耗低于 10%
- [ ] 16. 推进至 100%，观察 2 小时，核对 CPU、内存、连接数水位正常
- [ ] 17. 执行 `kubectl rollout status` 确认完成，记录新版本 ReplicaSet 编号
- [ ] 18. 解除告警静默，确认告警通道无异常触发
- [ ] 19. 更新发布记录：版本号、镜像 digest、发布时间、执行人、观测结论
- [ ] 20. 标记变更单完成；若任一环节触发回退条件，立即执行 `rollout undo` 并按回滚清单处理

回滚清单与上述步骤对称：先停灰度推进 → 回滚应用 → 若涉及迁移则评估向下迁移 → 恢复流量 → 校验核心链路 → 复盘记录。回滚同样需要两人复核，尤其是数据库向下迁移操作。

## 4.12 本章小结

- 三套环境在账号、网络、数据、密钥四个维度完全隔离，同一镜像靠 `APP_ENV` 区分行为，禁止环境专属镜像。
- 容器化以多阶段构建、非 root、只读根文件系统、全能力裁剪为基线，镜像控制在 250 MB 以内，冷启动不超过 30 s。
- 编排分两阶段：Compose 保证离线可演示，CCE 用 Deployment/Ingress/HPA/PDB/NetworkPolicy 覆盖弹性与可用性。
- 连接数是首要容量约束，集群阶段必须经 PgBouncer 把 360 个客户端连接收敛到 20 个数据库连接。
- 发布以滚动为主、蓝绿为辅，数据库严格"先兼容后切换"，灰度按 5%→50%→100% 三级推进并以错误预算为闸门。
- RPO 15 分钟靠 WAL 连续归档，RTO 1 小时靠每日全备 + PITR，季度演练验证实际恢复时长。
