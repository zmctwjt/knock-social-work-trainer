**验证方式**：`work/audit_k8s_manifests.py`（纯静态，不需要集群，已进 CI）。

覆盖 100 项检查：YAML 可解析、镜像不用 latest、resources/探针齐全、

`/openapi.json`；`/healthz` 不暴露 pid。

## 二 仅提供制品，未在本机验证 ⚠️

### 2.1 Docker Compose 全栈

**状态：四条核心服务已实际跑通并验证业务链路。**

四个服务全部 healthy：`mysql` / `redis` / `api`（prod 模式 4 worker）/ `nginx`。
为避开本机已占用的 80/8080/6379，用 `docker-compose.slim.yml` 覆盖端口
（mysql 3308、api 8005、nginx HTTP 18080 / HTTPS 18443）。

| 验证项 | 结果 |
| --- | --- |
| 空库启动是否自动建表 | **16 张表**，`alembic_version=0008` ✓ |
| HTTP → HTTPS | 301 跳转 ✓ |
| HTTPS 经 nginx | `/healthz` 返回 `environment: prod` ✓ |
| 登录（经 nginx TLS） | 200 ✓ |
| 案例 / 知识卡（经 nginx TLS） | 12 / 19 条 ✓ |
| 就绪检查 | `ready`，**cache: redis** ✓ |
| 新接口 `/api/v1/me/growth` | 容器内 200 ✓ |

其中 **`cache: redis` 是首次真实验证** —— 此前所有环境都走内存缓存。

**为跑通这一栈修掉的问题**

1. **`docker compose up` 不会执行迁移**（已修并验证）
   新 MySQL 是空库，API 起来后所有查询报
   `Table 'knock.accounts' doesn't exist` → 登录 500。
   修复：把 `alembic upgrade head` 放进容器入口 `docker-entrypoint.sh`，
   成功后再 exec 起服务；失败则容器退出非零，不带病对外服务。
   k8s 里用 `RUN_MIGRATIONS=false` 关闭（迁移由 migrate-job 统一执行，
   否则 3 个副本会争抢）。
2. **compose 多文件合并时 `ports` 是追加不是替换**
   不加 `!override` 的话，nginx 同时保留 prod 的 `0.0.0.0:80`，
   而 80 被本机 Apache 占用 → 容器起不来。已在 slim 文件用 `!override` 修正。
3. **前端静态文件没进 nginx 目录**（已修）
   原挂载 `./static`（只有 README.md），访问 `/` 返回 403。
   改为直接挂 `../../frontend/dist`，不再需要手工拷贝。
4. **nginx 缺 TLS 证书直接退出**
   `nginx: [emerg] cannot load certificate ...`。证书属运营方提供；
   本机验证用自签证书走通（`certs/*.pem` 已 gitignore）。

**仍未验证的部分**

- 未做**跨机**部署（同一台机器上的容器，不是真实多机环境）
- prometheus / grafana / loki / 三个 exporter 未启动（数 GB 观测栈，
  与应用可用性无关）

**复现命令**

```bash
cd deliverables/deploy
cp env.example .env     # 改 JWT_SECRET（≥32 位）与 MySQL 密码
docker compose -f docker-compose.prod.yml -f docker-compose.slim.yml \
  up -d mysql redis api nginx
# 等约 60 秒；入口脚本会自动跑迁移
curl -k -H 'Host: api.knock.example.com' https://127.0.0.1:18443/readyz
docker compose -f docker-compose.prod.yml -f docker-compose.slim.yml down -v
```

## 四 给答辩的建议

被问到"部署验证到什么程度"时，建议如实回答：

> 本地启动、手动部署、CI 端到端三项已实测通过，其中 CI 是在 Linux 上
> 从全新仓库 clone 后跑通的，能证明项目不依赖某台机器的环境。
> 容器化与云原生部分提供的是设计制品与配置清单，未在真实集群验证，
> 属于方案设计成果。

这样比笼统说"都验证过了"更经得起追问。
