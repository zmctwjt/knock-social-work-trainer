## 一 已验证 ✅

### 1.1 本地一键启动（Windows）

**验证方式**：实际执行 `start.bat`，观察输出并访问站点。

| 检查项 | 结果 |
| --- | --- |
| MySQL 私有实例拉起（端口 3307） | ✅ |
| 数据库迁移 `alembic upgrade head` | ✅ 7 个版本依次执行成功 |
| 前端构建（`vite build`） | ✅ 产物落 `frontend/dist` |

| 幂等性（重复执行不重复建库/迁移） | ✅ |

### 1.2 手动启动（四步）

按 `docs/使用说明书.md` 第三章步骤执行，每一步均在 Windows 11 +
Python 3.12 + Node 20 + MySQL 8.0.17 上跑通。

### 1.3 CI 端到端（Linux）

**验证方式**：GitHub Actions `e2e` job，每次推送自动执行。

- 环境：`ubuntu-latest` + MySQL 8.0 service container + 预装 Chrome
- 内容：迁移 → seed → 构建前端 → 启动后端 → 10 个端到端审查脚本
- 结果：**全部通过**（见仓库 Actions 页面最近一次 `CI` 运行的
  「端到端审查」job）

这一步的意义：证明项目从**全新 clone** 出发，在 Linux 上也能完整跑起来，
不只是在我本机能跑。

### 1.4 AI 链路（真实密钥）

**验证方式**：配置真实智谱密钥后，对四条链路各发真实请求
（`work/audit_ai_live.py`、`work/audit_ai_latency.py`）。

| 链路 | 冷调用 | 热调用（缓存） | 结果 |
| --- | --- | --- | --- |
| 意图判定 | 2.5 s | 13 ms | 走模型，判定可用 |
| 服务对象台词 | **0.6 s** | 13 ms | 台词可信、符合人设 |
| 六维评分 | 3.7 s | — | 六维分值与总分正常 |
| 三段式复盘 | 5.9 s | 12 ms | 三段内容非空 |

模型选型依据实测延迟（见 README「AI 链路已用真实密钥验证」）。
三个模型由使用方限定，未超范围。

**降级链**：另起实例配无效密钥，四条链路全部 200 并降级，
`used_ai=false` + `degrade_reason=auth`，页面仍可用。

### 1.5 容器镜像（仅 API）

**验证方式**：`docker build` 构建 `knock/api:1.0.0` 并实际运行容器。

- 多阶段构建成功，镜像内非 root 运行
- 容器启动后 `/healthz` 返回 200，`/readyz` 显示数据库已连
  （连的是宿主机 MySQL 3307）
- 容器内登录接口对真实库返回 200，角色正确
- 容器默认模型链已随代码修正为允许的三个模型

**未做**：完整 `docker compose up`。该 compose 会拉取
redis / grafana / loki / prometheus 等 7 个镜像（数 GB），
与"不在本机额外安装软件"的约定冲突，故仅做了
`docker compose config` 语法与变量校验（11 个服务，通过）。

### 1.8 生产配置强校验

**验证方式**：`tests/test_production_readiness.py`，22 个用例。

SQLite、缺 Redis、关闭限流、自动建表——任一项在 `APP_ENV=prod` 下命中

`/openapi.json`；`/healthz` 不暴露 pid。

## 二 仅提供制品，未在本机验证 ⚠️

### 2.1 Docker Compose 全栈

**状态**：制品齐备且语法校验通过，**未完整启动**。

已做：`docker compose config` 校验通过（11 个服务、变量齐全无警告）；
`knock/api` 镜像已构建并单独运行验证（见 1.5）。

未做完整 `up` 的原因：该 compose 会拉取 redis / grafana / loki /
prometheus / 三个 exporter，合计数 GB，与"不在本机额外安装软件"的
约定冲突。**如需要完整验证，请确认可以拉取这些镜像。**

**制品位置**：`deliverables/deploy/docker-compose.prod.yml`

**如何验证**（有 Docker 环境时执行）：

```bash
cd deliverables/deploy

# ① 准备环境变量（务必改掉默认值）
cp env.example .env
# 编辑 .env：JWT_SECRET 至少 32 位、GLM_API_KEY（可留空）、MYSQL 密码

# ② 起全栈
docker compose -f docker-compose.prod.yml up -d --build

# ③ 等就绪并验证
for i in $(seq 1 60); do
  curl -sf http://127.0.0.1:8000/readyz && break
  sleep 2
done
curl -s http://127.0.0.1:8000/healthz
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/

# ④ 跑权限与接口审查（容器内或宿主机均可）
cd ../..
python work/audit_permissions.py
python work/audit_extended_api.py

# ⑤ 清理
cd deliverables/deploy
docker compose -f docker-compose.prod.yml down -v
```

**预期结果**：`/readyz` 返回 `status: ready`（数据库与缓存均就绪），
首页 200，两个审查脚本全绿。若 `APP_ENV=prod`，还会触发前述八项配置强校验。

## 四 给答辩的建议

被问到"部署验证到什么程度"时，建议如实回答：

> 本地启动、手动部署、CI 端到端三项已实测通过，其中 CI 是在 Linux 上
> 从全新仓库 clone 后跑通的，能证明项目不依赖某台机器的环境。
> 容器化与云原生部分提供的是设计制品与配置清单，未在真实集群验证，
> 属于方案设计成果。

这样比笼统说"都验证过了"更经得起追问。
